# Vocabulary 分段测量：总数、地点规划与分页（2026-11-04）

## 结论

计算“多少页”本身只需除法和向上取整，成本在于先准确找到有多少条匹配记录。结果 COUNT 是部分请求的大头，但不是所有慢例的最大成本：本地同版 SQLite 的七轮对照中，“路 + 22 地点”第一页结果 COUNT 占 SQL 时间约 56%，全库“喉结”约 36%，其分页读取更贵。总数缓存命中后，后续页面仍可能需要全表筛选。

确认三个实现上的优化缺口：地点规划仅接入第一页；规划及分页 SQL 改写放在总数缓存 miss 回调内，命中总数缓存时也会跳过；规划为计算预算额外做一次全库 COUNT。对于这次“路”的实际数据，保留预算探测但强制使用地点索引方案的离线对照明显更快，不能把超过 32768 自动视为“扫描更便宜”。

生产服务器未执行本轮测量，未修改代码、配置或数据库。应用源代码也未修改。实验脚本、原始数据留在 Git 忽略目录，本文是唯一提交内容。

## 测量方法与边界

- 数据：上一轮只读拷贝的生产 vocabulary.db + WAL，529032 条词条、167 个地点；副本文件前后稳定，quick_check 为 ok。它是采集时副本，不是历史请求各自的事务快照。
- 24 个组合：8 个条件/页码，均测当前路径的结果总数缓存 miss/hit；“路”第 1–4 页额外测地点索引对照路径的两种缓存状态。每个组合 7 轮，顺序固定种子随机交错，之前对每个条件运行一次参考查询。
- 先用本地 myapp 镜像加载当前 query 实现，通过只读 sqlite3 适配器记录每条 SQL 的 execute 和 fetch 时间，分别测 Python 剩余时间、可选缓存编码和 JSON 响应编码示例。此镜像为 AMD64，在本机 ARM Docker Desktop 下涉及架构仿真，业务层绝对时间只作补充。
- 主表另用原生 ARM64 的 Python 3.12 / SQLite **3.46.1（与生产同版）**重放实际语句和参数，仍为 24 组合 × 7 轮。Docker Desktop 本地容器上限 2 CPU / 256 MiB，无网络，只读文件系统/挂载，SQLite 页缓存 2 MiB。它只运行 SQL，不代表完整 2C2G 生产服务。
- 结果缓存一律模拟未命中，才能测查询工作；独立总数缓存 hit 用参考查询得到的正确总数模拟，不访问 Redis。总数 miss/hit 会改变现有代码选路，因此不是单纯“删一条 COUNT”的对照。
- 文件系统页缓存没有清空。新建 SQLite 连接不等于冷磁盘；虚拟化文件系统、CPU、机器其他工作均不同于生产。没有测生产 Redis RTT、计算租约/资源准入/线程池/数据库连接池等待、连接 PRAGMA、实际 FastAPI 全链路和网络耗时。
- 所有 168 次业务层组合测量均核对与参考结果的总数、当前页 ID 和顺序一致；覆盖“路”第 1–4 页。这里只证明本副本、本参数的等价性，不替代通用语义/并发写入回归测试。
- 本地业务测量进程峰值 RSS 98316 KiB，原生 SQL 重放进程峰值 18008 KiB；这是实验进程测量，不能推断生产 worker 占用。

## 分段结果

以下为原生同版 SQLite 7 轮中位数，单位 ms。各阶段分别取中位数，列相加可能不等于合计。规划包括地点名、元数据解析、全库规模 COUNT 和候选预算探测；结果 COUNT 指计算本搜索匹配总数。

| 条件（结果总数缓存 miss） | 地点规划 | 匹配结果 COUNT | 查询当前页 | SQL 合计 | 结果 COUNT 占比 |
|---|---:|---:|---:|---:|---:|
| 调皮，全库 p1 | 0 | 182.6 | 201.5 | 382.9 | 47.5% |
| 喉结，全库 p1 | 0 | 159.8 | 284.4 | 442.1 | 36.0% |
| 路 + 22 地点 p1 | 91.8 | 264.1 | 113.4 | 468.0 | 56.2% |
| 路 + 22 地点 p2 | 0 | 315.6 | 35.4 | 350.9 | 89.9% |
| 路 + 22 地点 p3 | 0 | 317.4 | 36.6 | 353.8 | 89.7% |
| 路 + 22 地点 p4 | 0 | 317.1 | 37.6 | 354.6 | 89.4% |
| 韭 + 五華 p1 | 89.9 | 0 | 1.9 | 91.7 | 0% |
| 喉结 + 文昌 p1 | 92.4 | 0 | 0.9 | 93.4 | 0% |

“韭”只返回 1 条，“喉结 + 文昌”返回 0 条，第一页不足 50 条直接推断结果总数，无需再统计匹配结果。但其地点规划仍分别花 84.5/86.8 ms 执行全库规模 COUNT。**这两种 COUNT 必须分清：529032 用于规划预算，338 才是“路”的匹配结果总数，7 才是页数。**

全库“调皮”“喉结”的 COUNT 和分页执行计划都仍为 SCAN e；多字预过滤只减少每行匹配代价，不提供子串索引定位。查 50 条也可能需要检查很多不匹配行；后续 OFFSET 还需要跳过先前匹配项。

业务层对照中，50 条结果的可选缓存编码约 1.3 ms、JSON 响应编码示例约 0.8 ms，远小于上述 SQL。这里没有测实际响应模型验证、网络发送和 Redis 写入，不能给它们填写零耗时。

## 总数缓存命中后，为何仍慢，甚至更慢

代码将设置 page_sql 的优化逻辑放入 execute_count 回调。结果总数缓存命中时不执行回调，因此会跳过地点规划及该回调中的多字预过滤选路。如果外层完整结果缓存命中则直接返回，不进入这些 SQL；以下专门测外层 miss、总数 hit。

| 条件 | 总数缓存 miss，SQL 合计 | 总数缓存 hit，SQL 合计 | hit 后路径 |
|---|---:|---:|---|
| 路 p1 | 468.0 | 114.1 | 无 COUNT，原分页扫描 |
| 路 p2 | 350.9 | 269.8 | 无 COUNT，原分页扫描 |
| 路 p3 | 353.8 | 277.7 | 无 COUNT，原分页扫描 |
| 路 p4 | 354.6 | 281.0 | 无 COUNT，原分页扫描 |
| 韭 + 五華 p1 | 91.7 | 335.7 | 无 COUNT，也没有小地点规划，分页退回扫描 |

“韭”的回退可在代码和本地参数上稳定复现，尚无证据确认线上那条 2.789 秒请求当时命中了哪个缓存。总数 hit 可以通过结果键被 LRU 淘汰等情况独立于结果 miss 出现。

注意同一页在先执行 COUNT 与未执行 COUNT 时，其数据/索引缓存状态可能不同，分页时间不能机械相减。例如“路”p2 的 miss 分页为 35.4 ms，hit 的分页约 269.8 ms；该对照同时改变执行前的读取状态。不能据此建议保留多余 COUNT 或声称其差额都是查询计划变化。

## 地点规划是什么，为什么后续页没有用

其工作是先在小型地点名称/元数据集合中解析 locations 原来的包含匹配语义，得到匹配的地点名及额外 (user_id, location_name) 身份，再通过现有地点索引，只读取这些地点的词条，最后检查 q、排序和分页。它不把所有词条 ID 一次装进内存，也不能简单用地点名等值替换原模糊匹配，否则可能改变结果。

当前实现存在两个明确限制：

1. query.py:665 的 scoped_eligible 写死 page == 1。
2. query.py:697 的规划及 page_sql 改写位于 execute_count；query.py:753 的独立总数缓存命中会跳过整个回调。

此前实施计划明确把优化限定在首个页面和 lazy count miss 回调，以保留其他路径。它是实现范围选择，不是业务或 SQLite 要求，也不是第二页无法按地点索引查询。

## “路”是否应当超过预算就回退

本例探测达到 32769，超过 32768 预算。增加两个有针对性的同版 SQLite 对照，各 7 轮：

| 路 p1 方案 | SQL 合计中位数（ms） | 结果核对 |
|---|---:|---|
| 当前方案：规划后回退，含结果 COUNT | 468.0 | 总数 338，p1 为参考结果 |
| 保持原分页方案，单独移除结果 COUNT 语句 | 235.5 | p1 ID/顺序一致；本组合不计算总数 |
| 保留全库规模 COUNT 和预算探测，只忽略本例回退决定，走地点索引 | 158.9 | 总数 338、p1 ID/顺序一致 |
| 地点索引，同时省去全库规模 COUNT / 候选预算探测 | 66.6 | 总数 338、p1 ID/顺序一致 |

两个单独追加对照与主表分批测量，缓存/负载有波动，不能把数字当精确可相减的代数关系。结果支持：**本例回退不是最优；只省去结果 COUNT 还没有用地点索引的方案快。** 最后一行是多项变化的组合，不能将全部改善归于单独提高预算。

地点索引对照还覆盖了“路”的其他页面；下面模拟总数已经缓存，不再执行结果 COUNT，仍解析原有地点匹配语义：

| 页面 | 当前分页扫描（ms） | 地点解析 + 索引分页（ms） |
|---|---:|---:|
| p1 | 114.1 | 31.8 |
| p2 | 269.8 | 33.0 |
| p3 | 277.7 | 37.7 |
| p4 | 281.0 | 42.9 |

这些是离线诊断对照，不是已经实施的应用改动。没有证明所有大范围都适合强制走索引，不应直接删除预算保护。

## 优先级与尚未定位的线上延迟

建议优先将分页选路与“是否需要计算总数”解耦，再覆盖后续页；减少规划为计算预算而执行的全库 COUNT；根据真实候选覆盖范围重新验证成本选择。“路”这一类可以同时优化 COUNT 和分页，不应只关闭总数统计。若产品允许只有上一页/下一页、返回 has_more，才考虑改变精确总数契约；当前没有实施这种行为变化。

本轮仍未复现历史线上 10–14 秒，不能把该延迟按本地阶段占比直接拆分。要确认生产的额外耗时，需要有界记录请求 ID/worker PID、结果/总数缓存命中、计算租约等待、准入等待、数据库连接获取、规划、结果 COUNT、分页、编码阶段。当前日志只有完整请求 duration，缺失这些历史阶段证据。此次不改生产，所以不能用臆测填补这一部分。
