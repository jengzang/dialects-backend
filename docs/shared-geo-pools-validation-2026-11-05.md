# Toponyms / GIS 通用连接池：验证与收益（2026-11-05）

## 已实施的范围

业务读取接入 app/sql/db_pool.py 的同一池实现、同一管理器和停机释放；移除 GIS 的 _ReadOnlyPool 和 toponyms 的逐请求自行建连逻辑。其他数据库原来的可写通用池默认配置保持；ORM 的统一管理入口不变。通用 SQL 管理接口仍沿用自己的现有连接路径，本次不改其写入权限或管理行为。

| 配置 | toponyms | GIS |
| --- | --- | --- |
| 连接权限 | mode=ro + query_only | mode=ro + query_only |
| 连接创建 | 惰性 | 惰性 |
| 页缓存目标/连接 | 4096 KiB，沿用原值 | 2000 KiB，明确原 SQLite 默认预算 |
| temp_store | FILE，沿用原值 | FILE，避免使用其他可写池的 MEMORY 配置 |
| busy timeout | 100 ms，沿用原值 | 5s，沿用原值 |
| 每 worker 最大借出/存活连接 | 3 | 6，沿用原上限 |
| 每 worker 最大空闲连接 | 1 | 3 |
| 池满等待 | 0，返回 QueryBusy / HTTP 503 | 最多 5s |

不预建连接，不新增执行线程、进程、任务队列或重试循环。toponyms 原有跨 worker heavy=2/light=1、tree=1（占用 heavy）准入保持；池的3条上限不代替跨进程限流。流式仍每批256行，借用直到消费结束或断连，保留 limit=0 完整结果合同，不新增总时限。

饱和时不绕过池建立连接；故障归还丢弃失效连接，后续请求按需新建；超额归还直接关闭。归还前清除 progress/trace/authorizer，关闭活跃游标，回滚事务，恢复 row_factory/query_only，再检测健康。连接初始化失败关闭连接并传播，不启动后台重试。运行中的SQL仍只在原有同步任务/线程工作中执行。

只读池不设置 WAL、synchronous 等持久配置，不复制数据库，也不会因路径错误新建空库。连接按文件身份（dev/ino/mtime/size/ctime）检测版本变化，旧空闲句柄在借出前丢弃，旧活跃句柄在归还时丢弃，不强制中断正在执行的请求。GIS几何缓存按文件身份+sub_id隔离、元数据随连接版本刷新；旧请求不会覆盖新元数据或把旧几何用于新库候选。仍是一个总条数受原 GEO_CACHE_MAX_ITEMS 限制的 LRU，不为每个版本另建缓存。

## 为什么 toponyms 最终保留 4 MiB

首次实验统一为2000 KiB：简单查询明显受益，但 points prefix（q=大、limit=5000）中位数约143→164ms，约慢14%。随后4096KiB实验恢复到原实现附近，因此没有强行统一数值。统一实现/配置入口允许按数据库保留不同预算。

toponyms 旧实现结束请求时不保留连接，新实现空闲最多保留1条，即最多约4MiB页缓存目标；不能从结构上承诺空闲内存必然下降。并发最多3条，页缓存目标合计约12MiB，与旧的3个并发连接相同。GIS按需创建，顺序负载可以只用1条；并发压力后可保留3条/临时最多6条。页缓存目标不是进程RSS硬上限，SQL临时数据、SQLite/Python分配器、GIS几何LRU与操作系统页缓存仍另外消耗资源。

## 测量方法

只在本地真实数据库测量：toponyms约4.9GiB、GIS约181MiB。不访问生产，不复制数据库，全部 mode=ro 打开。

scripts/benchmark_geo_pools.py 每个服务/实现使用3个独立进程，每项查询5次。旧实现动态读取 Git b299cc2 的资源模块/GIS引擎，当前实现在同一工作树运行；共享相同SQL、数据、加载算法。进程顺序执行，第2轮交换前后顺序，减轻系统页缓存顺序偏差。导入相同模块后才取RSS基线，不使用Redis结果缓存。对所有成功输出比较SHA256，结果一致。

耗时为三个进程内5次中位数的中位数，包含首次，不含HTTP网络和结果哈希计算。不是系统冷缓存测试；本地也没有模拟生产2核2GB的并发请求压力。

## 最终实测：toponyms

参数及耗时单位为ms；RSS为MiB。

| 查询 | 条件 | 原实现 | 通用池 |
| --- | --- | ---: | ---: |
| 名称前缀 | q=大, prefix, limit=20 | 0.5065 | 0.0652 |
| 名称包含 | q=村, contains, limit=20 | 0.4290 | 0.0579 |
| 精确搜索 | q=大村, exact, limit=100 | 0.4624 | 0.0987 |
| 点位前缀 | q=大, prefix, limit=5000 | 141.2408 | 145.1919 |
| 行政子级 | parent_code=44 | 0.4809 | 0.0593 |
| 流式reader | q=村, contains, limit=5000 | 5.3332 | 4.8772 |

这里流式一行直接测reader，不测HTTP路由；真实HTTP的limit=5000仍走普通查询，>5000或0才走流式。名称两项各20条、精确搜索返回100条、行政子级22条；并非空结果测量。

每进程共30次调用：新建连接30→1（减少96.7%），空闲存活0→1。查询结束后RSS增量中位数8.5781→7.9219，约少0.66MiB；三次范围分别8.55～8.62和7.86～7.95。累计查询CPU中位数752.661→760.702ms，约增加1.1%，没有整体CPU下降结论。较重的点位查询占主要CPU，连接复用不能优化它的SQL扫描/排序。

首次名称前缀约0.924→0.964ms，没有改善；约79%～88%的加速主要发生在简单重复查询，绝对节省约0.4ms。点位查询本轮约慢2.8%，前几轮在两侧波动，没有稳定提速证据。探索阶段还观察到首次点位查询触发原2s预算；最终轮90次调用/实现均未超时，不能据此声称冷读取超时已解决。

## 最终实测：GIS

| 查询 | 条件 | 原实现ms | 通用池ms |
| --- | --- | ---: | ---: |
| 初始化 | init_store | 0.3532 | 0.3973 |
| 点查询 | lng=116.4074, lat=39.9042 | 7.5617 | 7.6545 |
| 边界重建 | feature_id=110101 | 0.0484 | 0.1153 |
| 名称搜索 | q=北京 | 0.7958 | 0.6887 |
| 子级 | parent_id=11 | 0.0210 | 0.0511 |

首次点查询约21.74→21.88ms；点查询返回3个命中，搜索18个结果。边界/子级等很轻查询增加约0.03～0.07ms，来自管理器、文件身份和回收清理开销。没有GIS普遍提速结论。

每进程连接3→1，空闲3→1（这是顺序负载，不代表并发后仍只保留1条）。查询结束后RSS增量中位数25.1562→23.4219，约少1.73MiB；三次范围25.08～25.19和23.39～23.45。累计查询CPU约56.452→56.632ms，基本持平。几何解码缓存保持原条数上限，仍然是显著资源来源，本次没有将其清空以制造内存收益。

这些是本机实测，不能承诺每个生产worker节省同样内存；尤其SQLite原生分配器可能保留已经关闭连接释放的内存。此次改善主要是连接生命周期、重复轻查询和资源上限可控，不是OOM根因的完整修复，也没有优化大范围SQL或GIS几何运算。
