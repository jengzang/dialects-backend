# 词表查询下一步优化审查（2026-10-25）

基线：20bf8f8。此次仅审查、只读原型实验，不修改业务代码或原数据库，不提交新索引，不扩大标准词缓存，不引入应用临时聚合/响应文件。

## 推荐顺序

1. standard-words：为关键词叠加地点文本筛选单独选择查询计划，复用现有地点身份索引。下一步优先实施这个可量化的 SQL 优化。
2. 大响应：省掉确定无法缓存的响应所做的完整缓存编码/Redis 传输；不增加缓存，不截断 HTTP 返回。先验证现有各种响应类型和永久键例外。
3. map-items：单遍读取并直接构建最终条目，减少全量中间列表和宽字典；这是内存优化，当前原型没有明显提速。
4. map-points：保留已有分组路径；不要统一强制全表扫描。先补 HTTP 校验/编码阶段测量，再决定是否调整响应生成。

前端参数、响应结构、数组顺序、精确总数、简繁匹配和原有完整返回能力必须保持不变。

## 新实验：标准词关键词叠加地点

当前 standard-words 在没有地区条件时通常让 SQLite 自行选索引；关键词+地点仍可能扫描 standard_word/location_name 索引，再读取大量词条内容。对存在 locations 的原型改用现有 idx_vocabulary_entries_user_location，减少不必要的词条内容读取，然后对命中记录分组。

这仍是索引扫描，不是普通索引能够定位任意子串。EXPLAIN 显示 SCAN，而非把 LIKE 变成精确 SEARCH。新计划出现 GROUP BY 临时 B-tree，其内存/磁盘成本需要在生产 SQLite 版本和高命中场景继续验证，不能声称无任何临时 I/O。

全部标准词实验使用 limit=None，逐次比较完整返回字段、顺序和 total；returned == total。每种版本交替五轮取中位数，计时只包括服务函数；未计 Redis、HTTP、网络。

| 场景 | 当前 95,003 条：原→候选 ms | 增长 950,030 条：原→候选 ms | 增长规模耗时减少 |
|---|---:|---:|---:|
| q=什么，locations=廣州，完整 690 组 |109.181→37.994|901.661→306.947|66.0%|
| q=人，locations=廣州，完整 6,979 组 |88.939→36.156|772.490→220.234|71.5%|
| 地点文本没有命中，完整空结果 |43.578→4.998|641.221→51.337|92.0%|
| 多地点文本，完整 31,631 组 |约 1.7% 改善|472.493→423.458|10.4%|
| 关键词+省市+地区+地点，完整 6,979 组 |约 3.9% 改善|232.638→228.177|1.9%|

结论：优先针对“关键词+地点文本”和“无命中地点”设计条件分支；不能为了收益很小的组合强制换索引。原型是把全部 locations 条件强制改为身份索引，尚不等于可直接发布的最终分支。下一轮需要补地点选择性、通配符、definition 单字段、混合 location OR、简繁、多选、NULL、孤立词条、跨用户同名地点及完整结果的回归。

本机 macOS arm64、Python 3.12、SQLite 3.53.2；原库只读，增长数据在可删除的实验库中生成。增长只复制用户/地点身份，没有增加词形和地点名称种类。数据页预热结果不能当成生产 2 核 2 GB 延迟预测。首次矩阵测试与 map-items 实验有短暂重叠，因此表格采用之后顺序运行的独立复测结果。

实验文件：/tmp/vocabulary_next_review_full.py；原始结果 /tmp/vocabulary-next-review-full.json。另有 5 轮条件矩阵复测 /tmp/vocabulary-next-review-confirm.json。

## map-points：哪些改法不值得做

对同一基线，将聚合输入统一换为 NOT INDEXED，完整结果保持一致，但增长规模复测：

| 场景 | 当前实现→强制顺序扫描 ms |
|---|---:|
| 无关键词 |约40→226（首轮矩阵，仅作方向参考）|
| 默认字段搜索“什么” |378.200→367.078|
| 只搜 definition |86.702→75.590|
| 小省份 |3.771→95.265|
| 地点文本 |78.713→195.699|
| 关键词+地点文本 |314.923→374.122|

仅少数查询略快，反例很大，不能照搬 standard-words 的顺序扫描分支。definition 单字段是可继续研究的小范围候选，但需要比较覆盖索引和不同命中比例，收益优先级低于标准词关键词+地点。entries 的任意子串计数与深 OFFSET 扫描也仍存在；现有计数复用、空页短路、分页后 JOIN 已实施，没有证据再承诺普遍倍数提升。

## map-items：低复制原型的实际边界

当前实现 fetchall → 每条宽字典 → 分组列表 → 最终 dataclass；元信息会随词条重复保留。原型改成遍历游标，每条立即构建 VocabularyMapItem，每组保留一份元信息和最终 items；最后组装响应。保持当前按完整元信息合并地点的规则和首条出现顺序，不能仅按 user_id/location_name 替换分组语义。

独立复测结果（当前 95,003 条库，完整返回选词对应的全部记录）：

| 场景 | 完整记录数 | 服务耗时原→候选 ms | tracemalloc 峰值原→候选 MiB |
|---|---:|---:|---:|
| 选 1 个高频词 |51|0.173→0.189|0.092→0.060|
| 选 100 个高频词 |3,374|11.249→11.705|4.819→1.428|
| 选 1,000 个高频词 |19,887|75.777→75.185|27.130→8.073|
| 1,000 词+关键词 |1,322|16.874→16.846|2.050→0.719|
| 1,000 词+地点文本 |11,119|46.693→47.279|15.331→4.777|

峰值是单次调用的 Python 分配峰值，测量与计时分开，不是进程 RSS、生产机器总内存或 HTTP 编码峰值。原型不构成固定内存上限，最终 items 仍随完整结果数量增长，不能宣称“有界内存”。空/无效坐标占比很高时还需避免重复解析同组坐标。已比较上述场景完整结果，尚需异常坐标、跨用户合并和并发修改等正式回归。

实验 /tmp/vocabulary_mapitems_review.py；结果 /tmp/vocabulary-mapitems-review.json；独立复测日志 /tmp/vocabulary-mapitems-review-confirm.log。

## 缓存编码和 HTTP 响应

cache.py 的 store 先 encoded(value)，把完整参数发给 Redis，再由 Lua 对按需键做 128 KiB 判断。过大结果即使不缓存，也承担完整 Python 转换、JSON 编码和传输成本。默认永久键不受该上限约束，不能直接套用统一跳过规则。

已有上轮独立实验（非本轮新测）：完整 39,965 个标准词组，缓存编码约229→4.5ms；仅缓存准备阶段，不含 HTTP 编码，更不是接口整体提速98%。建议在达到现有上限时终止缓存编码，完整结果继续返回，不增加标准词缓存或更改缓存命中内容。超大单字段的编码器分片仍可能一次创建大字符串，因此需验证字节预算能否限制中间分配，不能仅靠 iterencode 宣称严格内存上限。

路由是 async def 且有 response_model。本机 FastAPI routing.py 的 serialize_response 在异步路由路径同步调用 field.validate；返回普通对象后还需完整响应编码。现有 run_bounded 主要覆盖服务函数，不能认为所有校验、编码、传输均已受 expensive 槽保护。下一步应补测服务完成至首字节、响应编码峰值和事件循环延迟，再决定是否在同一准入工作单元里生成已验证的 JSON Response。不得直接跳过响应校验，不得为了编码新增无限线程池。

## 并发、失败、资源和长期方案

这些候选不增加 worker、线程配额、常驻服务或自动重试。仍沿用2个heavy槽、1个expensive槽、8个等待名额与30秒准入预算；接受后的完整查询没有新增执行超时。实现时SQL失败应沿用现有异常路径，不额外自动重跑一次全量查询。动态试跑多个计划会增加CPU/I/O，不适合每个线上请求先探测再选计划。

标准词全量聚合的归一分组、地点去重和词形字典仍随不同词组/地点组合增长，换 SQL 不能消除这部分计算。无关键词全量、低选择性单字搜索、广泛地点匹配不应承诺同样收益。先利用上述代码/SQL方案；如未来仍无法满足性能，再单独比较持久化归一键及索引（需完整维护所有写入/编辑/导入路径）。普通 B-tree 无法解决任意子串扫描；FTS/ngram 需验证中文单字/双字、通配符与简繁语义，写放大和磁盘成本也需实测，不建议这轮直接引入。
