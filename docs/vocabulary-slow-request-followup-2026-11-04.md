## 代码路径与证据边界

1. 全库“调皮”“喉结”：包含搜索采用 `%词%`，多字稀疏样本可启用 instr 必要条件，但它仍逐行检查。首页返回满页时仍需要精确 COUNT；输出 LIMIT 50 不能限制 COUNT 工作量。缓存可以复用已有结果/总数，无法消除新参数首次计算。
2. “路 + 22 地点”：单字不启用 instr 预过滤。locations 现有语义是包含匹配，既查条目地点名，也查地点表多个元数据列；不能把用户选中的名称直接当成原本只做索引等值匹配。第一页地点规划有候选数量预算，超限会回退，第二页起则不启用该规划。
3. entries 查询结果缓存包含 page；总数有独立缓存，可跨分页共享。第二页仍需重新筛选/排序/跳过行，不能把所有分页耗时归因于重新 COUNT。具体请求是否命中缓存，历史日志无法确认。
4. SQL query 是另一条实现：先 SELECT 分页，再 SELECT COUNT，未复用 entries 的规划和独立总数缓存。它可能受条件扫描、排序、OFFSET、返回列大小影响；请求体缺失，无法定位这五次中的具体条件。
5. 请求 duration 还包括缓存通信、计算租约等待、资源准入等待、SQL、编码等。当前没有逐阶段计时和 request ID/worker PID，不能把线上 10–14 秒全部算作 SQL。

日志内没有与这些 entries 慢请求重叠的 vocabulary/toponyms 长请求记录，不能据此认定是在线并发排队；后台预热、未完成/未留存请求与其他系统负载仍未排除。

## 生产数据副本的本地核验

将同一份副本、实际参数和当前查询实现结合后确认：

- “路 + 22 地点”的候选探测返回 **32,769**，超过规划预算 **32,768**，第一页实际选择回退；执行计划显示分页和 COUNT 都 `SCAN e`。查询总数为 338。第二、三页同样扫描；本地模拟独立总数缓存命中后，二、三页不再执行 COUNT，但仍有分页扫描。
- “调皮”“喉结”启用了 instr 预过滤，分页和精确 COUNT 仍为 `SCAN e`，总数分别 119、74。优化已生效，但没有变成索引定位。
