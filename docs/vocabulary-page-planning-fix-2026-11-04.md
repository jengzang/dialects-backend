# Vocabulary 地点分页修复与测量

本次已完成本地实现，未部署、未连接或修改生产服务器。目标是修复地点查询在总数缓存命中、后续页、候选预算不足时丢失优化路径的问题。保留精确 total，没有取消总页数计算。

## 改动与适用范围

1. 将分页 SQL 规划从总数缓存 miss 回调中移出，每请求按需最多准备一次。总数缓存命中仍可使用地点索引方案；符合条件的后续页也可使用。完整响应缓存命中仍直接返回。
2. 移除仅为决定预算而执行的全表精确 COUNT。优先读取现有 sqlite_stat1；无有效统计时只数最多 4097 条。实际结果 total 仍精确计算或复用原缓存。
3. entries 的地点候选上限从 32768 调整为 65536，估计覆盖比例从 1/10 调为 1/4，使实际“路 + 22 地点”的 63382 个候选能够进入索引路径。聚合保留原 32768 / 1/10 政策。
4. 明显宽范围通过现有平均行数估计提前回退，保留 2 倍余量，避免先走完整候选预算才拒绝。陈旧估计最多影响选路，不参与过滤或截断结果。

主要改善具有选择性的地点范围查询，包括连续翻页、换 page_size 后仅命中总数缓存、definition 单字段和该范围内高命中词。没有地点条件的全库模糊检索仍有全库扫描成本，本次没有消除。

分段看，“路”第 1 页 miss 的旧规划全表 COUNT 约 83.66ms，改为统计读取约 0.02ms；候选探测由约 0.80ms 变为 10.63ms，但成功进入地点方案，分页从 115.44ms 降至 19.06ms，结果 COUNT 从 264.31ms 降至 28.33ms。第 2 页总数 hit 原本仍花 271.67ms 扫描分页，修复后加上地点准备，总耗时 37.34ms。因此总数是一个大成本，但分页扫描也需要修复，不能只取消或缓存 COUNT。

另用现有 AMD64 服务镜像在 ARM Mac 仿真执行真实 Python 查询入口（同样 420 样本）：“路”第 2 页 miss 为 438.03 → 88.84ms，hit 为 301.40 → 48.52ms；“韭 + 五華”hit 为 378.65 → 8.90ms。此组用于核对服务行为，绝对耗时以原生 SQL 对照为主。

这些是本地数据库重放，不含生产并发、等待槽、连接池、Redis 网络、应用日志和在线文件缓存争用。此前线上 10–14 秒没有被本地 SQL 单独重现，不能据此承诺线上全部请求低于 2 秒，也不能宣称 OOM 已修复。

## 资源边界与正确性

- 不增加 worker、线程、服务、后台任务或重试；原 heavy=2、expensive=1、在线等待者上限 8 不变。SQL 仍在现有受限工作槽中执行。
- 每次 entries 候选探测最多 65537 条索引项，仅返回计数；无统计规模探测最多 4097 条。地点名和额外身份各最多保留 256 个，最多 32 个地点条件，不生成词条 ID 列表。地点元数据匹配仍可能扫描元数据表，固定返回缓冲不代表总 I/O 恒定。
- 原生重放容器限制 2 CPU / 256MiB，观测进程峰值 RSS 23.90MiB；服务对照峰值 RSS 76.25MiB。两者均是单次本地测量，不代表线上完整 worker 或 2GB 整机峰值，也不是修复前后内存下降的证据。
- 保留原 count SQL 与绑定作为缓存键；保留精确 total、简繁变体、地点子串、跨用户和孤立记录、排序与页码语义。缓存 total 为零或页码越界时不做地点探测或分页 SELECT。
- 规划、结果 COUNT 和分页置于同一读 SAVEPOINT，异常释放自身 SAVEPOINT，保留调用方事务。缓存 total 沿用原有独立缓存的一致性边界，不宣称缓存 total 与当次数据库严格同一快照。
- 超预算继续使用完整正确查询，不截断候选或结果。宽范围回退仍可能较慢，后续应以线上只读证据评估。
