# Vocabulary 延后总数：实现、测量和兜底

本地实现，未推送或部署，未连接或修改生产服务器。前端提交 `34eb9753`。沿用现有生产数据库只读副本（529032 条词条、167 个地点），没有在线压测。

## 行为

`GET /api/vocabulary/search/entries?defer_total=true` 选择新模式；缺省仍同步提供精确 total。新模式返回 `items / page / page_size / has_more / total`，total 未就绪时为 null，不返回猜测值。没有新增轮询接口、服务或任务队列。

1. 先复用已有旧模式/预热的完整响应；否则复用新模式完整响应。命中时不执行 SQLite、不启动计数。
2. 完整响应 miss 时读取现有 entries-count。仍使用相同原始 count SQL/绑定及数据版本键，不为页码、page_size、新模式创建额外总数缓存。
3. 当前页最多读取 page_size+1 条（接口 page_size 最大 200，所以最多返回给 Python 201 条），向客户端返回前 page_size 条，以额外一条判断 has_more。
4. 首页返回 <=page_size 条时已知精确 total；后续非空末页可以推出 offset+返回数量，直接写原总数缓存。空越界页只能证明 total<=offset，不猜总数。
5. total 未知时不缓存完整响应，避免 pending 页面长期遮挡已算好的总数。由处理该请求的同一 worker 在 Starlette BackgroundTasks 中、响应体发送后尝试精确 COUNT；独立 Session，成功后写现有总数缓存。客户端下一次加载可读到它，未算完也正常继续。

前端只改 API 参数/类型说明、卡片和地图详情的 has_more 状态与入口判断。旧后端没有布尔 has_more 时仍使用原 total 判断；保留未知总数 null。没有组件拆分、样式更改或轮询。顺便修正本次测试发现的卡片追加失败后页码提前递增问题，现在重试同一页。表格、字音注释、地图聚合和顶部全库统计的 API 不变。

## 后台资源边界及失败处理

| 情况 | 处理 |
| --- | --- |
| 多个 worker/不同条件同时请求 | 跨 worker 的数据库级 Redis lease 限制后台计数最多 1 个；同条件还复用原 compute 锁，和旧同步 COUNT 去重 |
| 资源繁忙 | 复用 expensive=1 / heavy=2 工作槽，background 模式只尝试一次、不占在线等待者名额、不排队；后续真实请求可再尝试 |
| 用户很快加载下一页 | total 可继续为 null，has_more 独立工作；不等待后台任务 |
| 计算太慢 | SQLite progress handler 每 10000 个虚拟机操作检查 5 秒期限，实际中断 SQL；它是合作式检查，不是严格墙钟耗时保证 |
| 数据库锁等待 | 后台连接临时 busy_timeout=100ms，避免原 10 秒锁等待绕过 progress 检查；finally 恢复原连接设置并移除 handler |
| SQL/后台异常 | 记录警告并设置全数据库 15 秒冷却；没有自动重试循环，已返回页面不受影响 |
| Redis 故障/断路器打开 | 优先返回 lookahead 页面；无法可靠缓存/去重时不启动后台计数 |
| 计数期间数据更新 | 开始时核对 entries/locations 版本；原 Lua 缓存写入再次原子核对版本，旧任务不能写进新版本 |
| worker 中途退出 | 工作可丢失；lease 120 秒自动过期，后续请求可重算；分页无需等待。不是持久任务系统 |
| 协程取消 | 复用取消安全的 lease 获取；已提交的 SQLite 线程先完成/被期限中断，再关闭 Session、释放资源和 lease |
| 推导了零结果/末页 | 直接复用精确 total，无须后台 COUNT |

后台没有新增执行器或专用线程池，复用现有线程调度。额外控制 key 为每库 count-active/count-cooldown 两个，compute 锁沿用原机制，均有过期；总数和完整响应继续使用现有有界缓存容量。请求携带的条件有原接口约束，不保存完整结果集或 ID 列表。单行文本大小沿用原数据约束，201 行上限不是严格字节上限。

“在线优先”仅表示开始前不等待资源；已经开始的 COUNT 不会因为后来来了新请求而自动暂停。它仍消耗 CPU/I/O，并可能和剩余在线工作槽竞争。新模式使同一后台任务完成前的翻页不必等 total，但 OFFSET 和模糊分页本身仍可能慢。

## 多场景实际对照

比较基线为上一轮分页规划修复后的实现（`dfb0414`），不是更早的慢扫描版本。19 组条件 × 总数 miss/hit × 前后 × 7 轮，共 **532 次服务入口采样 + 532 次原生 SQL 重放**。所有完整响应缓存设为 miss，总数 hit 模拟正确标量，不含 Redis/HTTP 网络/资源等待延迟。另有 HTTP 测试验证响应体确实先于后台 SQL 发送，以及完整预热缓存命中不查 SQLite。

主表为原生 ARM64、SQLite 3.46.1 的 SQL 序列重放中位数，单位 ms。容器限制 2 CPU / 256MiB，无网络，只读挂载；连接缓存 2MiB。前台、后台各用新连接，未清空 OS 文件缓存。后台列是实际 COUNT SQL 工作量，没有模拟它“免费完成”。所有逐轮页内容、排序与基线相同，非空 total 和后台 COUNT 与基线精确总数相同，原 count cache 签名一致。

默认查询已被完整预热缓存命中时，本来就不查 SQLite，表中默认查询的收益只适用于完整响应/总数均 miss。全库零结果仍需完整确认匹配范围，基线的 COUNT 扫描与新分页扫描顺序/计划不同，本轮没有收益且有退化；原生 7 轮前者 350.55～466.40ms、后者 358.20～530.13ms，存在波动重叠，不能将中位数差当作固定退化幅度。标准词精确筛选本来很快，也没有可证实收益。

服务入口对照在现有 AMD64 镜像/ARM Mac 仿真下执行，作为行为和方向控制：调皮 535.47 → 258.35ms；喉结 608.59 → 367.64ms；all 字段调皮 719.46 → 236.18ms；路首页 87.55 → 49.80ms。全库零结果 855.70 → 891.91ms。服务组后台沿用同一连接作 SQL 控制，原生组用独立连接，更接近后台独立 Session 的情况，二者不能混为端到端线上耗时。

**首屏变快不等于总工作量下降。** 原生组前台加后台中位数合计：调皮约 607.84ms（原430.65ms，+41.1%）；喉结约714.66ms（原510.05ms，+40.1%）；路首页约114.06ms（原72.80ms，+56.7%）。这些是独立阶段中位数相加，不是 CPU 时间或吞吐测量；独立连接重复规划与读取成本真实存在。因此采用单后台任务、无队列、期限和冷却，不能宣称整机负载或 OOM 已改善。

原生进程累计峰值 RSS 23.38MiB，服务入口组累计峰值 76.09MiB；不是前后内存差值，也不代表完整生产 worker 的峰值。没有线上并发测量，不承诺 <2 秒、吞吐增长或 OOM 消失。

## 测试和审查

- 查询层 TDD：首次 56 项因功能缺失失败，最终通过；覆盖多字段、简繁、地点/省/分区/标准词/通配符、各页、缓存键和 count-only 不读取页面。

- 后端 vocabulary 最终 **809 passed / 6 deselected，14.29 秒**；六项是此前在修复前源码复现的既有失败：路由 rate_limit、DOCX 解析及四项 service 断言，不在本次改动范围。
- 前端相关全套最初 **193 passed / 2 failed**；两项在独立导出的修复前 HEAD 上同样失败（导入模板文案、旧页面源码字符串断言）。最终仅排除这两项，**193 passed / 2 skipped**。新增三项实际挂载测试先 red 后 green，涵盖连续 pending 页、地图详情缓存 pending、追加失败重试原页；原有旧后端响应测试继续通过。
