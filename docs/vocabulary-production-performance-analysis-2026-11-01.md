# vocabulary 生产慢请求分析报告

分析日期：2026-11-01（Asia/Shanghai）。本次是服务器只读调查，没有部署或修改业务代码、配置、数据库结构、缓存和服务状态，也没有在生产执行接口测试、压测或业务查询基准。

后续状态更新：用户已明确确认“四次约 30 秒的标准词计算锁等待失败”已经解决。下文保留采集时的历史证据和版本对照，不代表该故障仍然存在，也不能据采集时源码判断后续部署状态。剩余问题及本地候选实验见 [后续优化实验报告](vocabulary-followup-experiments-2026-11-01.md)。

## 1. 结论

1. **用户报告的“不输入 q，选地点后首页慢”在生产确实存在。** 近一周单地点首页 34 次，中位数 2.633 秒、P95 7.606 秒、最高 8.491 秒，11 次超过或等于 5 秒。无条件首页的 9 次记录中位数只有 0.019 秒，不能把这两个分支混为一谈。
2. **近期最值得优先优化的搜索是带关键词的 entries，尤其多个地点和全域方言词搜索。** 22 地点、标准词+方言词的首页中位数 6.772 秒、最高 10.542 秒；全域仅方言词的两个样本分别为 7.674、9.319 秒。常用的两字段组合不满足现有四默认字段的专用地点优先计划条件。
3. **standard-words 的 30 秒失败已经定位到计算合并锁等待，不是 Redis 写入慢。** 近一周 4 次 503 的响应正文均为“词表查询正在准备，请稍后重试”，对应缓存层等待计算租约 30 秒的特定分支。另有一次 NGINX 502，不在完成后的 auth 耗时统计内。
4. **存在真实的整机内存不足杀进程事件。** 当前容器自 10-27 启动以来的日志快照里有 37 次 worker SIGKILL；内核近期日志明确记录至少两次 `global_oom` 杀死该容器 gunicorn。不能把所有 SIGKILL 都逐一认定为已核实 OOM，更不能认定全由 vocabulary 触发，但稳定性问题已不是假设。
5. **生产尚未部署本地最新修复。** 地点优先精确计数、在线/预热计算锁分离、取消等待启动预热，以及 map-items 不再占昂贵任务槽的改动，都还没有出现在运行容器中。本次报告按实际线上版本解释历史记录。

本报告中秒数来自 `auth.db.api_usage_logs.duration` 的实际记录；诊断表和 NGINX 用来补充参数、错误信息及关联证据。没有把本机微基准当作生产耗时，也没有把请求总耗时全部归入 SQL。

## 2. 时间范围、来源与可信度

- 近一周：**2026-10-25 00:42:39 至 2026-11-01 00:42:39**，auth 耗时记录 **705 条**。
- 近 30 天：**2026-10-02 00:42:39 至 2026-11-01 00:42:39**，auth 耗时记录 **3,483 条**。
- 同期 NGINX vocabulary 记录 **4,423 条**，诊断表记录 **120 条**，其中近一周诊断 9 条。
- 本报告所有展示时间均为北京时间。数据库时间按代码确认的 UTC 转换；auth 的 `called_at` 是请求开始，诊断 `occurred_at` 是记录完成附近的时间，NGINX 是完成时刻且精度为秒。
- P50/P95 采用排序后的线性插值。小样本也列出数值以便核查，但 n<20 的 P95 不能当作稳定的容量指标。所有统计包括该行列出的状态码，不默认剔除失败。

关联按 **IP + 端点 + 状态码 + 估计完成时间（called_at + duration）**，并用响应字节数消除同一秒内的歧义；允许 NGINX 完成时间相对估计值 -1.1 至 +2 秒的窗口。出现压缩等字节数不一致时不强行要求相等。诊断表额外核对 duration_ms，允许 2 ms 舍入误差及 1.5 秒记录时间差。

近一周：693 条可唯一关联 NGINX，9 条由诊断表确认参数，3 条虽对应多条候选但参数完全相同，**705 条均可恢复查询模式**。近 30 天：3,390 条可恢复模式，91 条参数有歧义、2 条出现重复关联候选，后两类不强行归入已知条件。报告保留独立“参数未可靠关联”项。

**耗时边界：** `duration` 由请求日志中间件开始计时，在流式响应结束时计算，涵盖中间件鉴权、准入/锁等待、查询、编码与应用流式输出；它不是纯 SQL 时间，也不涵盖请求到达应用前的全部网络和 NGINX 等待。响应字节数是应用侧记录，未必等于压缩后的网络大小。现有 NGINX 日志是普通 combined 格式，没有 request_time/upstream_response_time，不能从中补出应用前等待时间。

`api_usage_logs` **确实包含每条已记录 API 的 duration**。另需说明统计覆盖：本地 `app/common/api_config.py` 的 IGNORE_API 明确排除 `/api/vocabulary/sql/query/count`、`/api/vocabulary/me`、管理接口等。NGINX 中有 872 次 query/count、50 次 me，但本次 auth 样本没有这些端点；这不等于 duration 字段不存在。没有耗时证据的端点不编造 P95。

记录总数也已经核对闭合：近 30 天 `4,423 NGINX = 3,483 auth + 872 query/count + 50 me + 13 admin + 5 上游502`；近一周 `1,102 NGINX = 705 auth + 387 query/count + 7 me + 2 admin + 1 上游502`。因此本次不是只挑出了诊断表中少数慢请求，也没有把未落库的上游失败当作成功快请求。

诊断阈值为 10,000 ms，且记录错误，因此 **5–9 秒请求不在诊断表很正常**；本报告仍从 auth 完整纳入。SQL query 是 POST，请求体不在 NGINX URL 中；不足 10 秒的成功 SQL query 没有诊断记录，无法据现有数据恢复其具体 filters/search_columns/sort_by。

## 3. 只读调查的资源控制

采集前服务器：物理内存约 1,870 MiB，可用约 169 MiB，swap 已用约 162 MiB，系统负载 0.03/0.11/0.21。磁盘约 84% 已使用。三个业务 worker 的 RSS 约 457/383/333 MiB；RSS 可能包含共享页，不能直接当作三者私有内存总和，但结合 MemAvailable 和内核 OOM 已能确认余量紧张。

采集只启动一个低优先级 Python 进程（nice 19、ionice idle），SQLite `mode=ro`、连接内 query_only、小缓存 512 KiB、逐行 JSON 输出，并设置执行时间预算；没有导入应用模块，避免触发初始化、迁移、预热等副作用。auth.db 文件约 20 MiB，因缺少时间/端点索引，以一次流式扫描筛出目标窗口，实测 0.539 秒；诊断按已有时间索引读取，0.121 秒。没有执行全表 GROUP BY、业务数据 COUNT 或生成新索引。

NGINX 按文件偏移定位近期日期，仅扫描约 58.1 MiB 的后缀，而非整个约 368 MiB 文件；仅输出 vocabulary 行。采集 Python 峰值 RSS 为 12,580 KiB（约 12.3 MiB，含解释器），没有完整装载数据库。业务容器源码以 tar 流复制到本地，后续比较、关联、排序和统计全部在本地完成。

另外只读提取约 7.8 MiB 的容器日志快照、约 357 KiB 的 NGINX 错误日志和内核末尾 180 行。没有重启、刷新缓存、修改配置、执行 VACUUM/ANALYZE/checkpoint，也没有在生产请求 API。调查后的可用内存仍约 169 MiB，短时 vmstat 样本 CPU 约 98% 空闲；这是采集期间快照，不是历史慢请求发生时的资源曲线。

## 6. 结合线上源码分析原因

### 6.1 entries：q 空 + 单地点首页，是已确认的高频慢分支

证据：34 次，P50 2.633 秒、最高 8.491 秒；返回通常只有 1–3 KiB，不能用大量返回内容解释这些耗时。两个同条件分页实例：

| 条件 | 首页开始时间 | 首页耗时 | 第二页开始时间 | 第二页耗时 | auth ID |
|---|---|---:|---|---:|---|
| 南城水濂客家話，无 q | 10-30 10:05:51 | 5.039 | 10-30 10:05:59 | 0.326 | 132895 / 132896 |
| 陽朔忠南平聲，无 q | 10-30 16:30:32 | 7.386 | 10-30 16:30:45 | 0.173 | 133184 / 133186 |

线上 query_vocabulary_items 先执行精确 COUNT，再取当前页。COUNT 省掉不必要 JOIN，结果页也已先分页再关联地点；这些以前的优化已在线上，不能再当作尚未实施的方案。**剩余地点 WHERE 仍是条目地点名 LIKE 与地点身份子查询的 OR**，同一个地点条件会在大量词条上重复判断。

线上 cached_search 为 COUNT 提供独立于页码的缓存，因此下一页可以复用总数；这与观察到的首页/第二页差异高度一致。现有日志没有记录 count-cache hit、COUNT 单独耗时和准入等待，故不能断言首页的 7.386 秒全部是 COUNT，也不能把两页差值视为 SQL 的精确计时。上述请求开始时，已记录的 vocabulary 在线请求通常只有该请求自身；没有证据说明这类慢请求都是用户并发排队造成的，但后台任务及其他 API 不在该并发计数中。

本地最新 _location_first_count_sql 已针对这个分支优化，但运行容器不包含它。应用它是近期最直接的代码行动；仍需上线后用真实阶段耗时核验收益，不能把本地毫秒结果当作生产承诺。

### 6.2 entries：q 非空 + 多地点，是下一阶段核心 SQL 目标

22 地点且只搜索标准词+方言词，6 次首页 P50 6.772 秒、最高 10.542 秒；q=欺负那次只有 801 字节响应，说明瓶颈不在大量输出。仅标准词搜索的同类 6 次首页最高 10.267 秒（锅巴，1,315 字节响应）。

线上 `_prefer_location_identity_scan` 的特殊计划要求：单地点、没有省市/分区、没有内容与地点文本相互包含、普通非通配符关键词，**并且 search_fields 恰好等于四个 DEFAULT_SEARCH_FIELDS**。用户常用的 definition+headword、definition，以及 22 地点组合均不满足。已有优化因此没有覆盖这些常用路径。

多个地点被展开为 OR LIKE；即使地点元信息先在地点表中匹配，词条 location_name 分支仍在条目上评估，代价随候选词条与条件数增加。关键词还会展开简繁变体，在选定内容字段执行 `%词%`；现有 B-tree 不能直接定位任意子串。精确 COUNT 可能处理大量候选，而不是只看首页 50 条。先得 total 可以避免零命中再查一遍分页，但对有命中的首次请求并不能省去 COUNT。

建议在本地分别比较：两内容字段/仅标准词、单地点/22 地点、少命中/多命中/零命中；尝试先确定地点身份集合再执行内容过滤、选择覆盖索引扫描或顺序表扫描。**不能直接把四字段的 INDEXED BY 强制扩展到所有分支**，不同命中率可能反而更慢。当前新地点计数只针对无 q，且条件多时保留旧 SQL，所以它不会自动解决这一组关键词请求；22 地点的无 q 请求也会因新语句谓词预算而回退旧计数。

### 6.3 entries：全域关键词，方言词与长文本字段尤其值得关注

全域 headword 的两个首页为 q=皮 7.674 秒、q=山东 9.319 秒；definition+headword 的 21 次首页 P95 8.007 秒，蜘蛛、玉米、香皂等均有 6–9 秒实例。音标+标准词 q=二 有一个 5.836 秒实例。它们都没有地点范围可先缩小。

原因候选是任意子串扫描、为非覆盖字段访问内容页、精确总数与分页分别执行，以及冷数据页/全机资源竞争。只看请求日志不能区分各占比。普通索引对 `%关键词%` 不提供常规范围定位，但某些窄索引可降低扫描字节数，不能一概说“索引完全无用”。应按字段组合比较覆盖扫描和表顺序扫描，不改变子串、简繁或精确总数语义。

### 6.4 standard-words：把租约等待与聚合计算分开

无 q、全域 limit=1000：54 次中 50 次成功，四次约 30 秒失败。50 个成功请求多数约 0.03–0.10 秒，较慢成功样本包括 3.728、3.237、5.264、5.487 秒。不能把此模式所有请求都理解为“聚合要 30 秒”。

四次失败详情：

|---|---|---:|---:|---|
| 131029 / 15454 | 10-27 11:43:20 | 30.059 | 503 | 词表查询正在准备，请稍后重试 |
| 131030 / 15455 | 10-27 11:43:49 | 30.051 | 503 | 同上 |
| 132890 / 15600 | 10-30 09:58:49 | 30.039 | 503 | 同上 |

该正文唯一对应线上 VocabularyCache.acall 中等待 compute 租约超时的分支；资源准入超时正文是“词表任务繁忙，请稍后重试”，与本次四条不同。**已经可以确定直接失败机制是等待计算租约；没有证据说明 Redis SET 单次写入要几十秒。**

10-30 有一条更完整的证据链：

| 时刻 | 事件 |
|---|---|
| 09:57:45–09:57:47 | 一次导入成功；导入会使词条缓存版本失效并唤醒预热 |

| 09:59:59.646 | 日志显示默认 vocabulary 缓存预热完成 |

线上计算租约 TTL 为 120 秒，每 10 秒续租；进程被 SIGKILL 不执行 finally 解锁。worker 被杀到预热恢复约 119.6 秒，**高度符合持锁进程死亡后残留租约等待 TTL 过期的链路**。但历史没有记录锁 token→PID 的归属，因此“被杀的正是锁持有者”仍是强证据推断，而非逐 token 证明。

生产预热与在线请求共享同一个 compute 锁，本地最新代码已把它们分开，但尚未部署。分离可减少在线请求被后台预热租约阻塞；不能保证消除所有在线持锁进程死亡留下的租约。因此还应考虑代码层可恢复的租约所有者身份（主机/进程启动标识），仅在确认本机持有者已死亡时按 token 回收；不能任意删除活跃锁，也不应只缩短 TTL 或无限等待。

成功的标准词关键词请求依然可能慢：definition+headword 最高 8.743 秒，headword 最高 7.814 秒。SQL 按词形与地点分组后，Python 归一简繁、合并分组、统计地点集合并选前 1000；**limit=1000 不是只扫描 1000 个原始词条**。所有归一分组及其集合仍驻留 Python，词形持续增长会增加内存。已有逐行读、有限转换缓存、堆选择和限额编码都在生产代码中，不能当作新建议重复实施。下一步应在既有返回语义下减少参与聚合的候选并简化分组对象，不新增标准词结果缓存或应用磁盘聚合。

### 6.5 map-points：空查询很快，关键词聚合才是重点

无 q、全域 59 次，P50 0.038 秒、P95 0.178 秒；分区无 q 5 次最高 0.067 秒。相比之下，q 非空、仅 definition 的全域 5 次 P50 6.730 秒，蜘蛛有 6.730/7.202 秒，皮有 7.247 秒。definition+headword 7 次 P95 5.155 秒。

线上已经先按 `(user_id, location_name)` 计数，再 JOIN 地点表，结果对象与地点数相关；不能再用“尚未先聚合后 JOIN”解释当前慢请求。重点是 GROUP BY 之前的词条内容过滤：字段不覆盖索引时，按身份索引遍历可能引入内容页查找，子串仍需扫描大量候选。这里是待本地执行计划/数据验证的成本解释，日志没有单独的 SQL 用时。

建议优先比较全域 definition、definition+headword 的扫描方式，以及多地点先筛身份后聚合；保持返回全部地点、精确 entry_count、坐标遗漏统计与顺序。不要为了提高速度减少点位或改变匹配方式。

### 6.6 map-items：目前大多数快，个别受共享昂贵任务槽影响

普通指定标准词 12 次 P50 0.139 秒，最高 2.871 秒；22 地点+指定蚯蚓的一次为 5.128 秒。该请求与 standard-words 在 10-31 19:48:28 几乎同时开始，后者 5.132 秒，两者几乎同时结束，说明存在共享资源影响的可能，不能据此断言两条 SQL 都各自计算了完整 5 秒。

线上 cached_search 将 standard-words 和 map-items 都标记 expensive，共享只有一个槽；导入也占此槽。**map-items 不再占该槽的修改已在本地，未上线。** 解除这项不必要的串行限制值得优先采用，同时仍保留共用的两个 heavy 槽，避免增加无界并发。现有日志不能给出这一改动的生产加速百分比。

### 6.7 sql/query：确实慢，但不能编造 POST 筛选条件

近一周 49 次，P50 0.058 秒、P95 4.329 秒、最高 9.457 秒；15 次超过 1 秒，2 次超过 5 秒。9.457 秒那次响应仅 30 字节，不能据此推定“无匹配”：它只说明输出很小，具体 JSON/请求体没有被采集。

代码 `_query_table_sync` 先执行带过滤/排序的分页 SELECT，然后同条件 COUNT；LIKE、非索引排序、首次 COUNT、空结果仍执行两条 SQL 均是可能成本。现有 auth 与 NGINX 没有 POST body，成功请求又不足诊断阈值，因此无法可靠区分是哪一种。应先通过小型、脱敏的查询形状诊断（字段名、过滤个数、排序列、页码、阶段时间）补证据，不能把它们全部标为“无 q 全域慢”。

### 6.8 imports：稳定的几秒到十余秒，文件大小有相关性

近一周 28 次全部成功，P50 4.440 秒、P95 11.279 秒；13 次≥5 秒，3 次≥10 秒。较慢样本：2,676,673 字节请求 15.779 秒；2,921,533 字节请求 11.836 秒；1,045,370 字节请求 10.245 秒。文件大小不是唯一因素，解析格式、词条行数、覆盖删除量都没有逐条记录，不能从请求字节数推导行数。

线上已将完整同步导入工作移入有界任务，512 条批量插入，旧日志快照最多物化 501 条；这些资源优化已经存在。仍需解析/校验整个文件、删除覆盖数据、维护多个索引、写入全部新词条和提交。导入占 writer/expensive/heavy 槽，提交后使缓存版本失效并触发预热，可能间接影响随后首次查询。没有分阶段计时，无法把 15.779 秒精确拆成“解析多少、SQL 多少、排队多少”。

预览 31 次 P50 0.288 秒、最高 2.155 秒，当前不是主要慢点。进一步优化优先检查重复预览/正式导入解析成本、事务内 Python 工作和批次选择，不能减少实际导入数量，也不应盲目增加并行写入。

location-options 150 次 P95 0.085 秒、最大 1.531 秒；locations 列表 73 次最大 0.098 秒；partition-options 46 次最大 0.133 秒；导出仅两个样本，最大 0.151 秒。当前样本没有显示它们应优先于上述慢搜索优化。动态地点接口一次 2.490 秒，但 GET/PATCH 在 auth 路径上合并，不能把整个端点都称为某种查询慢。

## 7. 服务器稳定性对这些耗时的影响

完整业务容器日志快照覆盖 10-27 18:31:52 至 11-01 00:46:23，记录 37 次 worker SIGKILL，不是只看末尾两条。内核末尾明确有两次 `global_oom`，受害进程属于本业务容器，gunicorn anon-rss 分别约 431/435 MiB。一次触发分配失败的进程名是 python3.7，说明需要考虑整机其他任务；触发进程、被杀进程和根因并不等同，不能单凭名字归咎某个程序。

内核 dmesg -T 换算的墙钟时间与 Docker 事件存在偏差，不强行按相同秒关联。OOM 存在性由内核确认；37 个精确事件时刻采用 Docker 自带 UTC 时间转北京时间，见附录 B。没有证据逐一确认这 37 次全部是 OOM，亦没有 SQL 分阶段证据证明每次 OOM 都由标准词聚合触发。

进程死亡会影响正在执行的请求、默认缓存预热以及 Redis 租约恢复；因此同一 SQL 在空闲/热缓存时很快，并不能排除生产偶发秒级延迟或 502。10-28 01:07:05 的 standard-words：NGINX 报上游提前关闭、返回 502；同秒容器日志记录 worker 91 SIGKILL。这条失败没有完整 auth duration，不能遗漏，也不能给它补一个假的耗时。

三个 worker、数据库页缓存、Python 聚合、其他 API 和宿主任务都共享 2 GB。现有 vocabulary 两个 heavy 槽与一个昂贵槽约束的是部分业务，不能保证全站不 OOM。此处只提出代码层内存与准入治理方向，本次没有更改 worker 数、swap、NGINX、Redis 或任何服务器配置。
