# 地点范围查询优化：本地探索与量化结果

日期：2026-11-01。基线为 `6cb37e4`；业务查询源码没有改动，SHA256 为 `0d039679778bce0c630c71663314ccdaf19f8ad9c9f7f4b63b445ce7a6d47712`。

## 结论与交付范围

**“先定位小范围地点，再按索引查词条”有明显收益，但不能推广成所有地点搜索的默认路径。** 本轮交付的是独立离线 SQL 原型、完整结果验证工具和量化报告，没有把候选写入业务端点，没有增加索引、缓存、线程、worker、常驻服务或改动前端。没有连接、修改或测试服务器。

最值得继续落地的是：entries 首次精确计数未缓存、地点范围小的模糊搜索，以及 standard-words / map-points 的同类地点筛选。范围大时保持原查询；entries 计数已缓存时，建议暂不启用新的探测和地点遍历。单纯改写为子查询或 UNION 不足以提速。

## 1. 实验设计与资源边界

- 原生 ARM Linux，Python 3.12 / SQLite 3.46.1；Docker 限制 **2 CPU、2 GiB、无 swap**，并禁用网络。不是上一轮 amd64 架构模拟。
- 当前本地数据 95,003 条；增长数据 475,015 条，原有词形和地点名保持不变，复制时用户身份分离；另用 95,003 条合成高命中集，给词形增加“共同”前缀。增长集不是生产未来数据的预测。
- 一次预热、7 轮交替执行取中位数，串行运行。entries 保留现有的首页不足一页推导总数流程；满页才回退精确计数。探测和 SQL 返回行的读取均计入时间。
- **表中是 SQL 执行时间，不是接口耗时。** 不含 Python 标准词归一化/排序、响应对象构建、JSON、Redis、鉴权、网络和排队。没有真正清空宿主磁盘缓存；独立进程首次计时也不是冷盘测试。
- 对每种计划，在计时外读取全部匹配记录并核对总数、完整有序结果摘要；标准词和地图 SQL 不加返回数量上限。entries 的 50 条是现有分页大小，额外验证时去掉分页读取全部结果，没有修改端点的分页约定。
- JSON/CSV 中聚合端点的 `total/returned` 是 **SQL 分组行数**；standard-words 后续还会简繁归一，不能把这个数当成端点归一词组总数。另执行了实际服务函数的完整对象等价检查。

## 2. 候选计划具体做什么

1. 用现有地点名索引逐次 MIN 跳跃，枚举最多 257 个不同词条地点名；只处理不超过 256 个名称的路径，超出则使用原查询，**不截断实际结果**。
2. 处理两条互斥分支：词条地点名匹配；地点元信息匹配且地点名未命中前一分支。后者保留 `(user_id, location_name)`，避免同名地点串数据；前者保留缺失地点表记录的词条。
3. 使用 `CROSS JOIN` 控制遍历顺序，分别通过现有 `location_name`、`(user_id, location_name)` 索引读取对应词条，再执行原内容匹配。两支 UNION ALL，因为已经互斥，不做全结果去重。
4. 用仅访问索引的有界范围探测选择计划：预算为 `min(32768, max(1024, 总词条数/10))`，最多访问预算+1 条候选来判定是否超出。范围更大则保留原 SQL。总词条数通过独立 `SELECT COUNT(*)` 获取，避免将其嵌入聚合表达式导致失去 SQLite 的快速计数指令。

上述 10%、1024、32768 是实验阈值，没有证明对所有数据分布最优；它们仅约束探测，主查询始终保留全部数据。范围判断不是看用户选了几个地点。元信息匹配 identities 在此原型仍由 SQLite 管理，未来地点表增长也要另加可回退的规划预算，不能称整个规划为常数成本。

业务实现时应在一次请求中复用已经解析的范围，避免在探测、计数、取页时重复解析。原型计入了这些重复解析成本；优化复用后的额外收益尚未测量，未计入下面的数字。

### 计数缓存命中：不能沿用同一结论

预先提供精确总数，测量只取页的 SQL 成本；不包含真实 Redis。这个实验暴露了必须保留的回退条件：

| small2-definition+headword-人 | 27.044 | 4.813 | 5.62× | 地点索引读取 |
| small8-definition+headword-人 | 1.512 | 11.606 | 0.13× | 地点索引读取 |
| large1-definition+headword-人 | 1.729 | 4.426 | 0.39× | 保留原计划 |
| wide22-definition+headword-人 | 0.428 | 3.778 | 0.11× | 保留原计划 |

缓存命中后，原路径有时只需按 id 顺序很快找到 50 条；地点遍历却要读取、排序更多候选。“8 个小地点＋人”甚至从约 1.5 ms 退化到约 11.6 ms。因此建议第一版把规划放入已有计数缓存的 miss 回调，缓存命中继续沿用原取页查询，不能把候选无条件插到请求入口。**这是建议的正式实现边界，本轮量化的候选本身尚未添加此生产路由。**

## 7. 内存和 I/O：没有虚报内存下降

内存每项使用独立 stdlib SQL 子进程，在计时之外验证结果。使用 Linux `/proc/self/status` 的 VmHWM，单位 MiB。`ru_maxrss` 在本机子进程中受到 exec 前历史峰值影响，因此保留原始字段但不拿它作为本表的查询进程峰值。

| 增长集 / 两字段 | 原进程 VmHWM MiB | 候选 VmHWM MiB |
|---|---:|---:|
| entries / small2-definition+headword-蜘蛛 | 22.28 | 22.80 |
| entries / small2-definition+headword-人 | 22.42 | 22.75 |
| standard-words / small2-definition+headword-蜘蛛 | 22.21 | 22.55 |
| map-points / small2-definition+headword-蜘蛛 | 22.25 | 22.55 |
| entries / wide22-definition+headword-蜘蛛 | 23.33 | 23.59 |

这不是完整后端 worker 内存，也不包含标准词完整 Python 聚合；不能据此承诺线上请求只需约 23 MiB。典型案例增加约 0.3–0.5 MiB，主要收益是 CPU/读取量减少。增长集整批 cgroup 峰值约 212.0 MiB，包含父进程、SQL 冻结信息、功能校验等，OOM=0，不能当单请求内存。

各独立查询进程观测到的最大 `write_bytes` 差值为 2,768,896 字节。非零写入出现在高命中标准词的大地点和宽范围案例，原查询与候选分别同为 1,478,656 / 2,768,896 字节；这些测量未观察到候选新增的 write_bytes。这是进程总 I/O，不能精确归属某个 SQLite 临时文件；GROUP BY / ORDER BY 仍可能使用 SQLite TEMP B-TREE，没有应用层磁盘聚合，没有修改 temp_store。也没有通过减少结果或增加并发换取提速。

## 8. 未采用的方案和安全边界

- 仅把地点条件换成 IN 子查询：SQLite 常仍选全表扫描，很多场景基本不变。
- 不控制驱动表的互斥 UNION：可能扫描两遍。第一轮增长集两小地点、仅标准词、“蜘蛛”约 66.8→124.2 ms，不应采用。
- 对所有范围强制地点索引读取：第二轮增长集 22 地点、仅标准词、“蜘蛛”约 34.5→194.8 ms，不应采用。不同轮次温度/负载不同，这两组只在各自轮次内比较，没有把第一轮前值与最终后值拼接成收益。
- 规划先读完全部词条 id 再构造 Python IN 列表：未采用，避免内存随候选记录数膨胀。
- 探测预算、名称枚举上限仅用于选择回退路径，不是结果上限。大范围请求仍完整执行原逻辑；没有引入新的超时、503 或自动重试。
- 任意子串匹配仍需要检查候选内容，没有普通 B-tree 支持任意子串的新结论。无 q、无地点、深分页、特殊通配符及未测字段组合不应盲目复用本轮路径。

## 9. 验证与下一步实施建议

业务查询源码保持基线哈希不变。本轮执行了：

- 153 组当前数据和 153 组增长数据的分支对照（各含 entries / standard-words / map-points），加 12 组高命中和 27 组 entries 计数命中；共 345 组最终前后比较。
- 所有 SQL 前后完整有序结果和总数一致；entries 另读完整结果，聚合不截断。
- 930 项合成语义检查，包括同名不同用户、缺失地点、名字与元信息重叠、NULL、满页，以及 356 个不同地点名触发完整回退。
- 当前数据和高命中数据各 153 项、共 306 项实际服务函数返回对象等价检查；standard-words 使用 `limit=None`，覆盖无限量返回。

建议正式实现分两步：先给 entries 的计数 miss 回调增加受预算保护的小范围路径，命中缓存时保留原取页；再让 standard-words / map-points 复用同一范围解析构件，分别执行自己的聚合。缓存键继续使用原计数 SQL 和参数的语义签名，候选 SQL 只在 miss 计算内部选择，避免因计划分叉打散已有计数复用。读取范围、页和精确总数时保留一致性快照；全部现有回退路径保留，不新增全局可变状态或标准词结果缓存。

并发仍沿用现有 heavy=2、expensive=1；范围缓冲必须有上限并可回退。正式代码合并前，仍需补计数缓存路由和并发写入的集成回归、端到端服务时间测量，以及独立 CR。本轮独立 CR 已复核实验工具和报告，未发现 P1/P2；这不替代后续业务实现的 CR。本轮没有借探索之名部署未经这些验证的原型。
