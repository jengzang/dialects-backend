# 后端性能、可靠性与边界条件审查

审查日期：2026-10-24。代码基线：`11f807f`。生产约束：2 核 CPU、2 GB 内存。

本次是代码审查、数据库只读检查和隔离复现，没有修改业务代码、索引、生产配置或业务数据。没有连接生产服务器，没有运行生产压测，也没有启动应用的迁移、维护或预热流程。仓库包含 341 个 Python 源文件；本次重点追踪入口、公共依赖、SQLite 连接池、日志、工具任务、地名与 VillagesML 计算链路，不意味着逐行覆盖所有文件。

证据分为：**已复现**、**代码确认**、**历史线索**、**待实测**。以下建议中的并发数和容量值是待验证的起始配置，不是已测得的安全容量或性能承诺。

## 1. 异步路由里仍有完整的阻塞工作

位置：

- `app/tools/check/check_routes.py:338`、`:394`、`:724`、`:923`：分析、上传、编辑、分页读取里直接读写 Excel。
- `app/tools/jyut2ipa/jyut2ipa_routes.py:126`：后台协程直接 `pd.read_excel`，逐行构造结果，再生成工作簿。每 500 行 `await asyncio.sleep(0)` 只在批次之间让出执行权，不能消除读取、转换和保存的阻塞。
- `app/tools/merge/merge_routes.py:97`：`async def merge_files_async` 内直接加载、合并、创建和保存工作簿。
- `app/sql/sql_admin_routes.py:64` 附近和 `app/routes/vocabulary_sql.py:602` 起：异步写接口直接执行 SQLite 操作与 commit。数据库忙时等待也发生在事件循环线程上。
- `app/service/auth/core/dependencies.py:421`、`:463`、`:487`：实际生效的鉴权函数直接同步查会话和用户；中间件和依赖层还可能重复鉴权。

影响：一个大文件或数据库锁等待可以拖慢同一个 worker 的健康检查、轮询及其他轻请求。`BackgroundTasks` 不提供独立执行进程；其中的异步函数仍运行在请求 worker 的事件循环。

建议：将一个完整同步单元放到受限执行入口，包括打开、使用、关闭其数据库 Session；不要跨多个线程碎片化使用同一个 Session。重文件任务的全实例运行上限先以 **1 个**作为验证起点；不建议每个 worker 各放行 1 个后称之为“全局串行”。队列应有数量和等待期限上限；超额返回 429/503。进一步优化为流式读取/写入、按页定位，避免每次分页或编辑重读整本工作簿。

失败策略：输入错误不重试；临时存储错误有限重试；重试需有任务幂等键，不能重复执行非幂等修改。

## 2. 超时和取消都没有形成实际资源边界

`app/villagesML/compute/timeout.py:25` 使用 `wait_for(to_thread(...))`。隔离测试中，一个约 120 ms 的同步工作设置 10 ms 超时，约 11 ms 返回超时，但等待后确认工作仍自行完成。该实验验证的是线程取消语义，不是业务接口耗时。

目前没有统一的重任务准入控制。Starlette/AnyIO 线程池与 `asyncio.to_thread` 的执行入口也不同，不能假设二者共用一个限额。即使线程数有限，仍可能积压等待任务。NumPy/sklearn 的原生计算线程也需要纳入预算。

Praat 的 `cancel_job`（`app/tools/praat/routes.py:558`）把状态写成 canceled 并清空 current_job_id；`_execute_job_sync`（`app/tools/praat/core/job_executor.py`）没有据此停止模块执行，结束时还会写 done、覆盖统一的 `result.json`。取消后立即提交新任务时，新旧计算可以重叠、结果可以互相覆盖。

建议：

- 使用现有 Redis 或数据库实现跨 worker 的全实例准入，先验证 1 个重任务运行、少量有界排队的配置。相同请求合并计算。
- 计算仍在运行时保持资源名额；客户端断开或 HTTP 返回 408 不能提前释放名额。
- SQLite 使用进度回调或适当的 interrupt 机制实现查询期限；应用循环在批次、模块之间检查取消与 deadline。原生算法无法中断时，必须如实暴露状态并持续占用名额，不能宣称“已停止”。
- Praat 的结果按 job_id 存放，终态通过比较并更新写入；完成、取消、失败不能相互覆盖。worker 退出后的任务要有恢复/失败标记，不能一直 queued/running。
- CPU 原生库线程数先限制为 1 做基线测量，再决定是否调整；不要默认增加进程或线程。

## 3. 有页大小限制，不代表有工作量上限

### 地名接口

`app/routes/toponyms.py` 的 points/search/names 接受 `limit=0`；`app/service/toponyms/config.py` 的最大值是 2,000,000。repository 在 limit=0 时去掉 SQL LIMIT，并用 `fetchall()` 把结果一次取回。随后还有 Python 字典、响应模型、JSON 和 gzip 的成本。

本地 `toponyms.db` 大约 4,980 MiB；`sqlite_stat1` 中 single/multi 行数估计分别为 9,359,099 和 2,106,635。这是优化器统计估计，未为审查执行全表精确计数。

`MAX_BBOX_AREA=25.0` 只定义而未在当前路由中使用；bbox 是可选的；zoom 只校验后丢弃。contains/suffix 不能依赖普通名称 B-tree 做前缀范围定位。`%`、`_` 直接进入 LIKE 模式，是否应按字面字符搜索也没有明确处理；prefix 上界算法另有 Unicode 最大码点边界。

建议：公共同步接口移除无上限模式，给返回条数和结果字节设硬限制。大地图查询按 bbox/缩放级别限制、聚合或分片；全量导出单独走有界任务。contains/suffix 要有限制条件和查询 deadline。先定义结果完整性和截断标志，再决定限制值。

### 字音比较

`app/service/core/compare.py:94` 先创建“候选字 × 地点”列表，再以 OR 条件分批查；`:125` 按全部输入字对组合比较。`app/routes/core/compare.py` 没有类似 search_chars 的 20 字上限，也没有展开后的地点数/字对数预算。

工作量至少与地点数乘字对数相关，约为 `L × C × (C-1) / 2`，简繁候选还会进一步展开。把参数切成 450 对一批没有限制总量。

建议：去重、展开后检查字数、地点数、字对数、候选数量及响应预算。比较查询参考已有 `search_chars` 的双 IN 分批策略，避免先建立完整笛卡尔积。空输入、重复输入、多字字符串和无效地点都应在昂贵查询之前校验。

## 4. 文件任务的跨进程一致性已经复现问题

`app/tools/task_manager.py:178` 用 `threading.Lock` 包住读改写。这个锁只覆盖同一进程。`_save_json` 的原子 rename 防止半文件读取，却无法防止两个进程分别读到旧值再覆盖对方。

隔离测试用两个进程同步读取相同任务，分别提交 `data.a=true` 和 `data.b=true`；两个进程都正常退出，最终 JSON 只剩一个字段。生产配置是 3 worker，因此这不是只有单线程调试才会遇到的假设。

Praat 接单还有独立竞态：create_job 只拒绝 running，不拒绝 queued；检查、job_counter 生成、追加记录和设置 current_job_id 分开进行。快速双击即使没有多进程，也可能在旧任务仍 queued 时再次接单。

其他边界：

- `_save_json` 捕获异常后只打印，调用者可能更新内存缓存并返回成功，但文件并未成功保存。
- 同进程不同写入路径共用以 PID 命名的临时文件；必须确保所有写入口均遵守一致的互斥契约。
- worker 被回收、磁盘满、清理与下载/完成同时发生，都需要明确状态与文件一致性。
- 任务访问目前主要依靠 task_id/job_id；需要明确“持有 ID 即可访问”的能力链接语义，还是要求用户所有权校验。这是权限设计待确认项，未据此认定已发生越权。

建议把接单和状态更新放进一个小型事务或跨进程锁内。高频任务元数据优先复用 SQLite/Redis 的原子能力；保留文件存储时，跨进程锁必须覆盖整个读取、校验、更新过程，不能只锁写文件。

## 5. 诊断日志存在失败时突破批次上限的问题

`app/service/logging/stats/diagnostic_pipeline.py:27` 的 batch_size 是 25。但写库失败后保留 batch，下一轮继续取新事件、append、再次尝试写整个 batch。

隔离测试模拟持续存储失败，输入 60 个事件，观察到写入批次从 25 增长到 60。外部队列有 maxsize 并不限制已经转移到本地 list 的数据，故不能据队列大小证明内存有界。

同类 writer 应一并检查，例如 keyword writer。auth_usage_pipeline 已有“保留失败批次并暂停消费”的更稳健实现，可复用思路，但恢复落盘也需要磁盘配额。

建议：达到固定批次后停止继续消费，按 deadline flush；对 SQLite BUSY/LOCKED 做少量带抖动退避的重试。对磁盘满等错误采用有配额的恢复记录或明确的丢弃/采样策略，并监测丢弃计数。诊断信息不应无限争夺登录、业务写入的资源。

## 6. Redis 故障策略不一致，会放大故障

`app/service/auth/core/dependencies.py:396` 的缓存读取没有捕获 RedisError；实际生效的 get_current_user 直接调用它。中间件有异常捕获，但路由依赖仍可能失败，不能据中间件的降级逻辑认为普通鉴权也会回源。

`app/routes/core/matrix.py` 的矩阵缓存读取/写入异常直接成为 500。`check_api_usage_limit` 则在 Redis 异常时降级为不限流。其他部分缓存会直接回源。

结果可能是同一次 Redis 故障同时引发部分请求 500、部分请求重复超时等待、部分昂贵请求失去限流并集中查库。

建议分开制定：

- 鉴权/会话撤销必须保持正确性，不能为了可用性接受失效会话；回源必须有容量和快速失败边界。
- 普通结果缓存可以短时间熔断后有界回源，避免每个请求反复等待数秒 socket timeout。
- 重任务准入在共享协调不可用时应返回明确的 503 或进入保守模式，不能直接无限放行。
- 目前限流的 zadd/remove/expire/card 是多次独立往返；用 Lua 原子检查并写入，并明确拒绝请求是否计数。小时额度不能替代短时间并发保护。

登录限流还依赖异步写入的 ApiUsageLog，存在写入滞后窗口；`_get_login_retry_after_seconds` 的查询没有使用与计数相同的一分钟过滤条件，历史记录可能使 Retry-After 偏差。这两项应补带并发和旧日志数据的验证。

## 7. 内存预算必须按整台实例统计

`gunicorn_config.py:83` 配置 3 worker，未开启 preload。每个 worker 的 startup 预建 5+8+4+3+3=23 个 SQLite 连接。`app/sql/db_pool.py:35` 为每连接设置 `cache_size=-16000` 和 `temp_store=MEMORY`。

仅这些连接的页缓存建议预算按 23 × 16,000 KiB × 3 计算，约为 1.05 GiB。**这是配置预算叠加，不是启动就分配的实测内存，也不是 SQLite 内存硬上限。** 还未包含临时排序、ORM 连接池、Python 对象、NumPy/Pandas、日志 master、Redis 和操作系统。

logs ORM 又设置每连接约 64,000 KiB 页缓存；toponyms 和其他按需数据库还有额外连接。原始数据库已经有数 GiB，不能预期整库驻留内存。

建议：先测 master/worker 的 PSS/RSS、Redis used_memory、SQLite 连接数、临时排序与并发任务峰值，再比较 1/2/3 worker；减少预建连接，给低频库惰性建连，优先避免页缓存和结果对象多份复制。不能直接把 worker 从 3 改成 1 就承诺更快。

## 8. SQLite 连接池的正确性与等待边界

`app/sql/db_pool.py:41` 归还连接前只执行 SELECT 1，没有 rollback。隔离复现：在连接内 insert 后抛异常；下一次借用时 `in_transaction=True`，仍可读到上一请求未提交的行；后续 commit 会把它提交。当前部分写路由有显式 rollback，因此本次没有据此断言已有业务数据污染，但池本身不能隔离遗漏 rollback 的调用者。

其他问题：

- `finally` 中在 conn is None 时 return，会掩盖原异常。已复现关闭池时得到 `RuntimeError: generator didn't yield`。
- closing 分支在 yield 后 return 也会吞掉上下文中的异常，应避免用 finally return 控制错误流。
- 先等满 30 秒才考虑扩容，扩容上限却达到 pool_size 的两倍；对交互请求不利。
- `_created_count` 在丢弃/替换连接时没有与存活数保持一致，不适合作为可靠容量判断。
- close_all 可关闭仍被借用的连接，需要清楚的停止接单、等待归还或强制结束协议。

建议：读写契约清晰化，归还前 rollback 未完成事务；固定小容量、短等待、明确 503；连接容量由存活和借用计数共同管理；测试异常路径、耗尽、坏连接和并发 shutdown。

## 9. 数据库性能证据与可优化路径

### 地名前缀查询的计划

实际只读查询：自然村类型 22200、名称前缀“大”、按 id 排序、取 5001 行。自动计划选择 `idx_single_type_id`，仅以 place_type_code 定位，名称条件随后过滤；使用现有 `idx_single_type_name_id` 可按名称范围定位，但需临时排序。

交替顺序执行 6 次，两种查询结果一致：

| 查询 | 本机中位耗时 | 各次耗时 ms |
| --- | ---: | --- |
| 自动计划 | 172.71 ms | 3083.20, 153.18, 196.92, 179.27, 158.37, 166.15 |
| 指定现有名称索引 | 69.95 ms | 137.95, 40.20, 176.90, 97.95, 40.86, 41.95 |

本机、缓存和系统负载不等同于生产，且首次耗时差异很大；不能据此承诺线上倍数收益。稀有前缀的自动计划又能选择名称范围索引，因此也不应把所有请求永久强制到一个索引。

先以真实词频、bbox、limit、排序组合验证计划，评估是否可按名称+id 排序后使用游标分页，以及需要返回坐标时的回表成本。已有索引很多，不能把“继续加索引”当默认答案。

### 统计与 SQL 树

- metadata/stats/tables 已经批量查询 dbstat，并有 300 秒 Redis 缓存；这部分已有优化。冷缓存仍会执行 `dbstat GROUP BY name`，并对缺少 sqlite_stat1 的表 COUNT，成本随库规模变化。
- N-gram statistics 每次缓存未命中会聚合统计表；api_cache 没有合并同时发生的 miss。部分缓存参数含 sqlite Connection 对象，导致缓存键包含运行时对象身份，跨连接/worker 无法充分复用。
- SQL full tree 在判定应降级 lazy 之前先精确 COUNT。之后 DISTINCT/GROUP/ORDER 的输入扫描量也不受输出 LIMIT 完全限制。

建议：元统计在数据版本变更时生成快照，接口返回生成时间；需要准确更新时由单个任务合并刷新。仅需判断超过阈值时，可评估有界子查询计数；需要精确 total 的契约应单独保留。缓存键只包含稳定业务参数、数据版本和必要权限范围，不包含连接、Request 等对象。

## 10. 聚类默认参数、小样本与数值边界

隔离执行实际模型类、实际方法片段，已复现：

1. `ClusteringParams(algorithm='kmeans', region_level='city')` 被接受，k=None。旧式字段 validator 不会自动对省略默认字段执行这里期望的交叉验证。
2. DBSCAN 可省略 dbscan_config，模型输出 None；engine 中 `params.get('dbscan_config', {})` 得到 None，再 `.get('eps')` 触发 AttributeError。
3. `run_clustering` 的 PCA 维度只与特征数取 min，不与样本数取 min。3 样本、20 特征会尝试 20 个主成分，触发 ValueError。城市筛选或很小的 region_filter 就可能遇到。

建议采用模型级交叉验证；数据库筛选后再验证样本数量、k、PCA 维数、空特征、NaN/Inf、常量列、重复样本。轮廓系数还要满足标签数量小于样本数，DBSCAN 噪声是否计入指标应明确定义。

性能边界：engine 多处全量计算 silhouette_score；DBSCAN 在某些参数/数据分布下邻域存储可能接近平方增长。subset.filter_villages 是先读全筛选结果到 DataFrame 再 sample，所以 sample_size 不能证明内存有界。应先对输入样本设硬上限并在 SQL/读取阶段采样；大样本指标采用固定样本评估，不能先算全量再丢弃。

## 11. 缓存容量、版本与回收

- `app/tools/task_manager.py` 的 `_CACHE_TTL=0.5` 只决定何时重读，不会自动删除 `_task_cache` 键。周期清理调用 FileManager，不会清掉各 worker 已持有的任务副本。一个 worker 访问的不同任务越多，缓存可能持续增长。
- ComputeCache 每 worker 最多 100 条，但单条结果无字节限制，读写还会 deepcopy。过期项只在读取同一 key 时删除，冷的过期结果不会按时间主动释放。
- VillagesML 计算缓存只以 endpoint+params 标识，未包括数据库路径和数据版本。当前 schema_config 仅配置一个 village 数据源，因此“不同数据源串缓存”属于扩展风险；在线更新或替换数据文件后的旧结果有效期问题仍需明确。
- 普通核心缓存缺少统一的失效与并发 miss 合并；词表缓存已有修订号、按 key 租约、串行预热、部分容量限制和取消后等待线程结束的实现，应保留并复用其原则。

建议：任务缓存设条数及过期淘汰；计算结果同时限制条数、估算字节、单项大小。明确数据更新、权限变更、取消、租约过期、Redis 恢复后各自如何失效；永久默认缓存也要评估数据增长边界。

## 12. 日志、维护与进程生命周期

代码确认与待验证项：

- diagnostic 事件没有出现在当前 scheduler 的保留清理逻辑中。公网 401/404 探测也会产生记录，日志表需要按类别保留期限和采样策略。
- 本地诊断表存在两个完全相同的 duration_ms 单列索引：`ix_api_diagnostic_events_duration_ms` 与 `idx_api_diag_duration`，模型定义也同时包含 column index=True 与显式 Index。它们增加写放大和空间，应通过迁移去重。
- 日志恢复文件可持续落盘，但没有独立容量/数量预算；磁盘满时仍会影响业务数据库。
- keyword 聚合每小时删除再全量重建；多项清理是单个 DELETE 大事务，备份直接执行 src.backup。数据增长后需要增量聚合、分批删除、可让出 I/O 的备份，以及失败退避和监控。新方案不应增加常驻服务。
- Gunicorn on_starting 在 fork 前启动 logger/scheduler/backup 线程；相关导入也会创建 ORM engine/连接。fork 后继承线程锁和已建立连接的状态需要专项验证，不能因为后台服务只启动一次就认为进程间资源安全。子进程应重置/丢弃继承的连接池，并审查 max_requests 回收和滚动重启。
- AUTO_MIGRATE 在 Docker 中开启，启动步骤按 worker 执行；部分 import 也会修改 schema。需要把迁移的单实例性、失败后 readiness、滚动部署期间新旧 worker 共存纳入设计。VACUUM 在新 master 的 worker fork 前执行，不代表旧 master 的 worker 已全部停止。
- GZipMiddleware 未指定 compresslevel，所安装 Starlette 默认为 9。大 JSON 的同步序列化、解码缓存和压缩仍会消耗 worker CPU；压缩等级与代理是否重复压缩需要测量后调整。
- `check_routes.py` 重复注册 analyze_async 和 progress 路由；鉴权文件有多组同名函数，后定义覆盖先定义。这会增加审查误判和后续修改失效的概率，应清理重复定义并核对路由表。

## 建议实施顺序与验收

第一批先处理安全容量和确定性错误：跨进程原子任务接单、queued/running 互斥、取消终态保护、诊断失败批次上限、全量查询入口、聚类验证错误。随后把工具同步工作移出事件循环，并在同一次改动中建立全实例有界准入，避免只是把阻塞转成更多并发。

第二批在实际部署环境测量并调整：worker/数据库连接/页缓存预算、地名排序与索引计划、统计快照、缓存字节预算与失效策略、日志写放大。

验证至少覆盖以下场景：

| 场景 | 需要观察的结果 |
| --- | --- |
| 单个重任务运行，持续发轻请求 | 轻接口 P50/P95/P99、事件循环延迟、连接池等待 |
| 多请求同时提交相同与不同重任务 | 运行/排队数始终受限，重复计算合并，超额快速失败 |
| 超时、客户端断连、取消后立刻重提 | 不提前释放资源名额，终态不倒退，旧结果不覆盖新结果 |
| Redis 不可用/恢复 | 鉴权正确，重请求不会无限回源，缓存恢复不复活过期数据 |
| SQLite 长写事务、BUSY、磁盘满 | 重试次数有界，无跨请求残留事务，日志内存不持续增长 |
| worker 回收/滚动重启 | 任务不会永久悬挂，继承连接/锁无异常，迁移维护不相互争抢 |
| 大文件、超大解压体积、超长/重复参数 | 在昂贵工作前拒绝，文件/行/列/字节/展开数量均有预算 |
| 缓存失效、冷启动、多 worker 同时 miss | 只运行允许数量的刷新任务，内存和临时文件可回收 |

生产采样应记录整台实例的 CPU、PSS/RSS、Redis 内存、I/O、WAL 大小、锁等待、线程池/连接池等待、任务队列深度、拒绝与丢弃数。使用分阶段的 1/2/4 并发开始，遇到在线延迟或内存水位恶化立即停止；重计算在 2 核 2 GB 环境中不宜直接用大量并发试探。

验收目标应包含“失败后资源仍有界”和“轻接口不被重任务拖垮”，不能只看单次请求变快。具体延迟、内存和吞吐目标需在目标机器上取得基线后确定。
