# 词表多条件搜索：下一阶段提速实验

## 范围与结论

本次是分析与候选实验，**没有继续修改业务查询实现**。基线是当前工作区：已经包含 entries 的计数优先、空页短路及分页后关联地点，而不是这些改动之前的版本。没有把之前的提速重复算作新收益。

优先级建议：

1. standard-words 根据搜索字段和地点限制选择查询路径，避免非覆盖索引导致的逐条回表。
2. 地点文本模糊搜索先求匹配地点身份，减少在每条词条上重复匹配地点元信息；保留孤立词条及通配符语义。不能把所有省市条件也统一替换。
3. 已确定超出 Redis 缓存上限的结果提前停止缓存编码，减少无效工作。
4. 有限扩大/改进简繁归一缓存，对重复大范围聚合有益，但不是长期解决不同词形增长的方案。
5. NOT NULL 字段去掉 COALESCE 的收益通常只有几个百分点，优先级低。

这些优化都不需要改前端、不新增索引或常驻服务。生产并发沿用既有上限；本次只在独立实验模块和测试库中运行，没有新建生产数据缓存、临时聚合或结果文件。

## 实验环境与多条件覆盖

macOS 26.3.1 arm64，Python 3.12.13，SQLite 3.53.2。串行运行，SQLite 页缓存预热，每个候选/场景/端点交替比较 5 轮中位数。计时为服务函数（含 SQL、Python 聚合和结果 dataclass 构建），不含 Redis、HTTP 校验/编码、网络或前端。结果比较/摘要在计时外完成。不保证生产 2 核 2 GB 上同样的毫秒数或比例。

- 当前库只读：95,003 条词条、29 个地点身份、41,558 个原始词形。
- 增长库：950,030 条、290 个地点身份；保持原索引，用独立用户身份复制。**词形和地点名称不随复制改变**，不能据此模拟 10 倍不同词形/不同地点名称的成本。测试库仅为实验夹具，完成后删除。
- 基础参数矩阵 23 类：默认、常见词、单字、简繁、无命中、标准词单字段、音标、备注、地点、词条与地点混合 OR、省份大小范围、省市组合、多地点文本、关键词叠加省份、地区大小范围/多地区/关键词叠加、关键词+省市+地区+地点组合、`%`、`_` 和互相矛盾的省市条件。
- 不适用的候选不机械遍历所有参数，按其可能影响的条件选择场景；共 161 个端点/条件/候选组合，均与当前完整返回值逐项相等（包含顺序、计数和全部字段），不是只比较 ID。
- 另建包含跨用户同名地点、孤立词条、空地点、NULL 元信息的内存夹具，增加 33 个完整结果比较，验证 `%`/`%%`/`_` 和混合字段。`%` 可匹配 LEFT JOIN 的 NULL 空值，不能直接用地点子查询替代，原型显式保留原路径。
- standard-words 的默认 100 项沿用现有语义；另测试 `limit=None` 的完整 39,965 个归一词组并比较全部内容。没有通过新加截断获取性能改善。entries 沿用既有分页。

复现脚本：`scripts/benchmark_vocabulary_search_candidates.py`。每种实验可以指定 `--scale 10`、`--rounds 5`，输出 JSON 含每轮样本、查询计划、结果摘要和实际参数。例如：

```bash
_RUN_TYPE=MINE .venv/bin/python scripts/benchmark_vocabulary_search_candidates.py \
  --experiment standard-table-scan --scale 10 --output /tmp/search-table-growth.json
_RUN_TYPE=MINE .venv/bin/python scripts/benchmark_vocabulary_search_candidates.py \
  --experiment metadata --scale 10 --output /tmp/search-metadata-growth.json
```

## 1. standard-words：避免低效回表

当前默认多字段搜索走 `idx_vocabulary_entries_standard_word_location` 有序扫描，但 local_expression/ipa/notes/informations 不在该索引中，需要回表。低命中时，为少量最终分组付出全表随机读取成本。

候选原型让该查询顺序扫描词条，再对匹配记录 GROUP BY。EXPLAIN 从 `SCAN e USING INDEX ...standard_word_location` 变为 `SCAN e` + `USE TEMP B-TREE FOR GROUP BY`。仍需要读取全部候选，不是让任意子串查询获得索引定位。

| 搜索场景 | 9.5 万：当前 → 候选 ms | 减少 | 95 万：当前 → 候选 ms | 减少 |
|---|---:|---:|---:|---:|
| 默认字段，“什么” | 79.416 → 37.017 | 53.4% | 890.338 → 368.958 | 58.6% |
| 默认字段，单字“人” | 69.992 → 34.840 | 50.2% | 756.240 → 239.225 | 68.4% |
| 默认字段，“太陽” | 76.465 → 36.430 | 52.4% | 889.520 → 367.849 | 58.6% |
| 默认字段，无命中 | 58.170 → 19.658 | 66.2% | 757.040 → 202.222 | 73.3% |
| 音标字段，“a” | 117.374 → 74.812 | 36.3% | 721.307 → 231.949 | 67.8% |
| 备注字段，“常用” | 48.437 → 10.907 | 77.5% | 683.619 → 111.187 | 83.7% |

不能全局强制顺序扫描。95 万条反例：

- 只搜标准词“什么”：47.410 → 71.267 ms，慢 50.3%。现有覆盖索引能直接完成扫描，不需要回表。
- 关键词+省份：298.721 → 369.670 ms，慢 23.8%。
- 关键词+地区：284.002 → 368.677 ms，慢 29.8%。

建议先仅在**没有地点范围限制、搜索包含索引外词条字段**的路径验证/启用；只搜标准词或已有地区范围时保留原有路径。不能对每次请求新增一次昂贵 COUNT 来猜选择率，额外探测可能抵消收益。

该改写使用 SQLite 普通分组临时排序，不新增应用临时文件，但不能声称 SQLite 内部绝不使用磁盘。高命中、宽字符串及生产 SQLite 版本不同可能改变分组排序开销，需要在目标服务器复核。没有测量磁盘临时写入或进程 RSS，不能承诺排序不占额外资源。

## 2. 地点文本：先筛地点身份

地点元信息在当前库仅 29 条，而在每条词条上对省市县村/分区等字段反复 LIKE，会重复做大量相同工作。候选把地点元信息匹配放在地点子查询中，再用 `(user_id, location_name)` 筛词条；仍保留 `e.location_name` 的匹配分支，使孤立词条不丢失。混合词条/地点搜索仍保持 OR，不能改成 AND。

95 万条、每端点每场景 5 轮中位数：

| 端点 | 条件 | 当前 → 候选 ms | 耗时减少 |
|---|---|---:|---:|
| entries | q=广州，search_fields=location | 392.156 → 75.418 | 80.8% |
| entries | q=廣州，headword+location | 318.238 → 114.165 | 64.1% |
| entries | locations=廣州,香港 | 247.282 → 57.906 | 76.6% |
| standard-words | q=广州，search_fields=location | 1228.659 → 486.467 | 60.4% |
| standard-words | q=廣州，headword+location | 1110.804 → 828.697 | 25.4% |
| standard-words | locations=廣州,香港 | 1068.290 → 420.943 | 60.6% |
| map-points | q=广州，search_fields=location | 397.831 → 88.976 | 77.6% |
| map-points | q=廣州，headword+location | 343.487 → 146.099 | 57.5% |
| map-points | locations=廣州,香港 | 265.361 → 77.164 | 70.9% |

反例同样重要，不能把所有地点条件一起改成 IN：

- entries 小省份：1.189 → 5.562 ms，耗时成为约 4.7 倍。
- entries 省市组合：12.224 → 39.440 ms，耗时成为约 3.2 倍。
- standard-words 小省份：9.319 → 659.263 ms；某矛盾省市组合甚至从 0.045 → 755.768 ms，因计划改为扫描标准词索引，空地点集合未能短路。
- map-points 省市组合：105.378 → 143.425 ms；关键词+省份：300.602 → 372.168 ms。

建议仅先优化地点文本条件及已验证的混合 OR 场景；省市/地区精确约束与其组合保留原路径，后续再单独测。不把这些原型作为可直接整体部署的改写。

## 3. 简繁缓存：有收益，也有上限

现有 8192 项 LRU 对顺序遍历 41,558 个词形会反复淘汰。默认标准词聚合实验中，当前 6 次调用累计 249,348 次 miss、0 hit；65536 项原型第一次计算后保留全部词形，后续访问命中。

| standard-words 场景 | 9.5 万：当前 → 候选 ms | 95 万：当前 → 候选 ms |
|---|---:|---:|
| 默认大范围聚合，返回 100 项 | 128.165 → 71.926 | 177.105 → 119.304 |
| 省份大范围 | 116.310 → 69.686 | 356.332 → 306.130 |
| 地区大范围 | 114.058 → 67.699 | 331.316 → 279.047 |
| “什么”默认多字段 | 75.757 → 76.481 | 902.759 → 920.844 |
| 返回全部 39,965 组 | 218.287 → 163.838 | 276.749 → 196.498 |

这是转换缓存已热、**整页响应缓存未命中**时的收益。首次转换仍要计算；整页 Redis 响应命中本来就不聚合，没有这项收益。“什么”仅涉及较少词形，原容量已足够，增加容量没有实质收益。不同实验进程的绝对基线不能横向相减或相乘。

`scripts/measure_vocabulary_normalization_cache.py` 独立进程的 Python tracemalloc 实测（不是 RSS）：

| 不同词形数量 | LRU 容量 | 保留分配 MiB | 第二轮 hit / miss |
|---:|---:|---:|---:|
| 41,558 | 8192 | 1.82 | 0 / 41,558 |
| 41,558 | 65536 | 8.18 | 41,558 / 0 |
| 415,580（追加词形后缀） | 8192 | 1.88 | 0 / 415,580 |
| 415,580（追加词形后缀） | 65536 | 15.61 | 0 / 415,580 |

因此不能回到无限缓存，或宣称加到 65536 就能解决未来增长。建议同时明确每 worker 的容量/字节预算；短期扩大缓存是 CPU 与少量常驻内存的取舍，不是长期聚合架构。

## 4. 超大结果：免除无效的缓存编码

当前会把结果完整 `jsonable_encoder`/JSON 编码，再由 Redis Lua 判断超过 128 KiB 而不写入。对 standard-words 非永久大结果，可以有界编码，超过上限停止缓存编码，但仍完整返回 HTTP 内容。

用 `scripts/benchmark_vocabulary_cache_encoding.py` 做专用于现有纯 dataclass 结构的编码原型；非超限结果与现有编码逐字相同，超限返回“不缓存”，保留默认 100/1000 永久缓存绕过上限的既有规则。

| 返回分组 | JSON 大小 | 当前缓存编码 → 候选 ms | 说明 |
|---:|---:|---:|---|
| 100 | 10,512 B | 0.504 → 0.362 | 微小收益 |
| 1000 | 103,296 B | 5.073 → 3.529 | 保留完整编码/缓存 |
| 10000 | 1,052,342 B | 52.585 → 4.497 | 都不写缓存，候选提前停止 |
| 全部 39,965 | 4,248,105 B | 229.118 → 4.549 | 都不写缓存，候选提前停止 |

仅节约缓存准备阶段，HTTP 内容仍需完整校验/编码/发送，不能据此宣称整个接口快 98%。`limit=None` 是内部服务兼容性测量，HTTP 的既有 limit 默认/上限未修改。生产实现应专门处理返回 schema，不把 `vars` 原型当通用 FastAPI 编码器。

## 5. 低优先级与不建议项

- NOT NULL 的 standard_word/local_expression/ipa/location_name 去掉 COALESCE：entries 默认多字段几类场景约减少 2.6%–3.5%；map-points 通常约 2%–4%；备注字段没有收益，部分组合略慢。只可对实际 schema 确认 NOT NULL 的列使用，不得改变 nullable 字段的空值/通配符语义。
- 去掉 standard-words 的地区索引提示：小地区 3.976 → 46.395 ms，关键词+地区 30.202 → 86.887 ms。当前保留地区身份索引有依据，不应一律删除。
- 用全局地点位图替代标准词地点集合：当前 29 个地点名称时大范围/全量约快 5%–9%，但地点名称大量增长时，每个稀疏分组的大整数可能远比小集合占内存。暂不优先，不把小数据结果外推到未来。
- 不通过缩减默认字段、前缀匹配、估算 total、隐式截断或默认增加 worker 提速。现有任意子串 LIKE 的全扫描成本仍存在；这些实验未增加倒排索引，也没有把扫描变成常量时间。

## 实施边界

这些收益来自独立候选，不可将百分比相加或相乘。组合后的查询需要重新验证。不要每个请求额外全量探测，也不要根据本机结果对所有条件强制一个计划。

若进入实施，先落地两类按条件分支的 SQL 和有界缓存编码，再评估转换缓存预算。沿用跨 worker 准入，不新增并发或自动重试。扩大常驻缓存按 worker 数累计，普通 SQLite 排序可能增加工作内存/I/O；在真实 2 核 2 GB 和生产 SQLite 版本上复核后才能确认生产收益。
