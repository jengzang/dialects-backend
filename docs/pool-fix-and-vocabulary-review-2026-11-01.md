# 连接池 P0 修复与 vocabulary 复核

日期：2026-11-01。仅修改本地连接池及其测试，没有 SSH、部署、服务器配置修改或生产负载测试；没有修改另一位 worker 负责的 vocabulary 源码。

## 连接池缺陷与修复

文件：`app/sql/db_pool.py`。

旧代码把 `SELECT 1` 失败和归还队列已满放在同一个异常分支。健康的溢出连接归还时，队列已满，因此关闭原连接后又创建替代连接；替代连接再次入队失败，却没有关闭，仍被 `_all_conns` 引用。旧计数还只增不减，既不能反映实际连接数，也会使后续扩容误判已达上限。

本次改动：

- 健康连接归还遇到满队列时直接关闭，不创建替代连接。
- 成功创建/关闭后，用跟踪集合更新存活计数；关闭失败保留跟踪与额度，允许后续 shutdown 重试。
- 创建、归还、关闭共用生命周期锁；等待队列时释放该锁，避免阻塞其他借用者归还。
- 借出前再次检查关闭状态；初始化 PRAGMA 失败及部分初始化失败清理已创建连接。
- 修复上下文管理器 `finally` 中 `return` 吞掉调用方异常的问题，保留耗尽时的 TimeoutError、关闭错误和业务异常。

保留原池容量、最多 `pool_size * 2` 条连接、借用超时及 SQLite PRAGMA。没有新增线程池、后台服务、缓存或重试。关闭阶段仍沿用关闭全部连接的原语义，调用方应先停止业务借用。

## vocabulary 评审范围与判断

行为代码冻结在 `15b36458537619ea460a40f3fda8d802d7346609`，避免另一位 worker 持续提交影响复核。另阅读了随后提交的 scoped/global fuzzy 基准报告。总体判断：实现方向合理，在已复核范围内未确认需要阻止合入的新缺陷，但完整集成验收尚不能由本轮独立背书。

- `6fb221c` 的紧凑分组延后创建集合和字典，减少单值组对象开销；仍保留精确变体、计数和顺序。

## 资源收益与待办边界

以下量化数据来自另一位 worker 的提交报告，本轮核对实现与测试，未重复运行大型基准：

- scoped 报告中，47.5 万行、两个小地点、两字段“蜘蛛”的原生 SQL 为 43.204 → 3.506 ms；宽范围也有探测退化，如 54.586 → 58.061 ms。
- global fuzzy 报告中，47.5 万行、全域两字段“山东”为 113.421 → 52.909 ms；单字与高命中搜索收益有限。
- 新 scope/global 规划优化的查询进程峰值 RSS 基本持平，约 76 MiB。这些测量不是线上完整 worker，也不说明此前紧凑分组没有内存收益。
- 服务函数基准包含 ARM 上模拟 amd64 的测量；绝对延迟不可换算为生产 HTTP 延迟，也未验证多请求下的全站容量。

后续优先关注：全域 `standard-words` 仍建立所有归一分组，`limit=1000` 只限制最终输出，不限制中间分组；不同标准词数量持续增长时内存仍会增长。全域/宽范围子串搜索仍可能扫描，imports、sql/query 等其他历史风险也不在本批查询优化的闭环内。应结合原 OOM 时间线分开验收，不能把查询提速等同于消除整机 OOM。
