# 地名与词表接口性能复查（2026-10-24）

## 结论与约束

针对 2 核 CPU、2 GB 内存，应优先修复后台工作量和中间对象随数据增长的问题，再考虑新增索引。当前 vocabulary 的主要风险不是单次精确查词，而是全量标准词聚合、跨查询并发、批量导入/编辑和缓存失效后的重算。

- 本次只分析、只新增报告，未修改业务代码、真实数据库或索引，未部署。
- 地名 `limit=0` 完整返回是硬约束：不能增加隐性 LIMIT、强制分页，或用总耗时上限截断合法全量结果。词表已有全量返回也应保持完整。批处理内部切块不等于截断结果。
- 词表 entries 已有分页、standard-words 已有 limit，这里分析其现有行为，不提议用更小的返回上限优化。另做了 `limit=None` 的全量标准词验证。
- 有限机器无法同时保证无限数据、无限并发和固定延迟。这里限制同时工作的数量、缓存和中间缓冲，不限制成功请求的完整结果。
- 单机本地实验不是生产容量预测，尤其没有包含真实网络、全部中间件、Redis、多个 worker 的叠加负载。

## 实际数据与测试方法

真实 `data/vocabulary.db` 约 23 MiB：95,003 条词条、29 个地点、265 条日志、41,558 个不同标准词原始写法、39,965 个简繁归一分组，72,846 个“原词形—地点名”组合。

通过只读 SQLite 连接执行现有 query.py 服务函数，记录 EXPLAIN QUERY PLAN、函数耗时、独立进程峰值 RSS。Python 3.12 / SQLite 3.53.2，进程基础 RSS 约 58 MiB。没有导入会自动建表/迁移的 database.py。每种常规场景独立进程执行两次，第二次不是操作系统冷缓存。表中范围为这两次观测值，不是统计分位数。

临时数据库 A：复制十份词条，为每份变更 user_id/location_name/id，保留原词形与相同索引，ANALYZE 只作用临时主库。950,030 条、290 地点、728,460 个词形—地点组合；词形数不变。

临时数据库 B：在 A 基础上给每份词形增加不同后缀，模拟不同词持续增长。415,580 种词形、399,650 个归一分组。这是合成压力样本，不代表真实语言分布。

| 场景 | 真实库耗时 | 临时库 A 耗时 | 真实库 / A 峰值 RSS |
|---|---:|---:|---:|
| standard-words，现有 limit=100 | 0.105–0.144 s | 0.483–0.556 s | 109 / 307 MiB |
| entries，模糊“什么”，含精确 total | 0.040–0.054 s | 0.369–0.405 s | 约 61 / 61 MiB |
| entries，模糊无命中 | 0.095–0.154 s | 0.745–0.780 s | 约 61 / 61 MiB |
| map-points，无过滤 | 0.009–0.011 s | 0.103–0.105 s | 约 61 / 62 MiB |
| map-items，选“什么” | 0.00026–0.00106 s，52 条 | 0.00207–0.00278 s，520 条 | 约 59 / 63 MiB |

B 的 standard-words limit=100：1.676 / 0.976 s，进程峰值 570 / 603 MiB。转换缓存最终包含 415,580 项。

全量标准词补充验证：真实库 `limit=None` 返回全部 39,965 组，0.177 s、峰值 108.6 MiB；B 返回全部 399,650 组，2.149 s、597.9 MiB。返回长度均等于 total。这里只验证服务函数完整结果，不是 HTTP 序列化或传输测试。

不能把单个进程峰值简单乘 worker 数作为实测总内存，但若多个 worker 同时执行这些任务，2 GB 机器的余量显然值得警惕；还需给其他 API、Redis、数据库页缓存和系统保留空间。

## 词表：具体瓶颈与改法

### 1. 标准词聚合是第一内存风险

位置：`app/service/vocabulary/query.py:458`、`app/service/vocabulary/script_variants.py:22`。

现有查询有 `(standard_word, location_name)` 覆盖索引，EXPLAIN 确认使用。因此不能说它“没有索引”。问题在于 SQL 分组后依然：

1. fetchall 全部词形—地点组合；
2. 构建词形映射和按归一词分组的字典，保存地点 set、各变体计数；
3. 对全部归一词排序，最后才取 100/1000。

内存由词形数、归一词数和词—地点组合数共同决定，并非返回条数决定。另外 `standard_word_key` 使用 `lru_cache(maxsize=None)`，新词不断出现时每个 worker 的缓存持续增长。3 个 worker 不共享这份 Python 缓存。

先做代码优化：游标逐行/fetchmany 消费；有限 limit 用堆选择，完整结果仍完整排序输出；转换缓存设定容量并观测命中率，删除无必要的重复映射。缓存条数上限仍不是严格字节上限，必须同时考虑长字符串，不能承诺固定 RSS。

仅在实验脚本内替换 fetchall 为迭代、全排序为 heapq.nsmallest：A 的峰值从 307 降至 206 MiB，耗时约 0.420–0.498 s；前 100 结果完整对象与原实现相等。没有改业务文件。这只能减少中间对象，grouped 字典和地点集合仍随数据增长，不能作为长期内存有界方案。

需要完整且严格限制 Python 内存时，可将中间归一结果分批写入临时 SQLite 文件，再在磁盘上聚合、排序和逐批输出；临时空间按磁盘配额控制、失败清理、并发 1。这会增加 I/O，应测量后采用。大量反复查询的长期方案见后文汇总表。

必须保留既有语义：简繁归一、代表词按频次和字典序选择、排名规则、variants 顺序、精确 total。目前 location_count 按地点名去重，不能顺便改成 user_id+地点名去重。

### 2. 模糊搜索不受普通 B-tree 的子串定位支持

位置：`query.py` 的 `_build_filter_clause`、`_append_like_group`、`query_vocabulary_items`；`routes/vocabulary_sql.py` 搜索构建函数。

默认搜索将原文/简繁变体与 standard_word、local_expression、ipa、notes、informations 的 `COALESCE(column,'') LIKE '%q%'` 组合 OR。前导通配符无法通过普通列索引定位子串；执行计划显示 SCAN。精确 standard_words 的 IN 查询则能走索引，应保留快路径。

entries 每页先查数据再做精确 COUNT；无命中时可能完整扫两次。已有地区过滤的 count-first 优化，但未覆盖一般条件。深 OFFSET 也会增加扫描成本。SQL 编辑器查询同样有宽列模糊匹配、分页和 count 成本。

代码优先：

- 精确 count 与分页结果分开缓存，缓存键包含权限范围、完整过滤条件和数据版本，但不包含页码；相同过滤翻页复用准确总数。不能拿估计值冒充精确总数。
- count 没有引用地点元数据时去掉 LEFT JOIN；当前地点身份有唯一约束，才能保证等价。
- 第一页未填满时，可在语义及一致性成立的情况下直接用已返回数确定 total；第一页满了不能推断总数。
- count-first 对无命中有效，但命中第一页可能变慢，需按负载选择，不能机械全改。
- 保留用户选择 search_fields 和范围过滤的能力；不能默认少搜字段、少搜地区以改变召回。
- 深分页可增加可选游标接口作为后续兼容能力，不撤销已有分页，更不能用它取代全量模式。

A 上无过滤 count 小实验：原 JOIN 约 72–100 ms，省略 JOIN 约 7–12 ms，结果相同。这是特定 SQL 微基准，不是接口整体倍数。

### 3. 地图聚合可以减少重复关联，地图明细需要减少全量复制

位置：`query.py:563` 与 `query.py:663`。

map-points 普通分支先逐词条关联宽地点元数据，再按 user_id/location_name 分组；地区分支已经采用先聚合再 JOIN。可将这个优化推广到不依赖地点字段过滤的普通查询，依赖地点字段的过滤必须放在正确阶段。

A 上等价核心 SQL 小实验：先 JOIN 再聚合约 110–122 ms，先聚合再 JOIN 约 40–48 ms；返回行一致。它仍需要计数全部词条，不会变成常数复杂度。

map-items 选少量词时当前很好，精确词索引有效。但选词/地点/命中数增长后，会 fetchall → 行字典 → 分组列表 → 数据模型 → JSON，存在多份表示。建议按现有分组及顺序流式构造完整 JSON。分组顺序需要全局信息时先生成窄的组目录或临时磁盘分组，避免为了流式输出擅自改顺序。也需处理无坐标省略统计等既有字段。

### 4. 缓存并没有覆盖所有内存与并发风险

位置：`app/service/vocabulary/cache.py`、`cache_warmup.py`。

已有良好设计：共享 Redis、版本校验、同 key 合并、租约续期、按需缓存 128 项且每项 128 KiB、串行预热、启动/失效重算复用部分结果。应保留，不能简单重写成进程内无限缓存。

剩余问题：

- Lua 默认缓存分支在大小检查前直接 SET。7 种默认组合没有这个大小上限，也无 TTL；地点选项、地图点随地点增长，不保证固定大小。旧版本由清理逻辑回收，仍应核对异常情况下积累。
- 普通缓存是先完整 jsonable_encoder/json.dumps，再发给 Redis，最后才检查 128 KiB。大响应即使不入缓存，也已经付出完整编码、复制和网络传输成本。
- 大结果不入缓存时，等待者拿到锁后可能再次执行相同查询，形成连续重复计算。
- 同 key 合并不等于不同 key 限流；Redis 不可用时直接执行 loader，也没有统一重查询预算。
- 搜索统一依赖 entries 和 locations 两个版本；只改词条也会使纯地点选项失效。频繁写入会造成预热反复失效。

建议：默认缓存也设定可观测的预算；超预算只跳过缓存，不能截断响应。使用可中止的增量编码或响应类型准入，避免先完整构建可缓存副本。拆分必要的数据依赖，保留版本栅栏。大结果合并可选择短生命周期磁盘成品，但要有磁盘字节配额/TTL/单生产者；磁盘不足时回退原完整流式路径，不把半成品当成功。不能单纯扩大 Redis 内存或缓存项目数。

预热继续单生产者、串行执行；写入突发应合并失效通知、设置冷却与最大延迟，在线重查询繁忙时让路。预算计入共享重任务池。失败沿用有界退避，不在故障时密集循环。

### 5. 部分 async 接口仍然阻塞 worker 事件循环

位置：`app/routes/vocabulary.py:825`，`app/routes/vocabulary_sql.py:603/729/889/911`。

上传预览在 async 路由内同步执行解析与数据库调用；SQL mutate/batch-mutate/batch-replace-preview/execute 直接同步操作 ORM/SQLite，批量替换还有逐行 Python 验证。大的请求会让同 worker 其他协程等待。

普通搜索已有卸载到线程机制，locations/logs 等同步 def 路由也由框架处理，不应一概指责为事件循环阻塞。

改法：把整个同步工作单元放入受准入控制的同步执行函数，在该工作单元中管理数据库会话和事务；不跨并发任务共享 Session。后台线程不是免费资源，必须先准入再占线程，别让很多线程阻塞等待 SQLite 写锁。写事务提交后即使客户端断开仍需完成失效通知；只读任务无人等待时可以取消计算并清理。

### 6. 上传、替换、导出的峰值内存与写锁

位置：`parser.py`、`service.py:303`、`routes/vocabulary.py:673`、`routes/vocabulary_sql.py:911`。

- 上传 `await file.read()` 全读，随后 pandas DataFrame、ParsedVocabularyRow 列表、bulk_insert_mappings 列表可能同时存在。预览也解析完整文件。解析错误列表亦可增长。
- 导入替换先 `.all()` 旧词条并建立快照，然后才判断是否超过 500 条日志保存上限；这个上限没有限制前面的内存分配。
- `_import_locks` 按用户/地点持续积累且只在进程内有效，不能实现跨 worker 写入限流。
- 批量替换 BEGIN IMMEDIATE 后 fetchall 所有命中行，再 Python 模拟和验证，写锁覆盖很长的读/计算阶段。
- 导出已用 yield_per(2000) 和 write_only Workbook，这是好基础；但最终 ZIP 写入 BytesIO，再一次交给 StreamingResponse，并不是有界文件输出。

改法顺序：

1. 旧记录快照最多查询 501 条以判断能否记录，真实删除数量另行准确计数；不减少实际替换/删除的记录。
2. 保留 UploadFile 的磁盘落盘能力，CSV 分块、XLSX 用只读迭代；保留完整解析结果/错误时写入临时文件，不积累多个全量列表。预览可对全文件做有界内存扫描，不牺牲完整统计和校验。
3. 导入分批执行插入但仍保持一个原子事务。分批 SQL 只减 Python 峰值，不自动缩短写锁。更短写锁要靠锁外解析/暂存，以及事务内校验版本后原子应用；必须避免锁外验证后的并发数据变化。
4. 批量新增对重复地点一次性验证，避免每行重复查询。批量替换只取验证所需列，逐批校验；挪出事务的部分必须有版本冲突检测和事务内复核。
5. 导出 ZIP 保存临时文件，用文件响应发送并在结束/异常后删除；完整导出不设行数截断。临时磁盘按可用空间和配额管理，失败明确报错，不发送伪完整文件。
6. 本机词表写入串行入口，覆盖所有写路径；多 worker 不能只用 threading.Lock。可复用本机 flock，统一顺序取得资源锁并及时释放。

### 7. 地点、分区、日志和维护任务

location-options 的规模主要是地点数，当前只有 29，优先级较低。partition-options 即使指定 parent 仍会读完整路径树，可按 parent 过滤/缓存子树，维持层级语义。

locations/logs 已分页；logs 为各种过滤建了单列索引，但未来日志增长后，组合过滤 + created_at/id 排序 + 精确 count + OFFSET 仍有成本。应根据实际高频组合评估复合索引，不能给每一种组合都加索引。日志 payload 的大对象也要计入写入与备份体积。

database.py 未配置显式 pool_size/max_overflow；当前 SQLAlchemy QueuePool 默认 5+10，每 worker 最多 15 个连接配额，3 worker 理论最多 45。并不表示实际常驻 45 个连接或每个连接占用固定内存。SQLite busy_timeout=10 秒只是等锁，不是执行时间预算。应先统一准入，再按每 worker 会话需求设显式小池、禁用/限制溢出并实测排队；不能只减池大小造成依赖持有连接与后台取连接的死锁。

导入时自动建表/补索引/迁移应逐步移到一次性的发布步骤。启动维护在 master 执行，达到空闲页 15% 且至少 1024 页时 VACUUM，总会 ANALYZE；随着数据库增长，重启成本上升。建议维护窗口、按变化量决定统计刷新，并保留失败记录。

备份已有单后台调度，词表每 3 小时完整备份、保留 7 天，稳态约 56 份（边界数量会变化）。数据库变大后磁盘与 I/O 放大明显；例如每份 1 GB 时约 56 GB 只是容量估算。应增加总字节预算/保留分层、校验恢复能力，SQLite backup 分步让路。仅配置 pages 参数并不等于严格带宽限速，需测实际 I/O 并实现节流。维护/备份失败不要密集自动重试。

## 地名还有哪些值得优化

前次已经解决全量内存驻留、整张行政树加载、部分回表和并发问题。下一步重点不是重新限制结果数。

1. **子串扫描仍在。** 覆盖索引降低扫描字节和回表，并不意味着 `%词%` 已能索引定位；单字高命中查询仍有线性扫描/输出成本。精确/前缀路径、范围选择性可继续分析，但不擅自替换用户的 contains 语义。
2. **HTTP 层尚需测量。** 已有全量“村” points 测试返回 935,922 点、82,389,909 JSON 字节；之前本地生成约 4.975 秒，峰值约 43.7 MiB。这是服务流式生成记录，不是网络 SLA。全量输出的序列化、GZip CPU、传输带宽可能成为后续主瓶颈。当前 app 启用 GZip，应测压缩等级/分块/代理压缩的权衡，不盲目关闭压缩。
3. **慢客户端占用查询资源。** 流式请求持有游标和 heavy slot 直到结束；两个慢客户端可能长期占住两个槽。先测背压和取消释放。如果确有问题，再选有配额的磁盘结果暂存，把数据库计算与下载解耦。不能在健康全量传输到某个时间后硬截断。
4. **重复全量查询尚未合并。** 全量绕过小对象缓存是正确的，但热门完全相同的请求可考虑单生产者临时文件复用。只在重复率证实后实现，因为多一轮写盘/读盘可能反而拖慢 SSD。
5. **需要跨模块预算。** 当前 toponyms 的 heavy=2/light=1/tree 子限制只约束本模块。vocabulary 另起查询/预热/导入仍会争抢同一台 2 核机器。

## 面向 2 核 2 GB 的资源方案

以下是建议的起始配置，需要真实部署混合压测调整，不是已经验证的最佳值：

- 跨 worker、跨 toponyms/vocabulary 的重计算池：全机最多 2 个执行单元。一次高内存词表聚合/导入解析/导出生成可占满 2 个配额，使这类任务全机最多 1 个；普通重扫描占 1 个。避免简单地让两个约 600 MiB 的任务并发。
- vocabulary 写事务全机最多 1 个；写操作和后台任务消耗同一个重工作预算，不另开一组无约束线程。锁取得顺序固定，防止死锁。轻量请求保留独立但有限的通道。
- 在占用连接和线程之前排队；起始可用全机 8 个候选等待位。满队列明确返回可重试状态，或由产品选择持久任务机制；不会无限保留请求对象。排队超时只用于未开始的工作，不给已接受的全量输出加总耗时截断。
- 读失败不进行无限服务端重试，客户端带抖动退避；事务失败先回滚，仅确认未提交/具幂等性的操作才允许有限重试。无法确认提交状态的写入不能盲目重复。
- 所有缓存、临时文件、等待队列、解析缓冲分别有上限。单个超大结果绕过缓存，仍按完整结果输出。无足够磁盘时明确失败，不伪装成成功但少返回数据。
- 保持现有 worker 数做基线，不通过加 worker 解决问题。是否从 3 调整到 2，要看总 PSS/RSS、事件循环延迟、吞吐与混合请求结果；不能仅凭核数决定。

## 什么时候才需要改数据库

### 标准词汇总数据：比盲加普通索引更有价值

代码优化后，若标准词聚合仍是热点，可以持久化简繁归一键及按词/地点/变体的计数、必要的最早 id 等汇总数据。默认列表直接读汇总，不再每次从全部 entries 构建 Python 聚合。

需解决：地点名去重的既有语义、变体代表词规则、导入替换/删除/移动地点的事务性增量更新、恢复与重建。模糊搜索匹配词条 notes 等字段时，不能直接使用未过滤的全局汇总计数；必须回退匹配子集的聚合或维护合适的条件路径。汇总表不是所有过滤组合的万能缓存。

后台重建一次一个、分批写新一代汇总，完成并校验后原子切换；失败继续使用旧版本/原始查询，不暴露半成品。初次迁移先离线测时间、空间与写放大。

### 子串索引：FTS5 需认真验证中文与语义

普通 standard_word/notes B-tree 解决不了 `%词%`。FTS5 trigram 可用于部分长度足够的子串候选检索，但不能把 token MATCH 当作现有 LIKE 的等价替代：

- 用户常搜 1–2 个汉字；trigram 对少于三个字符的查询无法按同样方式有效定位，需要回退扫描或另外设计单字/双字倒排。
- 多字段 OR、简繁变体、LIKE 的 `%`/`_` 通配符语义、空值与大小写行为必须一致。先生成候选，再原谓词核验，并测试无漏召回。
- 需要确认生产 SQLite 的 FTS5/trigram 可用性与具体查询形式可用的执行计划，不能仅凭本机版本判断。
- 倒排索引增加数据库大小、导入写放大、备份成本；中文高频单字的候选可能仍非常多。

因此第二阶段先做汇总优化和典型查询分布采样，再决定是否试 FTS 或单/双字索引。全量结果本身的输出成本任何索引都无法消除。

## 建议落地顺序与验收

第一批，不改表：事件循环阻塞路径卸载并受准入控制；跨模块全局重任务预算/单写入；归一缓存有界；旧记录日志先限快照再物化；精确 count 省 JOIN；地图先聚合后关联；大缓存编码避免无效全量副本。

第二批，不改数据语义：聚合逐行消费；全量 JSON 流式化；上传解析/导出用临时磁盘；批量写减少 Python 全量对象并保持原子性；缓存依赖和预热合并；连接池及备份维护预算。对于真正无界的聚合，按测量选择磁盘中间表。

第三批，仅在前两批压测仍不足时：归一键/汇总表、选择性复合索引、模糊搜索倒排试验。

验收必须包含：

- 地名 limit=0 的全部 ID/字段/顺序/计数与原查询一致，无隐藏截断；中文单字高命中、无命中、慢客户端、中途断开。
- 词表全量模式的全部分组、明细、计数、排序、简繁及权限语义一致；有限列表的优化也与原结果逐项比较。不能只验前 100 项就宣称全量能力成立。
- 同词增加地点、不同词增长、单地点大表、长文本、连续导入、Redis 不可用、多个不同搜索 key 同时请求、与地名全量查询混合。
- 测总进程 PSS/RSS、Redis 内存、临时磁盘、SQLite WAL 大小与 checkpoint、I/O、CPU、事件循环延迟、排队和写锁等待；看 p50/p95/最大值而非一次最快请求。
- 原子写入故障注入：回滚、断开、提交后通知失败与幂等；临时文件清理、进程退出释放锁、预热失败退避。

本次没有执行真实写入/上传并发/生产 HTTP 压测，所以这些路径的风险来自代码证据，未给出虚构的提速倍数或生产承载量。
