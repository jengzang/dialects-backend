# auth.db 使用日志写入与故障处理

适用于 `api_usage_logs` 和 `api_usage_summary`。现有表结构、记录路径规则、匿名处理及登录请求排除规则不变。

## 正常写入

- SQLite 连接明确设置 `busy_timeout=5000` 毫秒。
- 两个消费者各自按 50 条或从批次第一条事件起 2 秒触发写入。数据库拥堵时，实际入库会更晚。
- 对 SQLite `BUSY` / `LOCKED`（包括扩展错误码）最多执行 3 次写入尝试，每次确认回滚后才退避重试。非锁错误不反复重试。
- 汇总重试重新建立本批次的变更，避免把同一次调用重复累加。

## 失败文件

当明细或汇总队列满、队列入队异常、数据库写入重试耗尽或出现永久错误时，保存原始事件至项目根目录下的 `logs/auth-usage-recovery/`。可用 `AUTH_USAGE_RECOVERY_DIR` 指定服务器上的可写持久化目录。

每个文件包含 `version`、`queue_name`、`reason`、UTC `saved_at`、错误信息和 `events`。文件通过临时文件写入、文件同步、原子重命名发布，权限为 `0600`；目录创建权限为 `0700`。若发布后的目录同步失败，报告 `AUTH_USAGE_RECOVERY_SYNC`，不重放已发布的批次，避免产生重复补偿证据。

日志标记：

| 标记 | 含义与处理 |
| --- | --- |
| `AUTH_USAGE_RETRY` | SQLite 写锁暂时冲突；关注持续出现的情况 |
| `AUTH_USAGE_RECOVERY` | 原始事件已保存，但尚未计入对应数据库表；需要人工核对 |
| `AUTH_USAGE_RECOVERY_SYNC` | 文件已发布，但目录同步失败，掉电持久性降低 |
| `AUTH_USAGE_LOST` | 入队与失败文件保存均失败；该事件无法保留 |
| `AUTH_USAGE_SHUTDOWN` | 停止信号投递失败或排空超时，未完成的队列仍有丢失风险 |

数据库与失败文件都写不进去时，后台保留当前批次并暂停继续取队列，每秒再尝试处理；不会清空该批次。此时队列仍可能被填满，应立即处理磁盘、权限或数据库故障。

如果事务回滚也失败，则关闭该 Session，当前批次只重试保存失败文件，不自动重试数据库写入，避免对事务结果不确定的汇总再次加数。

失败文件不是自动重放队列。**不要直接把所有汇总失败文件重新累加**：明细和汇总是独立写入的，故障范围可能不同，`rollback_failed` 的事务结果尤其需要人工核实。先核对数据库、错误类型及事件内容，再执行针对对应表的补偿；核对或补偿完成后才归档文件。当前改动不提供自动补偿命令。

## 停止与边界

停止服务前先停止请求等生产者。日志停止函数只对已启动线程投递停止信号，等待排空并退出，共享 30 秒期限。超时返回 `False` 并报告仍存活的线程；需要再次完成停止后才能重新启动，避免重复消费者或部分消费者缺席。

这次改动不改变以下边界：

- 明细与汇总仍使用两个队列、两个事务，不保证两表同时提交。
- 正常入队的事件仍在内存中；强制结束、机器掉电或排空超时可能损失尚未持久化的事件。
- 磁盘不可用时不能保证失败文件保存成功。
- 没有自动重放或事件去重机制，不提供“恰好一次”处理保证。
