# entries 查询提速验证（2026-10-24）

## 实现

基线为 `7ebdbc0`。只修改 `query_vocabulary_items` 查询流程：

1. 使用原有精确计数 SQL 和计数缓存先取得 total；`offset >= total` 时返回完整计数与空页，不执行明细 SQL。
2. 筛选不引用地点元信息 `l.` 时，在词条子查询完成原有筛选、ID 倒序和 LIMIT/OFFSET，再 LEFT JOIN 地点表；外层显式按 ID 倒序。地点关联按 user_id + location_name，不丢弃孤立词条。
3. 涉及省、市、地点元信息 LIKE 等条件时，继续先 JOIN/过滤再分页。地区身份子查询仍在分页前执行。

没有修改前端、参数、JSON schema、分页规则、匹配语义、索引或生产数据。没有新增应用临时文件、磁盘聚合、后台任务、线程、缓存或重试。沿用既有 heavy 并发上限和计数缓存；新增子查询最多输出一页（HTTP 上限 200）记录。计数扫描与深分页跳过本身仍可能随数据量增长。

计数缓存和 SQLite 仍保持原有一致性边界：没有新增跨 Redis/SQLite 的原子事务，也不保证并发写入时两个读取组成同一快照。缓存正常失效机制不变。

## 测量方法

本机 macOS 26.3.1 arm64，Python 3.12.13，SQLite 3.53.2。单进程直接调用完整 entries 服务函数，计时包含 SQL、计数和响应 dataclass 构建，不含 Redis 往返、HTTP 编码、网络、代理或前端。SQLite 页缓存预热，**不是磁盘冷启动测试**。

每场景每版本预热后交替运行 11 轮，报告中位数；每次都完整消费返回页，比较每个字段、列表顺序、total/page/page_size 与基线一致。这里测试的是接口原有分页契约，不是用分页替代原本全量接口。输入数据库只读。

- 当前数据：95,003 条词条、29 个地点。
- 增长测试：复制到独立可删除测试库，词条和地点身份均扩大 10 倍，950,030 条、290 个地点，索引保持不变。增长库仅为基准夹具，不是应用运行时的临时磁盘方案。没有模拟所有词形也增长的场景。
- `deep-page` 为第 950 / 9500 页，每页 50 条，约跳过半数词条。
- `fuzzy-hit` 使用“什么”和现有默认搜索字段，匹配 946 / 9460 条，每次返回 50 条。
- `fuzzy-no-hit` 使用确定无命中的测试字符串；SQL LIKE 的通配符和简繁语义保持原样。
- `exact-word` 自动选取高频原始词形，匹配 51 / 510 条；不代表所有精确词查询。

复现：

```bash
_RUN_TYPE=MINE .venv/bin/python scripts/benchmark_vocabulary_entries.py \
  --rounds 11 --output /tmp/entries-current.json
_RUN_TYPE=MINE .venv/bin/python scripts/benchmark_vocabulary_entries.py \
  --scale 10 --rounds 11 --output /tmp/entries-growth.json
```

脚本输出全部样本、范围、完整结果 SHA-256 和 EXPLAIN QUERY PLAN。基线与新实现逐项比较一致，不仅比较 ID 或数量。

95 万条关键场景的 11 轮最小–最大范围：

- 深分页：原 48.292–52.566 ms，新 19.772–22.454 ms。
- 模糊无命中：原 402.189–407.738 ms，新 201.901–338.674 ms；新实现有一次明显长尾，不能据此保证每次都减半。
- 模糊有命中：首页原 367.068–373.740 ms，新 367.450–370.006 ms，基本无改善。

EXPLAIN 确认旧深分页在词条扫描时查找地点索引，新查询先通过 co-routine 产生一页词条，再查找地点索引，避免为跳过的大量记录关联地点。

## 结果：理想计数缓存已命中

用内存 resolver 模拟原有计数缓存命中，**不包含真实 Redis 网络成本，也不是整页响应缓存命中**。用于隔离明细 SQL 的变化。

| 场景 | 95,003 条：原 → 新 ms | 950,030 条：原 → 新 ms |
|---|---:|---:|
| 默认深分页 | 3.547 → 1.038 | 40.329 → 11.874 |
| 模糊搜索无命中 | 20.067 → 0.009 | 203.572 → 0.015 |
| 越界页 | 7.192 → 0.003 | 88.669 → 0.009 |

无命中和越界的微秒级数值是跳过 SQL 后的服务函数成本，不应解读成生产 HTTP 请求能在该时间内完成。整页响应缓存命中时，本来就不执行查询，不预期从本次 SQL 改写获益。

## 取舍

本次主要改善无命中、越界及深分页。常见有命中模糊首页仍受 `%关键词%` 扫描和精确计数支配，没有实质提速。极快的精确首页因子查询产生约 0.02 ms 额外开销，已保留在报告中，没有声称普遍更快。

这些是本机串行服务基准，不是 2 核 2 GB 生产服务器的延迟或吞吐承诺。未测生产并发、冷磁盘、真实 Redis 延迟和进程 RSS；本次未增加无界 Python 中间集合，不能据此承诺特定整机内存占用。

## 回归

- 核心查询资源与真实 FastAPI HTTP 契约测试：29 passed。新增 14 项查询资源断言中，旧实现最初全部失败；其中地区测试曾错误使用非现有路径分隔符，已修正为夹具中的完整地区路径。
- 较大范围运行出现 6 项失败，均在原查询基线重新执行后复现：限流配置、DOCX 空白解析、条目旧顺序/简繁旧顺序、地图旧字段、地点标签旧分隔符。
- Redis 集成测试需要隔离真实 Redis，本次环境没有 Redis，相关用例跳过；没有把跳过当作通过。计数 resolver 与无缓存 HTTP 路径已覆盖，缓存键/SQL/失效机制未改变。
- 排除已在基线复现的 6 项失败后，较大范围回归：135 passed、24 skipped、6 deselected。独立代码审查无阻塞问题；修正了基准脚本中缓存模式计划采集预热不对称的问题，该问题不影响正式计时（正式计时原本已预热）。
