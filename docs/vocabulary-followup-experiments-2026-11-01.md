# vocabulary 剩余瓶颈与本地优化实验

日期：2026-11-01。承接生产日志报告，标准词四次约 30 秒的计算锁等待失败按用户确认视为已解决，不再列入待修复项。

本轮没有连接服务器，没有修改业务代码、数据库结构、配置或前端。新增的是离线实验脚本和报告。以下候选尚未落入生产查询路径。

## 1. 剩下不只是几种慢查询

生产历史窗口：10-25 00:42:39 至 11-01 00:42:39，北京时间。耗时来自 auth.db 的请求 duration，不是 SQL 独立计时。已解决的四次 503 排除后，仍有 **65 条成功请求达到 5 秒**，分布在六类端点。

其中 >=5 秒分别为 entries 39 条、standard-words 成功 6 条、imports 13 条、sql/query 2 条、map-points 4 条、map-items 1 条。完整模式与逐请求列表保留在生产报告中。

一个月内还有稀少但更慢的模式：standard-words 音标单字段 22.575 秒、音标+详细信息 24.579 秒，map-points 方言词+音标+详细信息 14.054 秒。不能据最近一周某形状没有慢样本就断言该分支已经很快。

对照：一周无 q 的全域 entries 首页 9 次，最大 0.089 秒；无 q 的全域 map-points 59 次，中位数 0.038 秒。普通地点列表、分区选项暂不应排在关键词搜索之前。

字段命名要特别区分：`definition` 对应标准词 `standard_word`，`headword` 对应方言词 `local_expression`，`detail` 才是 notes/informations。下面按这个实际映射解释。

## 2. 实验方式与有效范围

- 原始本地样本 95,003 条、29 个地点名；增长样本 475,015 条，复制到不同 user_id，保留词形、地点名、索引和匹配分布。未使用生产业务数据库副本。
- 增长样本不是词形/地点持续增加的全部未来情形，也不是生产数据的等比例还原。沿用复制库的统计信息，没有在生产执行 ANALYZE。
- 大地点为廣州白話：原始 50,434 条；小地点为天柱竹林：原始 1,323 条。增长后分别 252,170、6,615 条。22 地点选择本地条数最多的 22 个，覆盖 454,025 条；不同于生产原始 22 地点的实际选择性。
- 第一轮另用 226 条的更小地点检查极窄范围，不能把第一轮 small 与后续 small 当作同一输入。
- 条件覆盖：标准词单字段、方言词单字段、标准词+方言词；全域、大地点、小地点、22 地点、无地点命中；蜘蛛、皮、人、无命中关键词；无 q、关键词/地点文本重叠、通配符、省和分区。
- SQL 在本地原生 arm64 Python 3.12 Linux 容器顺序执行。限制为 `cpu.max=200000 100000`、`memory.max=2147483648`、`memory.swap.max=0`，即 2 CPU 配额、2 GiB 内存、不允许 swap。候选交替执行顺序。
- 第一轮 520 个查询组合，3 轮；增长样本 364 个组合，3 轮；首页顺序试验 134 个组合，5 轮。表中取中位数。
- 导出阶段共 938 个服务调用组合通过返回值比较；SQL 回放检查结果摘要，entries 另外取消分页 LIMIT，逐行校验全部命中记录及顺序；不会只比较前 50 条就认定等价。
- 增长 SQL 进程峰值 RSS 54,868 KiB；首页顺序试验 34,680 KiB。这是实验进程，不是应用 worker、整个容器或标准词 Python 聚合的内存。

**2 CPU 配额不是与生产物理 CPU 同等速度。** 这里没有同时运行生产的多个 Python worker、其他业务、Redis 和现有 swap 压力；热页缓存也不同。因此下面的毫秒数、比例只能用于比较候选 SQL，不能承诺线上 8 秒会按同一比例缩短。

本地 growth SQLite 文件只是离线造数和验证文件；没有引入应用临时磁盘聚合。候选 SQL 中出现的 `USE TEMP B-TREE` 是 SQLite 的分组执行计划，并不意味着新增了应用层磁盘汇总方案，也未强制将排序放入内存。

SQLite 临时 B-tree 在结果较大时仍可能使用临时文件，取决于 temp_store、构建选项和数据量；本轮没有测量这部分独立 I/O，不能承诺候选绝无临时磁盘读写。正式采用改变 GROUP BY 计划的候选前，应补充高命中词的临时 I/O 测量；若不能接受，应保留原路径，不能通过修改生产 temp_store 或强制占用更多内存回避这个取舍。

## 3. entries：最值得推进的是小结果首页少做一次扫描

现有流程先精确 COUNT，再读取一页；无命中可以只做 COUNT，翻页可以复用独立计数缓存。这些优势应该保留。

实验流程只针对“计数缓存未命中、第一页”：先查当前一页，如果不足 page_size，就能从这一页严格推导 total；满页才补做 COUNT。没有近似总数，也没有截断匹配记录。

47.5 万条、page_size=50：

| 条件 | 精确命中数 | 当前 SQL 总耗时 ms | 页优先候选 ms | 解释 |
|---|---:|---:|---:|---|
| 蜘蛛，仅标准词，小地点 | 5 | 61.86 | 30.58 | 少一次扫描，耗时约减半 |
| 蜘蛛，标准词+方言词，小地点 | 5 | 89.79 | 45.58 | 少一次扫描，耗时约减半 |
| 蜘蛛，仅方言词，大地点 | 30 | 59.83 | 30.63 | 少一次扫描，耗时下降约 49% |
| 无命中，仅标准词，全域 | 0 | 30.01 | 45.51 | **退化约 52%**：COUNT 可走窄覆盖索引，取页还需不同的访问路径 |

结论：**不建议直接把所有首页改成页优先。** 下一步先验证范围明确的“内容非覆盖字段 + 地点筛选”形状，并保留已有计数缓存的零命中短路。若不能用稳定、低成本条件避开无命中/覆盖索引退化，应继续保留计数优先。

真正落地还要处理：计数缓存命中时保持原路径；推导出的 total 仍写入既有独立计数缓存；页查询和必要计数采用一致读视图；页满时 total 不能以 page_size 代替。不能仅在 SQL 文件里交换两行就交付。

### 已否决的 entries 简单改法

1. **把默认四字段的强制地点身份索引计划扩大到所有字段、所有地点数量。** 仅标准词、22 地点、蜘蛛从 36.96 增至 140.22 ms；标准词+方言词同条件从 57.41 增至 159.97 ms。覆盖索引和内容选择性被破坏，不可照搬。
2. **先 GROUP BY 全部地点名，再 LIKE。** 第一轮标准词、22 地点、人从 7.36 增至 42.72 ms；额外地点名扫描和不同 OR 计划抵消收益。
3. **用 MIN 索引跳跃枚举地点名后再 LIKE。** 带 q 的多数样本基本不变；无 q、22 地点从 80.69 降至 29.94 ms，但这属于已知无 q 计数方向。原型无地点基数回退保护，不可直接上线；已有有界实现可以进一步处理多参数回退问题。

目前没有证据支持一种 SQL 改写能普遍消除所有 entries 的模糊扫描。`%关键词%` 在现有普通 B-tree 上仍不能直接定位任意子串。

## 4. standard-words：地点范围内的非覆盖内容搜索值得单独选计划

当前为了 `GROUP BY standard_word, location_name`，SQLite 可能扫描标准词索引，再为方言词等字段逐条回表。对大量不命中行，这些读取没有产生聚合收益。

候选复用现有 `(user_id, location_name)` 索引遍历，随后只对命中项分组。**执行计划仍是 SCAN，不是通过索引直接定位了关键词，也不能宣称消除了全表扫描。** 改善来自不同遍历顺序和分组输入访问成本。

47.5 万条，以下仅 SQL 分组阶段，不含 Python 简繁归一：

| 条件 | 当前 ms | 候选 ms | 耗时下降 |
|---|---:|---:|---:|
| 蜘蛛，标准词+方言词，小地点 | 298.44 | 35.99 | 87.9% |
| 皮，标准词+方言词，小地点 | 300.01 | 35.33 | 88.2% |
| 蜘蛛，标准词+方言词，大地点 | 311.74 | 55.32 | 82.3% |
| 蜘蛛，仅方言词、大地点 | 281.83 | 47.92 | 83.0% |
| 蜘蛛，仅标准词、22 地点 | 21.80 | 110.72 | **变慢约 5.1 倍** |

建议推进：仅对经过验证的“带普通地点文本 + 涉及方言词等非覆盖字段”的路径扩展计划选择；保留仅标准词的覆盖索引路径。还需补齐音标、详细信息、通配符、范围非常宽、简繁重叠和高命中词；本轮数据不足以直接把这些形状归入同一规则。

全域标准词+方言词等非覆盖内容搜索，当前代码已经有 `NOT INDEXED` 计划，不应再次把它包装成新改动。

### Python 分组：按需升级集合/字典的独立原型

本地完整计算产生 39,965 个归一词组，其中 31,606 组只有一个地点，38,378 组只有一种词形。当前却给每组都创建地点 set 和词形计数字典。

候选用单个字符串保存第一地点/词形，出现第二个不同值时才升级为 set/dict。仍保留每种词形的精确次数、地点去重、代表词排序和完整返回，不新增结果缓存。

宿主机本地 Python 测试，9 次交替计时，内存单独用 tracemalloc 测量；**这一部分没有使用 2 CPU 容器，不能与前面 SQL 数字混算。** 第二轮结果：

| 条件 | 当前 ms | 紧凑分组 ms | Python 分配峰值，当前 → 候选 |
|---|---:|---:|---|
| 无 q、limit=1000 | 133.47 | 116.98 | 31.12 → 17.74 MiB |
| 无 q、完整返回 39,965 组 | 207.89 | 186.40 | 38.16 → 24.62 MiB |
| 皮、完整返回 949 组 | 21.30 | 21.06 | 0.76 → 0.42 MiB |
| 太陽、完整返回 88 组 | 37.27 | 37.35 | 0.06 → 0.04 MiB |

第一轮无 q、limit=1000 为 140.33 → 122.24 ms，完整返回为 210.41 → 179.98 ms，方向一致但存在波动。结论是大分组计算的提速约一成，减少 Python 分配更明显；小命中搜索主要耗在扫描，此改法收益很小。

5 种条件逐字段比较通过，包含完整返回、简繁匹配、多地点。这里的分配峰值不含全部 SQLite/OpenCC 原生内存，不是进程 RSS；未来不同词形增加时仍然线性增长，原型没有消除算法的这个边界。落地前需补充人工构造的多词形计数并列、多个地点重复、空地点和排序边界。

## 5. map-points：先内容扫描再分组，对部分条件有效

“先聚合词条，再 JOIN 地点元数据”已经存在。本轮候选是在内部聚合中使用顺序表扫描，避免为了身份分组而遍历非覆盖索引。

47.5 万条、完整地图结果：

| 条件 | 当前 ms | 顺序扫描候选 ms | 耗时下降 |
|---|---:|---:|---:|
| 蜘蛛，仅标准词，全域 | 37.08 | 28.73 | 22.5% |
| 蜘蛛，标准词+方言词，全域 | 52.88 | 44.52 | 15.8% |
| 蜘蛛，仅标准词，22 地点 | 112.54 | 30.19 | 73.2% |
| 皮，标准词+方言词，22 地点 | 134.48 | 46.34 | 65.5% |
| 无命中词，标准词+方言词，地点无命中 | 30.72 | 68.11 | **变慢约 2.2 倍** |
| q=%，单地点 | 37.90 | 54.47 | **变慢约 44%** |

因此候选不能无条件使用 `NOT INDEXED`。优先考虑无地点范围的普通关键词；宽地点范围的收益更大，但需要能低成本判断范围确实较宽。小范围、无地点命中、精确省/市/分区及通配符继续保留现有计划。判断不能单看“选了 22 个地点”，因为它们在生产可能只覆盖很小比例。

保持总词条数、无坐标省略计数、地点身份、结果排序完全一致。关联地点元数据仍需 user_id+location_name，不能为了提速只按名称 JOIN，避免不同用户同名地点混淆。

## 6. 推荐落地顺序与 2c2g 约束

1. **entries 的小结果首页试点**：先补计数缓存命中/未命中、零结果、页满/不足、并发写入的一致性验证；限定适用形状，拒绝已测出的覆盖索引退化。目标是少扫描一次，而不是增加预热或扩大缓存。
2. **standard-words 的地点范围 + 非覆盖字段计划选择**：本轮 SQL 收益最明确。先覆盖标准词+方言词与方言词单字段；不能扩大到仅标准词，也不要把所有多个地点都强制为该计划。
3. **standard-words 紧凑分组**：小幅提速并减少高基数对象分配，直接针对 2 GB 约束；保持现有单昂贵任务槽，不引入额外并行计算。
4. **map-points 的普通全域关键词计划**：收益中等且边界较清楚；宽地点范围先补范围选择性实验再纳入。
5. **import 与 sql/query 分阶段观察**：导入当前已有分批写入、有限日志快照和单写者，不能重复建议；下一步定位解析、验证、事务、资源等待的占比。SQL POST 需获取脱敏形状后再做特定计划，不能凭 URL 推断。

同时补低开销阶段计时：精确 COUNT、页 SQL、聚合 SQL、Python 归一、资源槽等待、编码输出。只在慢请求汇总记录，不保存完整上传内容、token 或请求正文。这样才能解释为什么同一模式有 0.1 秒和 8 秒的生产样本。

生产历史快照已证明有内存不足杀进程事件；修好计算锁不等于证明 OOM 已消失。多个 worker、其他接口、数据库和 Redis 共享 2 GB，本轮顺序 SQL 实验不能排除这些整机因素，也不能证明每个慢请求都由它们引起。

上述候选不新增后台任务、线程或常驻服务；内存仍随实际分组/返回数据增长，不承诺无限结果下恒定内存。继续保留既有有界并发，不做自动重试来放大扫描和写锁压力；离线实验发现退化则保留旧路径。接口参数、精确总数、简繁语义、排序和返回结构都是实施约束，前端无需为这些候选改变使用方式。

## 7. 复现与原始结果

实验脚本：

- `scripts/benchmark_vocabulary_followup.py`：在隔离模块中导出候选 SQL，检查服务结果。
- `scripts/benchmark_vocabulary_followup_replay.py`：纯标准库回放，生成本地增长库，计时、执行计划及完整结果摘要比较。
- `scripts/benchmark_vocabulary_standard_groups.py`：紧凑分组原型、完整结果比较、分开计时与分配测量。

本地原始记录位于 Git 忽略目录 `outputs/vocabulary-local-20261101/`：`jobs3.json`、`scale1.json`、`scale5.json`、`firstpage5.json`、`standard-groups.json`。计划与每轮耗时均保留在 JSON 中。输出包含本地查询文本，仅用于离线实验。

宿主机导出命令：

```sh
.venv/bin/python -m scripts.benchmark_vocabulary_followup --output outputs/vocabulary-local-20261101/jobs3.json
.venv/bin/python -m scripts.benchmark_vocabulary_standard_groups
```

容器回放需将仓库只读挂载到 `/source`，独立本地输出目录挂载到 `/work`；用 `--platform linux/arm64 --cpus 2 --memory 2g --memory-swap 2g`，运行 `/source/scripts/benchmark_vocabulary_followup_replay.py`，传入只读 `--db`、导出的 `--jobs`、新的 `--output`；`--scale 5` 会创建输出旁的本地增长库，存在时拒绝覆盖。不得在生产运行这些实验脚本。
