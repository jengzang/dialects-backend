# SQLite 通用池调整与 ORM 页缓存评估（2026-11-05）

## 已实施范围

普通 `SQLiteConnectionPool` 的缓存目标从每连接16000KiB降到2000KiB。
query、dialects、characters、yubao、villages、villages_admin、logs/auth原生统计、
yc_spoken、vocabulary原生SQL均使用这个默认值；toponyms只读池仍4096KiB，GIS仍2000KiB。
初始、溢出、异常替换连接均经过同一构建逻辑。连接数、等待时限、读写权限、事务行为不变。
characters经ATTACH使用的是另一个schema缓存，不继承main缓存；本地SQLite默认同样是-2000，增加回归检查，没有改JOIN。

本次**没有调整ORM运行策略**、连接数或任何生产服务器设置。ORM建议见下文。
此前普通池测量依据：`docs/db-cache-sweep-validation-2026-11-05.md`。

2000KiB约1.95MiB；4096KiB=4MiB；64000KiB=62.5MiB。
SQLite的`cache_size`是每连接、每schema按需使用的页缓存目标，不是预分配，也不是worker内存上限。
普通池每连接目标减少14000KiB（13.67MiB）是配置差额，不能当作必然RSS节省。

## 方法、数据安全与边界

脚本：`scripts/benchmark_orm_cache.py`；完整结果：`docs/orm-cache-results-2026-11-05.json`。

- 4个ORM数据库，2000/4096/8192/16000KiB；logs另测64000KiB。
  每组3轮，交替顺序，共51组、102个独立子进程，读写各自隔离。
- 使用当前真实SQLAlchemy模型；原始本地DB仅通过SQLite `mode=ro` + `query_only=ON`读取，
  不调用应用启动或ORM运行工厂的WAL设置。检查源文件inode/size/mtime未变；无复制数据库。
- 读取采用代表性的ORM查询形状，不调用完整HTTP/service流程。每case6次，首轮单列；
  表中查询值为各轮后5次中位数，再取3轮中位数。操作包括Session查询和对象加载，
  不含网络、Redis、鉴权、响应序列化。每条SQL设3秒进度回调截止，每子进程60秒超时。
- 写入使用临时目录新建合成数据和实际模型/索引，WAL/NORMAL；先12000行，随后20批。
  auth/logs用`bulk_save_objects`每批50并提交；诊断日志每批25且body2048字节并提交；
  vocabulary用`bulk_insert_mappings`每批512，20批共享事务后提交（与导入事务方向一致）。
  supplements采用每批10条信息的合成写入代理，不代表所有用户提交路径。
- 校验所有预算/轮次的读取标量值或实体ID签名一致；实体字段和joined关系内容未逐字段比较。
  写入校验最终行数，并测试额外插入后rollback不会增加行数。
- 同时只运行一个基准子进程、一个数据库连接；没有新增在线任务、并发、重试或常驻服务。
  仅本地测试，没有在2核2GB生产机压测。单组写入行数和对象批次有界，未设置进程RSS硬限制。
- RSS列是**阶段结束时RSS减阶段开始RSS的快照差额**，读取含SQLAlchemy对象/查询分配残留；
  写入基线在建表之后、seed之前，含seed和后续批次的分配残留。不是峰值，不是SQLite纯缓存大小，
  不能乘worker数当生产收益。操作系统文件缓存未清除，SSD/WAL/checkpoint性能不能外推生产。
- 未覆盖日志定期大DELETE/聚合维护、超大词汇上传、所有筛选组合、并发锁竞争/尾延迟。
  因此推荐是当前负载样本下的保守起点，不能宣称数学上的唯一最优值。

复测：

```sh
.venv/bin/python scripts/benchmark_orm_cache.py --data-root /path/to/local/data --output /tmp/orm-cache.json
```

## ORM建议

| ORM数据库 | 当前页缓存目标 | 建议起点（每连接） | 判断 |
|---|---|---|---|
| auth.db | 未显式设置，本地SQLite默认2000KiB | 2000KiB | 用户/最近使用查询与50条日志写入，大缓存没有明显收益 |
| supplements.db | 默认2000KiB | 2000KiB | 实际库很小，分页读取无收益，合成扩容写入也无需大缓存 |
| vocabulary.db | 默认2000KiB | 2000KiB | 分页几乎相同，模糊COUNT的大缓存仍扫描；4MiB仅在频繁导入时作为候选 |
| logs.db | 显式64000KiB | 优先2000KiB，确有ORM聚合热读时可选4096KiB | 50条关键词/25条诊断写入差异很小，没有支持62.5MiB的证据；2到4MiB聚合热读有收益 |

logs的关键词聚合在2到4MiB时约12.93→9.60ms，但这只是查询样本；
当前统计还存在单独的raw SQL池，本次已统一缩至2000KiB，不应因为这个样本给每条日志写入连接都配置大缓存。
当前合成写入RSS约3.58→12.61MiB（2MiB与62.5MiB目标），支持降低目标的方向，
不能声称生产单连接一定节省9MiB，更不能声称一定节省60.55MiB。

vocabulary在2到4MiB时512条插入批次约2.07→1.95ms，小幅收益；
单次导入还有解析、删除旧数据和最终commit等成本。为偶尔导入提升每条长期读取连接缓存不划算。
2到16MiB时模糊COUNT约28.40→28.84ms，读阶段RSS增量约3.86→20.92MiB。
优化COUNT仍应依靠查询规划、索引、结果复用/延后计算，而非单纯加大页缓存。

## ORM还有哪些改动值得做

1. **把缓存预算显式写入已有集中策略**：先auth/supplements/vocabulary明确2000KiB，
   logs从64000下调到2000（有真实热读证据再4096）。不需要把4个库合并为同一个Session/事务，
   也不需要改只读权限。此次只给建议，未应用ORM策略。
2. **限制闲置连接和峰值连接，先测占用再定数**：现有ORM已经按需创建，
   但每库每worker仍可保留5条，瞬时可到15条。`pool_status()`可查看现有占用，不开新连接。
   建议下一步记录各库checked_out峰值及超时，再测试更小的保留数/溢出上限。
   当前没有并发占用样本，不能直接认定“1条就够”；日志多个写入管道、auth鉴权和后台统计可能重叠。
   SQLAlchemy默认连接池等待是阻塞的，减少上限需要同时核对调用线程，避免事件循环排队。
3. **减少对象和长Session**：缓存不约束ORM实体、identity map、用户结果列表。
   `User.usage_summary`目前`lazy='joined'`，鉴权按User查找也会加载该用户的全部路径统计。
   可对鉴权查询单独排除不需要的关系加载，仅在统计接口加载，先验证字段/懒加载行为和查询次数。
   用户区域/自定义资料部分路径仍`.all()`；优先给返回/删除/统计增加合理界限或SQL聚合，
   避免以扩大页缓存掩盖Python对象增长。此次未改返回语义。
4. **日志维护、队列和上传另设边界**：小批写入已做Session关闭，不能简单归因于连接泄漏。
   queues内的ORM对象、诊断body、词汇解析结果/导入事务可独立占内存。
   如后续调整，沿用现有有界队列/512导入批次，不增加常驻服务/worker；
   维护DELETE需单独测锁时长和WAL增长，再决定分批与提交策略，不能用本次小批写入测试证明它安全。
5. **保留错误处理**：此次运行配置只改页缓存，无新增重试/后台任务，不改变日志现有恢复机制。
   后续如缩池，只允许有界等待、保留原事务回滚及auth落盘恢复；不要无限重试或池耗尽后另开无界连接。

2000KiB下，5条连接的页缓存目标合计约9.77MiB，15条约29.30MiB；
现有logs64000KiB下对应312.5/937.5MiB。这只是全部连接均达到目标时的预算加总，
不是实际常驻/峰值RSS，而且还未包括其他库、TEMP、Python对象、上传缓冲和worker基线。
