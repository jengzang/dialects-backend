# Vocabulary 分区筛选性能评估（2026-10-20）

实现完成：四个查询支持完整路径任意层级筛选，新增词表分区树、词条分区返回、地点选项分区集合；缓存正确依赖地点版本。未增加索引、线程池、worker、预热组合或生产服务。

## 方法与可复现性

- 对照基线 `9c4b76a`，用 `git show` 在独立模块加载旧查询/缓存代码，新旧使用同一个 SQLite backup 快照。源库仅以 mode=ro 打开，所有测试和实验写入快照或临时数据库。
- 快照 95,003 条 entries、29 条 locations，SHA-256 `978b50088330716db5dc1aced97d81ebb11ce2637f694fecff509beddb952656`。
- macOS 26.3.1 ARM64，Python 3.12.13，SQLite 3.53.2。Redis 7 Alpine 在本机 Docker 内运行，测试容器上限 0.25 CPU / 64 MiB，Redis maxmemory 32 MiB；只操作随机命名空间，不清空其他数据。测试容器不属于生产架构。
- 每个服务场景先预热 2 次，再取 21 次 wall/CPU 样本；同一既有场景的新旧版本交替运行，串行并发 1。计时包括 Session 获取及数据库服务函数，不包括 HTTP 序列化、网络和限流。
- 缓存测真实 `VocabularyCache.acall`：先 miss，再预热 3 次、测 50 次 hit，包含线程切换、Redis 往返和 JSON 解码，未含 HTTP 响应处理。新旧缓存命中按各自批次测量，不能把亚毫秒差异全部归因于改动。
- Python 分配峰值用独立 tracemalloc 查询；原生/SQLite 内存另用全新子进程记录 `ru_maxrss`，报告峰值相对建立连接后的增长。RSS 单样本，包含首次读取页面和初始化，不等于稳定驻留占用或生产 worker 总内存。
- 额外记录 EXPLAIN QUERY PLAN、每 1000 条 SQLite VM 指令的进度回调和独立子进程块 I/O 计数。VM 数为粗粒度计数，低于 1000 可记录为 0，不能解释为无工作。
- 查询使用温热 OS 页缓存；没有模拟掉电、冷磁盘、生产 CPU 或并发负载。开发机延迟不外推为 2 核 2GB 服务器承诺。

可复现脚本：

```bash
.venv/bin/python scripts/benchmark_vocabulary_partitions.py \
  --baseline 9c4b76a --repetitions 21 \
  --redis-url redis://127.0.0.1:16379/0 \
  --output benchmark/vocabulary-partitions-final-measured.json
```

原始样本、查询计划及内存数据保存在 [结果 JSON](2026-10-20-vocabulary-partitions-results.json)。脚本使用当前源库创建新快照，所以以后数据变化时结果也会变化。

## 查询形态与数据库 I/O

最初直接在词条 JOIN 后判断路径，导致相同地点路径按每条词条重复求值。探索性测量和执行计划确认该问题，最终采用：

```sql
(e.user_id, e.location_name) IN (
  SELECT p.user_id, p.location_name
  FROM vocabulary_locations p
  WHERE p.yindian_region = ?
     OR substr(p.yindian_region, 1, ?) = ?
)
```

保留完整复合身份，避免不同用户同名地点串选。前缀计算在小地点表上完成，词条复用现有 `(user_id, location_name)` 索引。

- entries 分区 count 走身份覆盖索引，先 count 再取页面；空范围直接返回。非空页面仍由 SQLite 根据 ORDER BY 选择计划。
- standard-words 只在传分区时使用现有身份索引，避免为少量地点扫描全库标准词索引；之后 GROUP BY 可使用临时 B-tree。无分区继续走原标准词覆盖索引，不新增持久索引的写放大。
- map-points 先聚合窄的地点身份/count/min，再获取地点元数据，避免临时分组携带所有宽字段。若关键词/行政区条件需要地点字段，内层仍正确 JOIN。
- 树只读 DISTINCT 路径，地点选项只扫地点表，不扫描 95,003 条词条。

SQLite VM 指令粗粒度计数：未筛选 standard-words 新旧约 197 万；根分区约 177 万、叶子约 29.3 万；map-points 未筛选约 180.7 万、根约 122.2 万、叶子约 17.5 万；50 路径根仅比单根额外约 4000–10000 条指令。分区条件的重复成本已被移到地点表。

所有独立内存/I/O 探针的 OS 输入/输出块计数均为 0，表明本次温热页缓存下该计数器未观察到物理 I/O；不能据此声称生产查询不读盘。新分组计划可能使用 SQLite 临时存储，数据增大后可能产生临时磁盘 I/O，需在生产 SQLite 版本和负载下复测。

首屏 entries 的 UTF-8 JSON 从 10,495 增到 14,195 字节；location-options 从 3,743 增到 8,251 字节。五份默认搜索结果的实测 Redis MEMORY USAGE 合计从 158,952 增到 167,208 字节，增加 8,256 字节；两份 SQL count 未改变，未计入上述五份合计。分区树本次额外按需键占 2,856 字节。

新增组合仍受原按需 128 键、每结果 128 KiB、TTL 1 小时约束；超过准入大小正常返回但不缓存。树内存随不同路径段数增长，地点选项集合随地点/不同分区值增长。默认预热仍为七项，不预热全部分区组合。

## 地点修改后的预热成本

正确性要求所有 search 结果依赖地点版本；地点分区、标签、行政区变化后，不能继续使用旧标准词计数或词条分区。因此仅修改地点时，也会重建默认搜索结果。这是本次最明确的额外后台成本。

以下使用实际串行 warm_once（保留每项 100 ms 暂停），每种情况 3 次，报告中位数；不包含写入后通知的 1 秒合并窗口。

| 失效来源 | 旧 wall | 新 wall | 旧 CPU | 新 CPU |
| --- | ---: | ---: | ---: | ---: |
| entries 变更 | 965.3 ms | 973.9 ms | 217.0 ms | 222.2 ms |
| 仅 locations 变更 | 797.5 ms | 971.8 ms | 57.9 ms | 217.4 ms |

预热并发仍为每库跨 worker 一份 Redis 租约、逐项执行，标准词 100 复用同版本 1000 的聚合。地点连续写入仍合并通知；计算中版本变化时拒绝旧结果入缓存。在线冷查询使用现有线程池，同键合并计算，不新增线程或并行分区查询；不同键并发及 Redis 故障回源仍受现有部署 worker/线程配置影响，未在此测量中验证全局资源上限。普通查询不新增失败重试；沿用缓存等待 30 秒返回 503、Redis 熔断与后台预热退避。

## 验证结果与结论

新功能、缓存、生命周期和公共路径测试在隔离 SQLite/真实隔离 Redis 上验证。独立审阅另做 48 组轻量语义对照：优化查询与直接谓词的筛选、计数、排序一致。审阅指出的 NUL 路径边界已补测试并拒绝。

完整词表/公共路径回归：289 通过、8 失败。8 项已用 `9c4b76a` 旧 query/routes 模块复现，均为既有失败，未修改其行为或放宽断言：

- 既有 location-options 限流配置与测试预期不一致。
- DOCX 空白解析测试预期不一致。
- 两个 entries 测试仍预期旧顺序（当前代码早已 id DESC）。
- map-points 测试仍访问已不存在的 location_label。
- location-options 测试仍预期斜杠标签（当前代码早已用中点）。
- 两个上传路由测试仍 monkeypatch 已移除的 routes.redis_client。

结论：在此数据规模下，新增路径筛选不需要新索引或服务；既有未筛选主查询中位开销接近原值，选择性分区显著减少聚合工作，大范围分区仍需按冷查询预算处理。新增主要固定成本为响应字段/缓存大小，以及地点修改后额外标准词预热。生产验收还应在实际 2 核 2GB 主机、实际 SQLite 版本下观察不同冷键并发、Redis 故障回源和写入期间的在线 p95/RSS/临时 I/O；本报告未验证这些生产场景。
