## 3. 实际代码为什么需要做这些工作

### standard-words

SQL 按 `(standard_word, location_name)` 分组，再由 Python 做简繁归一、同词合并、地点去重、变体计数，最后按地点数、词条数和代表写法选 top K。

- `limit=1000` 限制的是最终输出，不是 SQL 输入。提前对 SQL 分组 LIMIT 1000 会改变合并结果和全局排名。
- `total` 是归一后的标准词组数，不是 entries 的匹配词条数。
- 全库无 q 时，本地副本 SQL 输出 421746 条分组记录，Python 合并成 119360 个标准词组，处理 122514 个连续写法段。即使只返回 1000 项，这些合并仍要完成。
- 中午、窄的 SQL 输出分别只有 189 / 203 条分组记录，归一后分别 36 / 64 组。它们不是因为输出 1000 项而慢，实际远没达到 1000 项。

### map-points

先扫描匹配词条，按 `(user_id, location_name)` 计算 COUNT 和 MIN(id)，再取地点元数据与坐标。结果只有几十到一百多个点，也仍要检查全库候选词条。

- 哈欠 / 吃饭 / 窄分别命中 134 / 178 / 245 条词条，得到 111 / 59 / 134 个聚合地点行。
- 当前路径只抽样最多 128 条近期记录选择执行计划；样本不决定业务结果。主查询仍完整扫描和聚合。
- 没有一个可以独立拆走的“分页总数 COUNT”。COUNT 本身用于每个地点的点大小和总词条数，延迟它会改变地图响应语义。
- 返回点数少，不等于查询只读取少量词条。

### 当前索引选择

全库默认内容字段搜索是 `%关键词%`，普通 B-tree 不能直接定位任意子串。现有覆盖分组索引缺少另一搜索字段；按非覆盖索引逐条回表可能更慢，所以当前部分路径显式使用 `NOT INDEXED`，避免随机回表。

这比错误回表计划好，但仍在扫描宽词条表。**下一步可以让“必须扫描”的数据更窄，而不是简单撤销 NOT INDEXED，或继续堆叠扫描预算。**

## 4. 本地分段测量

### 方法与限制

复用此前生产只读副本：529032 条词条、167 个地点。生产数据库和 WAL 大小、秒级修改时间与此前副本采集元数据一致；没有重新复制大库，也没有重新计算生产全文件哈希，因此不声称逐字节证明当前生产内容完全相同。

- 所有测试在本地 Docker 内，2 CPU、256 MiB 上限、无网络。快照只读挂载。
- 服务测试使用冻结的部署源码；11 种条件，每种 7 次，SQL 执行、游标读取、Python 剩余、归一、top K、缓存编码分别计时。每种条件完整响应摘要在各轮一致。
- 服务镜像为 AMD64，在 ARM Mac 上模拟执行。因此这些绝对时间不是生产延迟预测。

## 5. 两种优化假设的实测

### 5.1 仅增加 instr 必要条件：收益不足

对本次中文普通字面量，在保留原 LIKE 的同时增加 instr 必要条件；7 个有 q 的全库条件均做 7 轮交替对照，结果摘要一致。原生 SQL 中位数大致只改善 0–5%，map“人”还有轻微回退。它没有减少被扫描的数据页，不应作为这次主要方案。

这只验证了这些中文条件，不能扩大解释为任意大小写、通配符、转义字符和多字段语义已经通过验证。

### 5.2 窄覆盖索引：值得优先推进

仅在一次性本地数据库副本上建立实验索引：

```sql
CREATE INDEX experimental_search_cover ON vocabulary_entries(
    standard_word, location_name, local_expression, user_id
);
```

`id` 是当前表的 INTEGER PRIMARY KEY，可从二级索引自带 rowid 取得。此索引同时覆盖默认搜索字段、标准词分组字段、地图身份字段和 MIN(id)，减少读宽表。它没有让 `%q%` 变成索引定位；执行计划仍显示覆盖索引扫描。

实验只替换无范围、默认内容字段聚合的主查询来源；保留 map 的近期样本、过滤条件、简繁变体、完整分组及排序。基线和覆盖索引在同一个实验副本中交替运行，每种 7 次。逐批读取的完整 SQL 结果摘要一致。

| 条件 | 当前 SQL 中位数 | 覆盖索引 SQL 中位数 | 减少 |
| --- | ---: | ---: | ---: |
| standard 中午 | 341.05 ms | 38.38 ms | 88.7% |
| standard 窄 | 353.91 ms | 38.94 ms | 89.0% |
| map 哈欠 | 336.39 ms | 39.90 ms | 88.1% |
| map 吃饭 | 362.26 ms | 63.99 ms | 82.3% |
| map 窄 | 334.17 ms | 39.52 ms | 88.2% |
| standard 人 | 351.77 ms | 43.05 ms | 87.8% |
| map 人 | 338.39 ms | 42.85 ms | 87.3% |

本地索引带来的文件增长为 **23969792 字节，约 22.86 MiB**；本地建索引用时约 1.38 秒，整个实验进程在建索引阶段峰值 RSS 23380 KiB。均不是生产建索引耗时、内存或上线延迟保证。磁盘增长也不等于新增同等大小的常驻内存。

重要限制：

1. 当前代码显式 `NOT INDEXED`，只加索引不会让这些路径自动受益；需要同时调整经过验证的查询计划分支。
2. 不把该索引强制应用到所有搜索。无 q 已有较窄的专用索引；地点范围、分区、其他字段、通配符、极高命中、不同用户同名地点等仍需专项验证。
3. 覆盖索引增加写入和导入维护成本，尚未测量这些开销；没有在生产创建。
4. 单字符“窄”也受益，因为关键是少读宽数据页，不要求关键词至少两个字。
5. 本地 SQL 减少 82–89% 不代表线上 8 秒必然变为 1 秒；必须用线上分段指标验收。

## 6. 建议实施顺序和验收

### 第一项：覆盖索引＋限定计划分支，同时补充分段指标

优先处理已确认的无范围 definition/headword 全库聚合，包括单字段和两字段组合。先完成本地正确性矩阵、写入/导入资源测试，再设计迁移。生产当前仅 143 MiB 可用内存，不在服务启动时由多个 worker 自动竞争建索引，不在本次只读会话执行迁移。

- 不增加 worker、线程池容量或服务。复用现有全机 heavy=2、standard expensive=1 的上限与同请求合并。
- 仅改变允许条件下的扫描来源，不缓存全量 ID 集合，不引入每请求常驻任务。
- 新索引未就绪时走现有正确路径，并记录所选计划；避免缺索引时 INDEXED BY 直接让 API 失败。
- 验收：完整响应、标准词变体/排名/total、地点计数、缺坐标计数、同名地点不同 user、NULL、简繁、空结果、单字符、通配符、字段组合、窄范围和高命中；现有快路径不能退化。写入后缓存失效与索引更新也要验证。
- 指标最少包括缓存 hit/miss/bypass、同键等待、资源槽等待、线程派发等待、SQL execute/fetch、Python 合并、编码/响应阶段、计划名、worker PID 和数据库 revision。已有慢请求阈值触发采样即可，限制日志量，不记录完整结果和全部候选 ID。
- 本次不增加后台任务、自动重试或新的内存缓存。失败沿用现有受控错误路径；索引缺失降级一次，不循环重跑整个重查询。

### 第二项：无 q standard-words 的全量合并

继续使用已有按 revision 失效的默认结果预热缓存，先识别那条无 q 3.306 秒请求是否落在冷启动、失效、缓存故障或等待上。不要因为一次慢请求增加每个 worker 的常驻全量词组缓存。

若冷计算仍影响体验，再评估导入/写入时维护规范化 key，或离线生成默认聚合结果，以减少每次 OpenCC 与地点合并。该方案涉及写入一致性，不能只把 DISTINCT 标准词数当归一后总数；也不能拿无 q 预聚合结果代替任意 q 的筛选后聚合。

按当前语义，简单调低返回 limit 对扫描和全量合并帮助有限。此项与覆盖索引解决的是不同成本。

### 第三项：前端去掉不必要的串行等待

本地前端 `VocabularyViewPage.vue` 的 `refreshVocabularyMapData()` 明确先 `await loadVocabularyStandardWords()`，然后才调用 `loadVocabularyMapPoints()`。11-04“窄”两条请求也呈串行：standard 完成后约 38 ms 才开始 map；从 standard 发起到 map 完成合计约 **17.39 秒**。

建议先考虑“无已选标准词时优先加载地图，标准词菜单按需加载”。已选标准词时保留必要的选项校验依赖，因为 standard 加载会清理失效选择。这样改善等待链，并减少用户不打开菜单时的计算。不要直接把两条重查询全部并行作为默认方案；2C2G 上同时全库扫描会竞争资源。

此项改善首屏体验，不降低一次地图聚合本身的 SQL 成本。应在后端扫描优化后评估，前端可以保持最小改动。

### 暂缓的方向

- 把 entries 的后台 COUNT 直接复用给聚合：响应语义不匹配。
- 自动为每个搜索词启动后台全量聚合：在内存紧张时额外消耗资源。
- 无界缓存命中 ID、不断增加缓存容量或 worker：会放大内存风险。
- 直接引入通用全文服务或对子串建立大规模倒排：需额外评估单字、简繁、LIKE 通配符、导入成本和容量；本次覆盖索引已有明确收益，应先做较小改变。

## 7. OOM 与本次慢请求的关系

OOM 仍在发生。11-04 最新观察到 15:08:30、15:44:34、15:54:34、17:38:39 的内核 `Out of memory: Killed process … (gunicorn)`，不是仅凭 SIGKILL 推断。对应匿名 RSS 约 471、513、465、465 MiB。

15:39 的 map 慢请求约在 15:39:37 完成，距离下一次 15:44:34 OOM 约五分钟，没有证据说该请求在执行中被 OOM 杀死，也不能认定它单独导致后续 OOM。内存持续紧张可能影响 I/O 和调度，但现有日志不足以定量解释这次 8–9 秒。

17:38:39 OOM 出现在本次只读调查期间，触发分配的进程名为 `python3.7`。成功采集使用的是容器 Python 3.12，采集进程峰值约 12.75 MiB；这些事实不足以证明调查导致或完全没有影响该次 OOM。后续重查询均留在本地，没有继续在生产压测。17:40:20 的可用内存约 300 MiB，是 kill 后的状态，不能当作压力已经解决。

因此，需要并行看待两个结论：聚合扫描存在已实测的优化空间；整机内存问题仍未解决，不能靠本次 SQL 实验宣称 OOM 已修复。
