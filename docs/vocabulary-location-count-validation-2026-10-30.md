# 无关键词地点计数优化验证

## 修改范围与语义

仅优化 `/api/vocabulary/search/entries` 中 q 为空或空白、带 locations，且没有 standard_words、省、市、分区条件的精确计数。分页数据 SQL、响应格式、排序、精确总数、简繁匹配规则和所有结果的可访问性保持不变。其他查询分支保持原路径，前端无需改动。

使用已有地点名索引的 MIN 范围查找，跳过重复词条，枚举不同地点名。计数分成互不重叠的两部分：名称直接匹配的词条；地点元信息匹配、但名称没有直接匹配的词条。第二部分仍通过 `(user_id, location_name)` 关联，避免串入其他用户的同名地点。第一部分保留缺少地点资料的词条。

单条 SQL 的递归中间关系最多枚举 257 个地点名；超过 256 个时，CASE 惰性执行原计数。这是算法选择边界，不是数据返回上限。组合谓词参数超过 400 时直接保留原 SQL，避免在一个 SQL 内复制原查询条件后触及旧 SQLite 参数数及表达式深度限制。没有新增索引、服务、缓存或应用层磁盘聚合。

## 测量环境与方法

Docker 原生 ARM64 Linux，SQLite 3.46.1。核验 cgroup：`cpu.max=200000 100000`、`memory.max=2147483648`、`memory.swap.max=0`。这是总计 2 CPU 时间配额，并非与生产 CPU 型号、磁盘性能完全一致。

脚本只用标准库，从当前 query.py 提取实际 SQL 构建函数，在容器内复制离线数据库。当前样本 95,003 条；增长样本 950,030 条，通过复制词条和地点并增加用户身份得到，地点名集合不变。额外构造 256/257 个地点、每地点 1,000 条，以及 10,000 个地点、每地点 1 条的边界样本。

每个场景旧新 SQL 交替测量，预跑两轮后取九轮中位数，逐轮核对精确总数。使用热缓存，未测生产磁盘冷读、完整 HTTP、Redis、在线并发和后台任务。因此数字只说明这些数据分布下的计数 SQL 成本，不能解释生产 5–6 秒请求的全部时间，也不能直接推算端到端提速。

## 资源与失败处理

复用现有请求准入/线程池边界，不增加并行度、worker 或后台任务。名称枚举中间关系上限 257 个；地点元信息的匹配关系仍随地点表规模增长，已有索引计数仍需遍历匹配的索引项，不是常数时间。所有中间关系在 SQLite 内计算，不在 Python 装载全部词条。

容器运行含数据准备的进程峰值 RSS 为 35,976 KiB，memory.events 中 OOM、OOM kill、max 均为零；这不是完整应用的内存需求或相对旧查询的内存增量。单请求串行测量没有触发 CPU 限流，不能据此推断并发吞吐量。失败沿用现有异常处理和缓存降级，不新增重试。

## 回归

五项排除测试已用 HEAD 的旧 query.py 在内存中替换后重跑，仍全部失败，涉及 DOCX 空白解析和地点标签分隔符预期：
