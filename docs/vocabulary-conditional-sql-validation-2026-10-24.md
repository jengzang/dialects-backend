# 按搜索条件选择 SQL：实施与验证

## 本次实际改动

用户批准前两项查询优化，不实施简繁缓存扩容或缓存编码优化。现有响应缓存和 8192 项归一缓存保持原样。

- standard-words：仅当 q 非空、没有省/市/地区/地点范围、不含 location 搜索字段、不含 `%`/`_`，且搜索涉及 headword/pronunciation/detail 时，使用词条顺序扫描后分组。标准词 definition 单字段、无关键词、地区身份索引、省市组合及通配符保留原路径。
- 地点文本：仅当没有省、市、地区约束时，先在地点表按文本匹配身份，再用于筛选词条。保留词条字段及 e.location_name 的 OR 分支；身份包含 user_id，保留跨用户同名地点和孤立词条。能够匹配空串的全 `%` 模式保留旧 LEFT JOIN 路径。
- 公共过滤器也供 map-items 使用，完整结果等价性测试覆盖该接口；主要耗时基准针对 entries、standard-words、map-points。
- 标准词搜索字段和地点参数先规范化为列表，支持一次性 Iterable，不因判定查询路径而重复消费。

前端、接口参数、响应 schema、排序、计数及现有 limit/分页语义未修改。不新增索引、正式数据列、常驻服务、线程或重试。不新增应用临时聚合/响应文件。

## 实测方法

直接比较本次修改前的 query.py 快照与最终业务实现，基线已经包含前一轮 entries 的计数优先及分页后 JOIN，避免重复计算此前收益。

macOS arm64，Python 3.12.13，SQLite 3.53.2，SQLite 页缓存预热；每个端点/条件/版本交替执行 5 轮，报告中位数。计时包含服务函数 SQL、Python 聚合和 dataclass 构建，不含 Redis、HTTP 编码、网络或前端。

- 当前库：95,003 条，29 个地点身份。
- 独立增长夹具：950,030 条，290 个地点身份，索引不变；词形及地点名称没有增加，不能冒充不同词形增长 10 倍的测试。
- 每个规模 80 个端点/条件组合，共 160 个。包括默认、单字、简繁、无命中、各搜索字段、混合地点 OR、省市大小范围/组合、多地点、地区大小范围/多选、关键词叠加地点与地区、省市矛盾、通配符、精确选词和地点深分页。
- 每次比较完整返回字段、数组顺序、全部统计及页码；标准词额外比较无搜索全部 39,965 组，以及搜索“人”全部 8,129 组。没有新加截断。

复现脚本为 `scripts/benchmark_vocabulary_conditional_sql.py`，需要一份修改前 query.py 文件。实施时保存为 `/tmp/vocabulary-query-before-conditional-sql.py`：

```bash
_RUN_TYPE=MINE .venv/bin/python scripts/benchmark_vocabulary_conditional_sql.py \
  --baseline /tmp/vocabulary-query-before-conditional-sql.py \
  --scale 10 --rounds 5 --output /tmp/conditional-sql-growth.json
```

输出包括原始每轮耗时、EXPLAIN、全部结果摘要、基线 SHA-256。原数据库只读；实验增长库自动清理，不是业务运行时落盘方案。

## 最终实现的主要结果

单位 ms，百分比为耗时减少。

| 接口 / 条件 | 9.5 万：原 → 新 | 减少 | 95 万：原 → 新 | 减少 |
|---|---:|---:|---:|---:|
| standard-words 默认字段“什么” | 78.492 → 37.380 | 52.4% | 898.205 → 368.677 | 59.0% |
| standard-words 默认字段无命中 | 77.800 → 20.257 | 74.0% | 755.985 → 202.987 | 73.1% |
| standard-words 备注“常用” | 51.350 → 11.064 | 78.5% | 732.793 → 113.416 | 84.5% |
| standard-words 搜“人”全部 8,129 组 | 83.691 → 44.724 | 46.6% | 766.806 → 244.046 | 68.2% |
| entries 地点字段“广州” | 42.259 → 7.831 | 81.5% | 386.739 → 74.003 | 80.9% |
| entries 多地点文本 | 28.035 → 6.388 | 77.2% | 248.915 → 58.209 | 76.6% |
| map-points 地点字段“广州” | 40.877 → 8.629 | 78.9% | 421.752 → 91.494 | 78.3% |
| map-points 多地点文本 | 25.903 → 7.765 | 70.0% | 266.414 → 77.003 | 71.1% |

省/市/地区约束组合在两个规模中均验证生成的原/新 SQL 逐字相同，避免原型中统一替换造成的大幅回退。

没有普遍提速承诺，部分场景没有收益或略慢：

- 无搜索全量标准词：当前库 221.758 → 222.195 ms，增长库 262.069 → 266.025 ms；这条路径没有新优化。
- standard-words 关键词+地点：当前库 81.187 → 87.908 ms，约慢 8.3%；增长库 900.237 → 896.011 ms，基本不变。
- entries 精确选词+地点：当前库 0.131 → 0.157 ms，增加约 0.027 ms；增长库 0.563 → 0.471 ms。地点子查询对极小候选集合可能没有收益，不能认为始终更快。
- 普通 entries、map-points 多字段搜索仍扫描候选记录；本次主要优化它们的地点文本条件。

## 资源、并发与失败

沿用既有全机 2 个 heavy 槽；standard-words 等昂贵作业仍额外受 1 个 expensive 槽限制。本次不改变 8 个准入等待名额、30 秒准入等待或已接收查询的执行时限。没有新增自动重试。

地点匹配由 SQLite 子查询执行，没有在 Python 中加载全量地点清单；SQLite 自身可能物化与匹配地点数相关的身份集合。标准词顺序扫描后的分组排序可能增加临时内存或磁盘 I/O，具体受 SQLite 配置和命中数量影响。本次没有测进程 RSS 或临时 I/O，不能承诺固定内存上限；原有 Python 分组字典仍随归一词组/地点增长。没有以增加常驻缓存换取收益。

异常、事务和缓存失效处理沿用既有路径。新地点计数 SQL 使用现有按完整 SQL/参数的缓存键，地点与词条修订依赖不变。没有新增返回数量限制或改变无结果语义。

## 回归与审查

- 新增条件 SQL 用例 93 项；与现有查询资源用例合计 120 项通过，包含 NULL、孤立词条、混合 OR、简繁、通配符、生成器和全量排序。
- 独立审查未发现阻塞问题；另外用修改前快照对四个端点做了 1536 次完整结果比较，全部一致。
- 完整 vocabulary 测试排除 6 项已在旧基线复现的失败后：311 passed、41 skipped、6 deselected。跳过项包含需要本地隔离 Redis 的集成测试；未将跳过项算作通过。
- 6 项旧失败为限流配置、DOCX 空白解析、条目旧排序/简繁顺序、地图旧字段、地点标签旧分隔符，没有为通过测试修改既有产品语义。

这些是本机服务层测试，不是生产 2 核 2 GB 的延迟/吞吐预测。部署后仍应使用相同条件观察实际延迟及 SQLite 临时排序的资源成本。
