# 词表预热与在线查询协调修正

用户确认：只有 standard-words 使用词表专用重查询名额，其他查询不受该单独名额限制；预热结果未就绪时在线请求可正常查库。直接在 dev 修改，保留 2 核 2 GB 服务器的既有总数据库并发上限。

实施步骤：

1. 先复现三个问题：entries/map-items 在线请求被同 key 预热锁阻塞；map-items 被错误计入专用 expensive 槽；启动等待预热导致其他 worker 尚未 ready。
2. 在线计算继续使用 compute 锁合并相同请求；预热改用独立 prewarm-compute 锁，并检查已有在线计算，繁忙时让出。保留同库全局 warm-lock，跨 worker 同时只有一份逐项预热。预热与在线可能重复计算一份结果，但仍受全机两个共享 heavy 槽约束。
3. 在线和预热只有 standard-words 标记 expensive；map-items、entries 等不再使用该额外单名额，写入槽和全局数据库名额不变。standard-words 在线请求仍可能等待正在执行的标准词查询，这是用户保留的单名额约束。
4. 主应用生命周期只注册后台调度器，不等待首次预热完成；其他 worker 立即具备接请求条件。所有 worker 仍复用现有事件循环和线程池，没有固定独占预热 worker，也没有新增进程。
5. 使用真实隔离 Redis 验证后台未完成时在线能独立返回、同库预热不重叠、在线相同查询仍合并、版本切换不能写回旧结果、取消后释放租约，以及启动/停服正确清理任务。
6. 更新 API 行为说明，执行相关回归并记录已有失败；审查后只提交本次文件，关闭临时 Redis。

资源边界：总受控数据库任务仍为两个，后台预热每库最多一个；不增加线程/worker配额。标准词单名额、写入单名额、最多八个资源等待名额和30秒准入预算保留。后台与在线分离锁不能消除资源饱和时的等待，也不能中断已运行的 SQLite；不得承诺生产响应耗时。

验证结果：新增七项真实 Redis 用例覆盖后台未完成时 entries/map-items 在线独立返回、第二份预热不进入、以及五种查询在在线和预热两条路径中只有 standard-words 申请 expensive 槽；生命周期测试确认后台未完成时启动函数即可返回。相关回归91项通过，独立审查通过；扩大缓存/写入回归为124项通过、4项已知旧 locations 规则断言失败，与本次锁/调度修改无关。测试仅使用临时容器和随机 Redis namespace，不清空其他缓存。
