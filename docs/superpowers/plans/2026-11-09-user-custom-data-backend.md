# 用户自定义数据安全保存：后端实施计划

> 执行方式：采用 executing-plans 按任务执行，每个任务先写关键失败用例，再实现和验证；本文件仅为计划，不授权部署。前端配套计划见同目录 `2026-11-09-user-custom-data-frontend.md`。任务均用复选框追踪。

**Goal:** 消除用户批量编辑先删后建造成的数据丢失，统一 ID 操作，提供原子保存、可控重试和冲突检测。

**Architecture:** 复用 supplements SQLite 与现有 SQLAlchemy Session。路由负责认证和协议，用户数据写服务负责整批校验、事务和结果；前端不拼装多个写请求模拟事务。新增接口与旧接口并存，分阶段发布。

**Tech Stack:** FastAPI、Pydantic、SQLAlchemy、SQLite WAL、unittest/pytest；不新增常驻服务或 worker。

**状态：** 2026-11-09 用户已批准实施，核心 A/B/C 已实现；验证结果、实现调整和未执行的环境验收见 `../../user-custom-safety-verification-2026-11-09.md`。以下复选框保留原计划明细，不作为线上部署完成的声明。

## 1. 方案选择与范围

| 方案 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| 仅加前端校验、限制数量 | 修改少 | 删除成功后创建失败仍然丢数据 | 不能作为最终修复 |
| ID 批量更新、严格删除，再提供地图事务保存 | 能分批上线，复用数据库和现有页面 | 需前后端联动 | 采用 |
| 全部重写为新数据平台或引入消息队列 | 可重新设计 | 成本和服务器负担超出本问题 | 不采用 |

阶段 A 为可独立交付的紧急修复；阶段 B 解决地图保存和重复新增；阶段 C 解决过期编辑覆盖及时间协议。阶段 A、B 不宣称已经防止并发覆盖。

非目标：恢复已经丢失的历史数据、改变全球用户显示时区、重写管理后台、删除旧客户端协议、修改无关查询或增加进程。

## 2. 前后端共享约定

### 2.1 阶段 A 接口

以下路径相对于当前用户数据 API 前缀 `/user/custom`，继续由现有挂载方式提供服务。

| 接口 | 请求 | 成功结果 |
| --- | --- | --- |
| GET `/all`、`/data-by-point`、`/data-by-feature` | 保持原参数 | 每条记录增加必填正整数 `id`，保留原字段 |
| PUT `/batch-update` | `{ "items": [{ "id": 123, ...全部可编辑字段 }] }` | `{ "success": true, "updated_count": 1, "data": [完整记录] }` |
| DELETE `/batch-delete-by-id` | `{ "ids": [123, 124] }` | `{ "success": true, "deleted_count": 2, "deleted_ids": [123, 124] }` |

单条编辑也调用 `/batch-update`，`items` 长度为 1。更新采用完整可编辑字段提交，不混用 PUT 全量语义和局部 PATCH 语义。允许编辑字段为 `簡稱`、`音典分區`、`經緯度`、`聲韻調`、`特徵`、`值`、`說明`；明确的空说明用空字符串提交，声韵调暂维持现有用户批量创建允许空串的行为。

安全约束：禁止客户端设置 `user_id`、`username`、`created_at`、`存儲標記`、`maxValue`；身份从登录态取，派生值由后端计算。ID 只定位当前用户自己的记录。

请求整批必须 1—50 条，拒绝重复 ID；任意目标缺失或不属于当前用户时，不区分泄露归属，返回统一错误且不修改任何记录。不会自动拆批后声称全量原子成功。超过 50 条时前端要求缩小选择，若用户主动分批，每批有独立事务。

### 2.2 校验与错误

建议新接口采用以下明确上限，实施前用隔离库字段长度分布确认能覆盖现有正常数据；如需放宽，前后端常量同时改，不静默截断历史长字段：

- 简称、音典分区、特征各 200 字符；声韵调 100；坐标串 100；值和说明各 4,000。
- 简称、音典分区、坐标、特征、值去首尾空白后不能为空。只 trim 边缘，不改动值内部格式。
- 坐标沿用当前客户端 `formatCoord` 的经纬顺序和输出格式；先读已有解析代码并固定测试样本，再检查有限数值、经度 [-180, 180]、纬度 [-90, 90]。不在迁移中交换经纬度。
- 编码后的新写接口请求体最多 2 MiB，在路由级 ASGI 接收包装中累计实际分块字节并拒绝超限，不能只信任 Content-Length，也不能等完整解析后才拒绝。只作用于新写路径，不影响上传接口。

错误结构统一为 `detail: { code, message, errors? }`；行级错误使用 `row_index`（从 0 开始）和 `field`。不回传其他用户的记录内容。

| 状态码 | code | 前端处理 |
| --- | --- | --- |
| 401 | `authentication_required` | 登录提示，保留草稿 |
| 404 | `record_unavailable` | 刷新服务端状态，不自动丢弃草稿 |
| 409 | `ambiguous_identity` / `version_conflict` / `idempotency_conflict` | 保留草稿并要求核对冲突 |
| 413 | `request_too_large` | 缩小内容，不重试 |
| 422 | `validation_error` | 定位具体行/字段，不执行写入 |
| 429 | `quota_exceeded` / `write_capacity_exceeded` | 显示原因，遵循 Retry-After |
| 503 | `database_busy` | 整批失败；允许用户稍后重试，不能前端循环重试 |

数据库异常响应不暴露 SQL 和原始内部异常。框架产生的 Pydantic 错误也应适配为可定位错误；允许在 API 包装层兼容原生 `detail` 数组。

### 2.3 事务原则

先完成纯字段校验，再打开数据库写事务，整批查询归属，再修改并一次提交。所有异常显式 rollback，finally 关闭 Session；查询校验与写入必须在同一个事务，不在逐行循环里 commit。

更新保留 `id`、`created_at`、`存儲標記`，只对值发生变化的记录重算 `maxValue`。SQLite 不使用无效的 `SELECT FOR UPDATE` 假装有行锁；采用显式、短生命周期的 `BEGIN IMMEDIATE`，先取得写事务再读取校验，使配额、归属、版本检查与写入处于同一串行写边界。测试确认与 SQLAlchemy 的隐式事务配置兼容，失败时不得退化为无保护的多次提交。

## 5. 阶段 B：地图原子保存和重复请求

### B1. 新保存协议

新增 POST `/save`，一个请求中包含：

```json
{
  "request_id": "UUID",
  "creates": [{ "client_row_id": "draft-1", "簡稱": "甲地", "音典分區": "甲区", "經緯度": "113.0,23.0", "聲韻調": "", "特徵": "阴平", "值": "55", "說明": "" }],
  "updates": [],
  "deletes": []
}
```

`updates` 使用 A 阶段完整行结构；B 阶段 `deletes` 为 `{ "id": 123 }` 数组，预留阶段 C 版本字段。新增、修改、删除合计 1—50，跨数组重复 ID 拒绝。同一请求可以把旧地点的已有 ID 更新到新地点；不通过地点名称扩大删除范围，不会删除用户没提交的其他记录。

返回 `success`、各操作计数、`created: [{client_row_id, id}]`、`updated_ids`、`deleted_ids`、`request_id`。完整记录另行 GET 获取，限制回执大小。保存成功后刷新失败属于读取错误，不能提示“保存失败”再执行一遍保存。

## 7. 资源、失败和在线请求影响

- [ ] 所有本次涉及的用户写入口复用每 worker 一个非阻塞 `BoundedSemaphore(1)`。获取失败立即 429，释放放在 finally，先门禁再开 Session，不在数据库连接池里无限等待。多 worker 总上限随现有 worker 数变化；SQLite 跨进程仍仅一个写入者，不增加 worker 数。
- [ ] 新同步路由或现有异步路由的完整同步事务在线程执行入口完成；不得在 async 事件循环直接等待 SQLite 锁。门禁不消除线程成本，不把多个逐行线程视为优化。
- [ ] 不增大现有连接池；复用目前 supplements 的 5 秒 busy_timeout。锁等待可能占用执行线程，超时统一返回 503；不自动无限重试，不休眠持有连接。
- [ ] 解析后常驻工作集最多 50 行、请求体最多 2 MiB、幂等回执有容量上限。字段长度与请求字节上限共同限制最坏输入；不加载全用户数据来验证 50 个目标。
- [ ] 新建隔离基准脚本，使用临时文件 SQLite，记录真实查询计划、SQL 次数、事务耗时、锁等待、进程 RSS、接口 p50/p95。场景为 1/10/50 行、1/2/4 个竞争请求；一次在线 GET 探针与写请求共存测响应。
- [ ] 基准只在隔离库运行，不复用生产路径，不修改线上数据；同时测旧流程作为对照。没有测量前不写“节约多少内存/快多少”的结论。
- [ ] 上线前在 2 核、2 GB 等效环境记录基线和新值；若在线 GET p95 恶化超过基线 20% 或出现连接池耗尽，停止发布并缩短事务/降低接入，不以增加线程补救。
