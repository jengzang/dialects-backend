# Vocabulary 分页选路修复设计

用户已批准分段测量报告中的三项修复，并要求直接开始。沿用当前 dev 工作区，不触碰无关未跟踪文件；生产保持只读，本轮不部署。

方案选择：仅移除结果 COUNT 无法解决分页扫描；全局强制地点索引会使宽范围退化。采用按请求、有限预算的地点解析与索引方案，将分页选路独立于总数加载，覆盖后续页，保留宽范围回退。

保持 API 的精确 total、模糊 locations 语义、简繁、排序、孤立词条和跨用户身份不变。原始 count SQL/values 保留为现有 Redis 总数键签名。完整结果缓存命中继续不查数据库；独立总数缓存为零或页码越界时不做规划或分页。旧私有二参数 count loader 保留原路径，作为兼容及结果对照入口。

将 scope/literal 的分页 SQL 准备移出 execute_count，按需最多运行一次。scope 支持所有页；原有多字预过滤仍只在已经验证的首页形状启用，但总数 hit 不再阻止准备分页。规划、COUNT miss 和分页保持在同一读 SAVEPOINT；异常释放自己的 SAVEPOINT，不提交/回滚调用方事务。

移除规划的全库精确 COUNT，优先读取 sqlite_stat1 现有地点索引的词条数估计（仅用于成本选择）。无统计或格式无效时只计数最多 4097 条索引记录：小表按实际小规模预算，未知大表保守使用旧 32768 上限。陈旧统计只影响选路，不改变结果。

Entries 的测量目标“路 + 22 地点”有 63382 个候选，因此评估上限 65536、估计覆盖比例 1/4；每次候选 probe 最多读取 65537 条索引项，只返回一个计数。聚合端点保留 32768 / 1/10 的预算政策，仅共享廉价规模估计改进。地点名和额外身份各最多保留 256，最多 32 个地点条件；不物化词条 ID 列表。更宽范围/超限解析继续原正确查询，不截断结果。最终是否保留该 entries 预算由真实副本及宽范围对照测量决定。

现有 heavy=2、expensive=1、在线 waiters=8 不变。全部规划/SQL 留在原有有界工作槽内；没有新的线程、常驻服务、缓存键、后台任务或重试。新内存仅为固定上限地点集合与 SQL 绑定，SQLite 缓存不变；报告实测峰值，不承诺生产 worker 内存。

验证：先新增红测试证明缓存 hit/后续页路径退化和全库预算 COUNT，然后实现；覆盖缺失/陈旧统计、预算边界和回退、跨用户/孤立/重叠匹配、零结果/越界、WAL 并发写和事务异常。运行 vocabulary 相关回归及隔离 Redis 集成测试。用同一生产副本、同版 SQLite、相同本地资源限制比较修复前后，核对 total 与每页全部内容/顺序，加入宽范围、全库和深页控制组。测量不等于线上十几秒已定位或 OOM 已修复。
