# 词表聚合与地图明细的磁盘处理设计

状态：用户已否决，未实施。用户明确以提速为主要目标，不接受默认使用临时磁盘聚合换取内存下降；后续不得以本文作为已批准实施方案。

## 范围与约束

面向 2 核、2 GB 单机，处理 standard-words 的全部分组内存增长与 map-items 的全量复制。保留接口参数、JSON 字段、分组、排序、计数、简繁匹配及已有 limit 语义。内部 limit=None 仍返回全部标准词组，map-items 返回全部匹配明细。不新增服务、worker、数据库持久化表或索引。前端继续按完整 JSON 消费。

## 已确认的现状

- query_vocabulary_standard_words 保存所有归一词组、地点集合和词形计数，有限 limit 只能减少最终结果对象，不能减少分组占用。
- query_vocabulary_map_items 同时建立 fetchall 结果、逐行字典、分组列表、dataclass 列表；HTTP 响应验证和缓存编码可能继续复制。
- 地图分组由地点名、原始坐标及八个行政/分区字段共同决定，并不等于 user_id/location_name。点按最早命中 e.id 排序，每个点的 items 按 e.id 排序。无有效坐标的记录仍计入 total_entries 和 omitted_without_coordinates。
- 前端使用 response.points 等 JSON 字段，并不要求后端先在内存建立整个响应。

## 方案比较

1. 临时磁盘聚合与结果文件（推荐）：每次缓存未命中依旧计算，增加磁盘 I/O；不增加持久化一致性负担，可覆盖任意搜索和地区过滤，工作内存不再随总分组/明细数量线性增长。
2. 持久化汇总表：适合默认查询反复读取，但任意 q、搜索字段、地区筛选不能简单复用全局汇总；还需处理所有导入、SQL 编辑、地点修改、简繁规则版本和重建。后续只有实测证明 CPU/I/O 成为主要瓶颈再引入。
3. 仅逐行查询后原样返回列表：能减少复制，但完整分组和最终响应仍占内存，不能解决本次长期增长问题。

推荐第一项。本轮不承诺未经测量的峰值内存或延迟。

## 标准词处理

复用现有筛选 SQL，按游标读取词形、地点、计数；分批写入独立临时 SQLite 文件。使用现有 standard_word_key 归一化，沿用有界转换缓存。地点去重使用磁盘键表，词形计数使用磁盘聚合。SQLite page cache 明确设为有界，排序临时数据使用文件。

在磁盘上计算每组 entry_count、location_count、代表词和排序。保持原排序：地点数降序、条目数降序、代表词 Python 字符串升序；必要时显式实现一致比较。代表词和 variants 按词形计数降序、词形升序。total 始终是所有匹配归一词组数。有限 limit 只作用于最终输出，不改变 total。全量结果及超大 variants 数组逐元素写入 JSON 文件，不能在内存积累单个巨型分组。

## 地图明细处理

保留筛选与简繁匹配逻辑，按 e.id 读取；逐批暂存分组身份、首次出现 ID、元信息和条目。磁盘分组键必须精确保留 NULL、空字符串和原始坐标差异，不能改成按用户或地点 ID 分组。

按首次出现 ID 输出点，点内按条目 ID 输出 items。逐条转换/验证并写 JSON；即使所有条目只属于一个点，也不建立完整 items 列表。统计保留原规则。源数据库读取完成后释放游标/快照；下载只读取结果文件，不持有源数据库连接。

## HTTP 与缓存

引入共用的临时 JSON 结果对象与响应清理机制。完整计算、逐项验证和文件写入成功后才发响应头，Content-Type 保持 application/json，保留 OpenAPI response_model 文档。不添加下载附件语义。文件按有界块发送，客户端仍接收一个完整 JSON 对象。

不能让 FastAPI 的全量模型验证或缓存的 jsonable_encoder 再将大文件读回内存。现有 Redis 修订失效与任务合并逻辑需适配文件结果：小结果在现有缓存大小上限内缓存；大结果跳过 Redis 内容缓存，绝不先完整编码再判断大小。不新增无界本地结果缓存。读取旧缓存的路径也必须遵守当前响应结构。

## 资源与失败

沿用单机跨 worker 的两个重任务槽、一个昂贵任务槽、八个等待槽及 30 秒准入等待；不增加执行超时，不自动重试昂贵计算。磁盘任务在既有工作线程内执行，不阻塞事件循环。

生成阶段占用昂贵槽；发送阶段释放计算槽。另设有界的在途结果文件名额，包含生成和下载阶段，避免慢客户端下载无限堆积文件；名额上限及排队纳入测试并记录。缓存命中亦不能绕过大结果资源边界。

提供专用临时目录配置，文档明确要求实际磁盘（tmpfs 会消耗内存）。设置 SQLite 内存缓存和读写批次上限；总磁盘需求仍随数据/输出量增长，不能承诺常量磁盘。磁盘不足、编码失败在发送响应前返回错误，不返回截断的成功 JSON。正常完成、发送异常、取消均关闭/删除中间文件与结果；异常退出遗留文件使用仅清理确认无活动持有者的机制，禁止按文件年龄删除正在下载的结果。

## 验证与验收

先补资源回归测试并确认旧实现失败，再实施。覆盖简繁合并、词形并列、跨用户同名地点、NULL/空串分组、坐标缺失、过滤、空结果、大单组、多组、全量及有限 limit。

对旧/新实现相同输入的完整解析 JSON 做逐项比较，保留列表顺序和全部计数；比较 OpenAPI、前端现有接口测试。测试缓存命中/未命中、Redis 不可用、取消、发送失败、磁盘失败及所有槽/文件释放。

独立进程测量旧/新服务及 HTTP 文件生成路径的峰值 RSS、耗时、临时磁盘峰值；至少包括现有规模、词形/地点增长、多点地图及全部条目属于一个点，且必须消费全部输出。报告运行环境和测试数据，区分本地测量与生产容量预测。不得以截断、只测前 100 项或不消费响应证明资源改善。
