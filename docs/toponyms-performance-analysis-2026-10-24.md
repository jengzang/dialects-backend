# Toponyms 性能分析与优化方案（2 核 / 2 GB）

日期：2026-10-24。范围：当前 `/api/toponyms/{points,search,names,details,divisions}`。

本次只分析并执行本地只读实验，没有修改业务代码、数据库表或索引，也没有连接生产服务器。这里的“模糊匹配”主要指 `contains`，同时分析 `suffix`、`prefix`。它不是拼写容错或相似度搜索。

## 1. 结论与优先级

推荐先做后端优化，再决定是否加索引。当前最值得解决的不是索引数量，而是：

1. **P0：名称树每次全量加载 739,719 条行政区数据。** 本地单独运行现有加载函数，峰值 RSS 增量约 501 MiB；并发请求可能放大峰值。
2. **P0：公开查询允许 `limit=0`，非零上限达 2,000,000。** SQL `fetchall()`、Python 对象、Pydantic 模型及 JSON 编码会叠加成本。
3. **P1：points 的排序让优化器选择 type/id 索引，名称筛选需要大量回表。** 利用已有名称覆盖索引先选 ID 再取坐标，本地验证有明显改善。
4. **P1：树接口完整去重计数、重复扫描、Python 遍历全行政区、深分页放大工作量。** “lazy”目前只限制部分响应，不代表计算轻量。
5. **P1：没有地名业务专用的有界执行、SQL 截止时间和结果缓存。** 通用 ApiLimiter 与线程池不能替代资源调度。
6. **P2：全国任意包含匹配仍有扫描下限。** 若上述优化后长尾请求仍不达标，再考虑区域索引或中文子串倒排索引。

## 2. 数据规模与真实索引

本地数据库约 4.86 GiB（1,274,980 × 4096 字节）。`sqlite_stat1` 记录 single 9,359,099 行、multi 2,106,635 行；这两个总量是统计信息，并非本次重新全表计数。

本次精确计数：默认类型 `22200` 在 single 中有 **4,343,313 行**，在 multi 中为 **0 行**。不能据此在代码中永久跳过 multi：其他类型及后续数据版本可能包含记录。

行政区实测共 739,719 行，其中 level 5 有 666,655 行，level 4 有 68,918 行。不得简单删掉 level 5 的加载逻辑，否则可能破坏 area_code 对应关系与祖先路径。

本地已有维护脚本列出的全部七个联合索引：

- single：`(place_type_code,id)`、`(place_type_code,standard_name,id)`、`(place_type_code,standard_name,area_code)`、`(place_type_code,longitude,latitude,id)`。
- multi：对应的前三种索引。
- divisions：code 主键、parent_code 索引、level 索引。

| 模式 | 现有名称索引能力 | 解释 |
|---|---|---|
| exact | 支持按类型和名称定位 | 实测计划包含 `place_type_code=? AND standard_name=?` |
| prefix | 支持名称范围定位 | 代码已有显式 `>= prefix AND < upper_bound`，计划包含名称上下界 |
| contains | 只能按类型缩小候选，不能按任意子串定位 | `LIKE '%黄村%'` 仍逐项判断名称 |
| suffix | 同样不能按后缀定位 | `LIKE '%村'` 无名称起始范围 |

所以“contains 用了索引”与“contains 能索引查找”不是一回事。它可以扫描较紧凑的覆盖索引、利用索引顺序提前停止，但稀有词、无结果词仍可能遍历整个类型范围。

## 3. 本地测量与执行计划

实验条件：本地 macOS，Python sqlite3 / SQLite 3.53.2，以 `mode=ro` 连接；SQL 测试使用 `cache_size=-16000` 和 `temp_store=MEMORY`。查询顺序执行，操作系统缓存未清空，无并发压测。记录为单次观察值，**不是生产延迟、冷缓存指标或 p95/p99**，也不包含鉴权、中间件、HTTP 与响应编码。

| 操作 | 结果 | 本地耗时 |
|---|---:|---:|
| search contains 黄，limit=100（内部取 101） | 101 行 | 18.6 ms |
| search contains 黄村，limit=100 | 101 行 | 13.7 ms |
| search contains 不存在的地名XYZ | 0 行 | 235.5 ms |
| points contains 黄，limit=5000（内部取 5001） | 5001 行 | 3964.8 ms |
| points contains 黄村，limit=5000 | 990 行 | 7350.1 ms |
| points contains 不存在的地名XYZ | 0 行 | 6812.9 ms |
| names contains 黄村，limit=20 | 20 行 | 4.2 ms |
| names contains 不存在的地名XYZ | 0 行 | 181.6 ms |
| single 分支 prefix 黄，limit=101 | 101 行 | 0.4 ms |
| 树：contains 村，完整 DISTINCT name/area 计数 | 922,507 | 266.5 ms |
| 树：同样条件仅探测 5001 对 name/area | 5001 行 | 2.5 ms |

search 实际采用 `MERGE (UNION ALL)`，两个分支使用 type/name/id 索引，无该样例下的全局临时排序。因此不能笼统认为 UNION ALL 必然导致全量排序。多类型样例则出现临时排序，应单独测试。

points 当前采用 `idx_single_type_id (place_type_code=?)`。该索引没有 standard_name，名称匹配要回表。bbox 样例选择 type/lng/lat/id 索引，但只用类型和经度范围缩小索引访问范围；纬度继续过滤，并出现排序临时 B-tree。这不是完整二维空间索引。

区域 descendants 样例只显示名称索引上的类型约束，`area_code LIKE '44%'` 没有转成有效的区域索引范围。

独立子进程用 AST 提取并原样运行 `_load_divisions()`，使用 sqlite3.Row：加载 739,719 行耗时 1.318 秒；进程峰值 RSS 从 18.5 MiB 增至 519.5 MiB，峰值增量约 501 MiB。这是本机单函数测量，含查询、行对象和字典构建，不是 Python 对象保留大小，也不是 Linux 生产内存承诺。没有把该数值简单乘并发数当作精确预测。

## 4. 第一阶段：后端资源边界

### 4.1 返回量、输入量与超时

- 建议起始上限：search 500 条、普通 names 200 条、points 5000 条；保留默认 search=100、names=20。它们是待压测的配置起点。
- 在线接口不再接受无限量查询。`limit=0` 是现有公开语义，不能偷偷改成有限结果却仍宣称完整；应明确拒绝、迁移到分页，或以版本化方式调整协议。
- points 保留 `truncated`；普通 names 若需要完整性反馈，应增加分页/截断信息。真正全量导出另行设计，不能直接转后台后无限运行。
- 限制 q 长度、类型列表个数、parent_path 各段长度及页码；避免超大 IN 参数和深 OFFSET。单字包含搜索仍可支持，但全国单字查询受更严格并发和截止时间约束。
- 当前 `%`、`_` 会作为 LIKE 通配符。明确产品语义：若是字面包含，转义并使用 ESCAPE；若兼容通配符，则把纯通配符和低选择性模式纳入高成本限制。此处是行为调整，需要回归测试。
- `MAX_BBOX_AREA` 当前未被路由使用，zoom 也仅校验后丢弃。bbox 不应被误认为已有面积保护。若增加面积/缩放约束，要给调用方明确错误信息。
- SQL 使用 `set_progress_handler` 检查单调时钟，建议先评估 1–2 秒执行预算；队列等待预算另设。该机制为协作中断，不能保证阻塞 I/O 在绝对时刻返回。
- 不能只在 await 外包超时：线程里的 sqlite 查询可能继续消耗资源。中断/取消必须作用于该请求独占连接，归还前清理 handler，避免影响后续请求。

### 4.2 并发与连接池

当前 Gunicorn 配置为 3 worker。地名代码请求 pool_size=4；通常相当于 12 个基础连接。池耗尽后等待 30 秒，还可能尝试扩到两倍。池按数据库路径共享且首次创建决定大小，其他调用可能影响实际配置。

`cache_size=-16000` 每连接约 15.625 MiB 的页缓存目标：12 个连接合计约 187.5 MiB 的配置额度；并非启动时实占，也不是进程总内存上限。临时排序、去重、返回对象在此之外，`temp_store=MEMORY` 进一步放大内存风险。

建议：

- 地名重查询全实例先限制为 **最多 2 个执行中**，待验证；重型树构建最多 1 个。不要把每 worker 的 Semaphore(2) 误当成全局 2 个。
- 如保持 3 worker，可利用单机跨进程非阻塞槽位锁实现固定执行槽，进程退出自动释放；或复用已有 Redis 原子租约。Redis 方案必须处理租约续期、所有权校验和失联，不能租约过期而旧查询仍执行时放进新任务。
- 同步 SQL 开始前异步申请槽位，不占用共享线程等待连接。可先采用满额立即返回 503 + Retry-After；若短队列确有必要，每 worker 至多 2 个等待者、等待不超过约 100–200 ms，超限拒绝。
- 各 worker 地名连接池以严格上限 2 为候选，不再按压力扩容；对轻量 details/divisions 设置独立的小预算，避免与长扫描相互饿死。实现时明确全部连接总数。
- 地名连接页缓存可从每连接 4 MiB 起测试；使用按数据库配置，避免直接修改所有业务的共享池策略。临时存储 FILE 也不是免费优化，会增加磁盘 I/O，应在消除无界查询后比较 MEMORY/FILE 的 RSS 与延迟。
- 不增加 worker。是否从 3 调为 2 应结合全站 RSS 和其他接口压测决定，不以 CPU 核数公式直接下结论。
- 服务端不自动重试超时、过载或同一条昂贵 SQL；请求方退避并取消过时搜索。槽位释放必须发生在数据库实际停止之后。

## 5. 第二阶段：复用已有索引改查询

### 5.1 points：先查 ID，再取坐标

对无 bbox 的 contains/suffix 路径，实测候选 SQL 为：

```sql
SELECT id, longitude, latitude
FROM single
WHERE id IN (
    SELECT id
    FROM single INDEXED BY idx_single_type_name_id
    WHERE place_type_code IN (?) AND standard_name LIKE ?
    ORDER BY id
    LIMIT ?
)
ORDER BY id;
```

内部 LIMIT 为接口 limit+1。名称筛选在覆盖索引完成，只对最终有限 ID 回表取坐标，保留原来的 ID 排序和截断语义。

| 关键词 | 原 SQL | 候选 SQL |
|---|---:|---:|
| 黄 | 3.965 s | 0.797 s |
| 黄村 | 7.350 s | 0.420 s |
| 不存在的地名XYZ | 6.813 s | 0.245 s |

“黄村”的 990 条结果与排序已与原 SQL 完整比较，相等；其余样例只检查了返回数量和首条样本，不能当作全面等价验证。测量顺序存在缓存影响，需重复交错测量。

该方案仍扫描名称索引，并为 ID 排序做工作，不能保证所有关键词都更快。强制 INDEXED BY 是实验用来验证访问路径的手段；上线前要验证索引存在性、数据版本与计划，防止缺索引直接报错。bbox、多个类型、exact/prefix 各自评估；尤其 bbox 条件必须在 LIMIT 之前应用，不能先截断全国 ID 再过滤 bbox。

### 5.2 search：保持已有优势，避免无意义重写

默认不返回 area_code 时，当前 SQL 仍总是 SELECT area_code。无区域过滤的普通路径可以按实际所需字段投影，使 type/name/id 索引有机会成为覆盖索引；include_area_code=true 或区域过滤时使用另一条路径。

保留 UNION ALL 与稳定排序，优先看执行计划；不增加 COUNT(*)，不要为了缓存把有限查询升级为全量扫描。后续分页使用 `(name,id,source)` 等足以处理跨表同名/同 ID 的游标，明确合并顺序，不随意丢弃重复记录。

区域编码可考虑显式上下界加原条件复核，但必须验证编码、排序规则与边界。仅改 `LIKE '44%'` 为范围条件不会凭空产生 type/area 联合索引；名称列在现有索引中排在 area 前面，也限制区域列的定位能力。

### 5.3 名称树：去掉全量行政区加载

- 完整树先获取最多 5001 个 DISTINCT `(standard_name,area_code)`，在小于等于 5000 时直接复用这批数据构建树，避免 COUNT 后再查一次。
- 超过阈值只表示“至少 5001 条”。当前响应强制要求精确 `filtered_count`，已有测试验证；应新增 `count_exact=false` / `count_lower_bound` 或可选字段等协议，不能把 5001 冒充精确总数。如果必须保留精确总数，就保留对应扫描成本并考虑有限缓存。
- 仅加载命中 area_code 的行政区及其祖先。批次建议 200–500 个 code，用 code 主键查询；深度设置合理上限和循环检测。不要每条结果独立递归查询形成 N+1。
- parent_path 由根向下，依靠 `parent_code` 索引分层解析，保留同名分支；不再遍历 74 万节点，为每个节点构造完整路径。
- lazy_bootstrap 和节点展开仍可能扫描全部命中区域。先去除无界 fetchall，以有界批次迭代、按请求预算执行；中间状态设硬上限，超限明确降级/错误，不能伪造完整 children。
- 只有在祖先映射和结果语义验证后，才按当前层投影、去重。不要对每个行政区运行一次全国模糊查询。
- 叶子分页逐步改游标；现有 DISTINCT name/area 语义及多同名区域要保持一致。过渡期限制深页，不把 LIMIT 当作扫描行数的上限。
- 行政区路径缓存只存最近访问的小集合，按字节预算淘汰；不把整个行政区表常驻缓存作为解决方案。

### 5.4 其他接口

details 最多 10 个 ID，主键查询是合理基础。当前字典推导先计算路径、再按 area_code 覆盖，同区域仍会重复查询祖先；应先去重 area_code，并合并祖先查询。

divisions 已有 parent_code 索引，通常优先级较低；可缓存小响应。其全量 children 响应仍应检查最大父节点规模。

路由里的 SQL 已在线程池执行，这是正确基础；但返回后构造 Pydantic 模型和响应编码仍有 CPU/内存成本。优先限制结果大小，再评估是否需要线程内编码或其他序列化调整，不能只把所有工作换成 async。

## 6. 缓存与重复请求合并

先缓存小而常用的 search/names、有限 points 响应与行政区路径；不缓存所有关键词的全量候选集。

- 候选配置：每 worker 本地缓存序列化值总量上限 4 MiB、最多 256 项、单项 128 KiB；该字节上限不含 Python 容器开销，需测 RSS。3 worker 有三份缓存。
- 正常结果 TTL 30–120 秒，空结果短 TTL（如 10 秒），不缓存超时/失败。不要在启动时批量预热。
- 缓存键包含数据库版本、接口、q、match_mode、排序后的类型集合、area_scope/area_code、bbox、limit/游标、字段开关和树模式。不要把 contains 与 prefix 混用，也不要擅自把 bbox 四舍五入改变边界。
- 同 worker 相同 key 合并为一次执行，等待者受前述队列上限约束。跨 worker 若需合并，复用现有 Redis 的短期结果与锁，但须独立限制本业务 key 数和字节预算，不能只靠 TTL 或改全站 Redis maxmemory。
- Redis 失败按短超时降级到本地受限路径；无无限重试、无重复启动后台刷新。部署新数据库时切换版本并失效缓存。

## 7. 第三阶段：只有测量证明必要时才改数据库

| 选项 | 适用条件 | 代价与限制 |
|---|---|---|
| 仅后端改造（首选） | 先解决内存、重复扫描、回表、并发争用 | 全国罕见子串仍需要扫描，不能承诺所有查询常数时间 |
| 增加区域优先联合索引 | 大部分请求能带省/市/县范围 | 可评估 `(place_type_code,area_code,standard_name,id)`；缩小区域候选，但区域范围后未必能直接满足名称排序，覆盖坐标会进一步增大磁盘 |
| 专用中文子串索引 | 全国 1–2 字 contains 长尾仍不满足目标 | 建库与维护更复杂，需要独立测空间、更新成本和线上 RSS |

不要再加一个普通 standard_name B-tree 并期待它支持任意 contains，也不要直接引入 Elasticsearch/额外常驻搜索服务。

SQLite FTS5 trigram 值得作为实验候选，但不是直接答案：需要生产 SQLite 支持；通常至少连续 3 个字符才有可用 trigram，一字“黄”、两字“黄村”无法得到同样收益。默认 unicode61 分词也不是中文任意子串索引。使用 ESCAPE 等 SQL 写法可能影响 FTS5 LIKE 优化，必须检查对应计划。

如果实际日志证明一、二字全国包含查询是主要长尾，可离线评估 unigram/bigram 倒排：索引单字和相邻双字，对更长查询选择稀有 gram/求交后回原表验证完整 LIKE。候选流式处理，限制结果、执行时间和临时集合；不能先把所有 ID 拉入 Python。单字“村”的倒排列表仍可能很长，索引不能消除本身极低选择性的成本。

后缀若单独占比很高，可评估反转名称索引；它不能解决一般 contains。空间 R-tree 只在 bbox 测量证明值得时评估，不与本次名称优化捆绑建设。

所有新索引先在离线副本创建、ANALYZE、验证容量和计划，单构建任务运行；失败人工/受控重试，不与线上查询竞争 CPU、I/O。上线保留旧库/旧查询路径回滚，原子切换时协调连接池生命周期。不要在线反复执行整个建索引脚本。

## 8. 实施顺序与验收

1. 加分段观测：排队、DB 时间、结果构建/编码、返回行数与字节、缓存命中、超时/拒绝、事件循环延迟、各 worker RSS/PSS、全机可用内存/Swap、CPU 和磁盘 I/O。
2. 优先去除全量行政区加载，限制响应量与重查询并发；这些是 2 GB 机器最紧迫的稳定性问题。
3. 改 points 的访问路径、search 字段投影、树阈值探测和路径解析；受协议影响的 limit=0、精确计数、分页单独迁移。
4. 加小缓存和相同请求合并，复测冷请求/热请求、不同关键词风暴，不以缓存命中样本掩盖首次查询成本。
5. 按结果决定区域索引或中文子串索引是否必要。

验收矩阵：四种匹配模式；1/2/3+ 字；常见/罕见/零结果；单/多类型；有无 bbox；精确/后代区域；树根/节点/叶子；特殊通配符；正常 limit 与边界输入。对 SQL 改写比对完整结果、顺序、truncated 和字段契约。
